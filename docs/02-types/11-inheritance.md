# 11. Наследование и интерфейсы

**Результат:** вы вызываете разные реализации через общий контракт и отличаете переопределение от скрытия.
Нужны главы 08–10. Запускаемый пример: `dotnet run --project examples/TypesAndQueries -- 11`.

## Подстановка объекта

Переменная имеет статический тип, известный компилятору. Объект имеет фактический тип во время выполнения.
Переменная базового типа может ссылаться на объект производного типа. Доступные члены выбираются
по статическому типу; реализация virtual-метода — по фактическому.

```csharp
Report report = new DetailedReport();
Console.WriteLine(report.Title); // Detailed

abstract class Report
{
    public abstract string Title { get; }
    public virtual string Format() => Title;
}

sealed class DetailedReport : Report
{
    public override string Title => "Detailed";
}
```

Это самостоятельный Program.cs: инструкции идут перед типами.
Abstract-класс нельзя создать через new. Abstract-член требует реализации в конкретном потомке.
Virtual имеет реализацию по умолчанию; override заменяет её в цепочке виртуальных вызовов.
Sealed запрещает дальнейшее наследование; sealed override запрещает следующее переопределение.

У класса один непосредственный базовый класс, но интерфейсов может быть несколько.
Конструктор потомка вызывает конструктор базы, при необходимости через `base(...)`.
Не вызывайте переопределяемый метод из конструктора базы: он может обратиться к ещё не
инициализированному состоянию потомка.

## Скрытие не равно переопределению

```csharp
BaseLabel first = new NewLabel();
NewLabel second = new();
Console.WriteLine(first.Name());  // base
Console.WriteLine(second.Name()); // new

class BaseLabel
{
    public string Name() => "base";
}
class NewLabel : BaseLabel
{
    public new string Name() => "new";
}
```

New явно сообщает о скрытии члена. Здесь выбор зависит от статического типа переменной.
Если нужен единый полиморфный вызов, объявите базовый метод virtual и используйте override.
Отсутствие предупреждения после добавления new ещё не доказывает правильность проекта.

Override некоторых методов и get-only свойств может возвращать более конкретный ссылочный тип,
чем база: это ковариантный результат. Например, базовый Clone возвращает Report, а производный —
DetailedReport. Параметры нельзя произвольно сузить: контракт базы должен оставаться применимым.

## Интерфейс как граница

Вместо «сервис знает List» сформулируйте нужную ему операцию хранения:

```csharp
public interface IExpenseStore
{
    bool TryAdd(Expense expense);
    IReadOnlyList<Expense> Snapshot();
}
```

Это фрагмент контракта L02; тип Expense появится в её библиотеке.
TryAdd возвращает false при повторном идентификаторе. Snapshot обещает отдельный снимок данных,
который не изменится после следующего добавления. Сигнатура не описывает эти обещания полностью:
их нужно записать в документации и проверить на каждой реализации.

Реализация `InMemoryExpenseStore : IExpenseStore` хранит Dictionary внутри.
Сервис принимает IExpenseStore в конструкторе. При замене хранилища правила расчёта не меняются.
Это внедрение зависимости вручную; DI-контейнер для такого проектирования не требуется.

## Явная реализация и default members

Если два интерфейса имеют конфликтующие члены, можно реализовать их явно:

```csharp
interface IText { string Render(); }
interface IJson { string Render(); }

sealed class View : IText, IJson
{
    string IText.Render() => "text";
    string IJson.Render() => "{}";
}
```

`((IJson)new View()).Render()` вызывает JSON-вариант. Вызова `new View().Render()` здесь нет.
Явная реализация доступна через соответствующий интерфейс; модификатор public перед ней не нужен.

Интерфейс может содержать реализацию метода по умолчанию. Она вызывается через интерфейс и
не добавляет обычный унаследованный член к самому классу. Такой механизм полезен для развития API,
но требует продуманного разрешения конфликтов. Интерфейс не хранит обычные поля экземпляра.

Static abstract и static virtual члены описывают возможности самого типа, например оператор или Parse.
Доступ к ним обычно выполняется через параметр обобщённого типа с нужным ограничением.
Это не виртуальный вызов через экземпляр. Применение — generic math в главе 13.

## Когда выбирать композицию

Наследование утверждает, что потомок можно использовать вместо базы с сохранением обещаний.
Если в базовом хранилище Add разрешён, потомок ReadOnlyStore, который всегда бросает
NotSupportedException на Add, нарушает ожидания такого контракта.

Композиция означает «содержит и использует». Ledger содержит хранилище, не является хранилищем.
Разделите интерфейсы чтения и записи, если потребителям нужны разные возможности.
Не создавайте интерфейс только ради наличия буквы I: он полезен на настоящей границе поведения.

## Практика

**11-A.** Повторите пример со скрытием, затем замените new на virtual/override в соответствующих местах.
Критерий: сначала base/new, после изменения оба вызова дают new. Объясните выбор реализации.

**11-B.** Опишите `ITextWriter.Write(string)` и две реализации: накопление строк в памяти и вывод в Console.
Метод формирования отчёта принимает интерфейс. Критерий: обе реализации получают одинаковые три строки,
а тест памяти не перехватывает Console.

**11-C.** Разделите `IStore` с Read/Add на `IReader` и `IWriter`.
Критерий: компонент отчёта компилируется только с IReader; подстановка реализации чтения
не требует метода Add, бросающего исключение. Приведите пример нарушенного обещания старого интерфейса.
