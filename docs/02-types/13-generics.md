# 13. Обобщения и контракты типов

**Результат:** вы пишете повторно используемый алгоритм с проверкой типов при компиляции.
Нужны главы 11–12. Запуск: `dotnet run --project examples/TypesAndQueries -- 13`.

## Зачем параметр типа

Вместо контейнера object, который допускает смешение данных и требует cast, объявите тип элемента:

```csharp
static T FirstOr<T>(IReadOnlyList<T> items, T fallback)
{
    return items.Count == 0 ? fallback : items[0];
}
```

Это функция для размещения в Program.cs. `FirstOr(new[] { 3, 5 }, 0)` возвращает int 3.
Компилятор выводит T из аргументов; иногда тип указывают явно, например `FirstOr<string>(...)`.
Вывод не строится только из ожидаемого возвращаемого типа.

Generics не равны текстовой подстановке макроса. Параметры типов присутствуют в metadata,
а CLR и компилятор знают закрытые типы вроде `List<int>`.
Reflection позволяет различать открытый `typeof(List<>)` и закрытый `typeof(List<int>)`;
создание типов по метаданным будет в главе 21.

## Ограничения

Без ограничения T не имеет произвольного свойства Amount или метода CompareTo.
Ограничение делает нужную возможность частью контракта:

```csharp
static T Min<T>(T left, T right) where T : IComparable<T>
{
    return left.CompareTo(right) <= 0 ? left : right;
}
```

| Ограничение | Что оно сообщает |
| --- | --- |
| `class` / `class?` | Ссылочный тип с соответствующим nullable-намерением |
| `struct` | Non-nullable value type; `Nullable<int>` не подходит |
| `notnull` | Non-nullable reference или value type |
| `unmanaged` | Value type без управляемых ссылок в составе |
| Базовый класс / интерфейс | Доступны обещанные им члены |
| `new()` | Можно вызвать доступный конструктор без параметров |

Notnull в nullable-анализе может приводить к предупреждению, а не безусловной ошибке языка;
в проектах курса предупреждения считаются ошибками. Он не валидирует данные во время выполнения.

Основное ограничение идёт первым, затем интерфейсы, new() — после обычных ограничений.
Struct уже подразумевает возможность создания значения без параметров, поэтому с new() его не объединяют.
Unmanaged несовместим с одновременным struct/new(). Полный набор допустимых сочетаний следует проверять
по [справочнику ограничений](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/generics/constraints-on-type-parameters).

У специального `where T : default` другая задача: он уточняет отсутствие class/struct-ограничения
при override или явной реализации, где важно толкование T?. Это не требование «T имеет default».
Антиограничение `allows ref struct` разрешает T быть ref struct, идёт после остальных ограничений
и требует соблюдения правил безопасности ссылок; с class/class? его объединить нельзя.
Практические ref struct будут в главе 23.

## Отсутствие значения и Result

Для произвольного T запись T? нельзя всегда понимать как `Nullable<T>`.
При T=string это nullable-аннотация; при T=int без struct-ограничения это не универсальная
команда «завернуть int в `Nullable<int>`». Контракт должен явно определять, как представляется отсутствие.

В L02 используем `Result<T> where T : notnull`: либо успех со значением T,
либо отказ с кодом ошибки. Фабрики Success и Failure скрывают конструктор.
Value доступен только при успехе; при ошибке чтение Value бросает InvalidOperationException.
Так результат не допускает комбинацию «успех без значения» или «ошибка без причины».

```csharp
// Фрагмент после объявления Result<T> из L02.
Result<int> result = Result<int>.Success(42);
if (result.IsSuccess)
{
    Console.WriteLine(result.Value);
}
```

Не кодируйте отсутствие результата только как default(T): 0, false и пустая структура могут быть
нормальными значениями. Ошибка duplicate_id — ожидаемое бизнес-событие, а не повод аварийно завершать процесс.

## Вариантность

Ковариантный параметр `out T` используется как выход. Например,
`IEnumerable<string>` можно присвоить `IEnumerable<object>`: чтение string как object безопасно.
Контравариантный `in T` описывает вход: обработчик object может обработать и string.

Такие преобразования вариантности действуют для ссылочных типов.
`IEnumerable<int>` не превращается в `IEnumerable<object>` автоматически.
`List<string>` не является `List<object>`: иначе через вторую ссылку можно было бы записать число.
Объявлять in/out разрешено на параметрах интерфейсов и делегатов, а не обычных классов.
Окончательные правила позиций учитывают вложенные делегаты, поэтому проверяйте сложные случаи компилятором.

## Статические данные и generic math

У `Cache<int>` и `Cache<string>` собственные статические поля.
Не ожидайте одного общего счётчика на все закрытые варианты типа.

Статический интерфейсный контракт позволяет выражать операции над T без dynamic:

```csharp
using System.Numerics;

// Метод внутри класса или локальная функция Program.cs.
static T Add<T>(T left, T right) where T : INumber<T> => left + right;
```

INumber обещает числовые операции, включая нужный оператор. Вызов `Add(2, 3)` даёт int 5,
а `Add(1.5m, 2m)` — decimal 3.5. Доменный Money не обязан реализовать весь числовой интерфейс:
не все действия обычного числа имеют смысл для денег. Берите минимально достаточный контракт.

## Практика

**13-A.** Реализуйте Min с IComparable. Критерии: Min(3,5)=3, Min(5,3)=3, равные числа сохраняют значение.
Для строк явно обсудите, какое правило сравнения вам нужно и почему CompareTo зависит от культуры.

**13-B.** Реализуйте `Result<T>` с закрытым конструктором и фабриками.
Критерии: Success(0) является успехом; Failure("duplicate_id") не выдаёт Value;
пустой код ошибки и null в `Result<string>.Success` отклоняются при выполнении.

**13-C.** Объявите `IProducer<out T>` с Get и `IConsumer<in T>` с Accept.
Критерий: объяснены безопасные направления преобразования для string/object.
Отдельно покажите некомпилируемый контрпример для `List<string>`/`List<object>`.
