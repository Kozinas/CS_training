# 18. Практикум библиотеки предметной области

**Результат:** правила расходов, контракт хранения и месячный отчёт доступны независимо от Console и файлов.
Нужны главы 11–17. Полный договор — в [лабораторной L02](../../labs/02-domain-library/README.md).

## Что меняется после L01

В L01 текстовая строка проходила разбор и участвовала в отчёте.
Теперь правила должны использоваться повторно: из консоли, будущего импортёра и веб-сервиса.
Текст `12.50` относится к формату ввода, положительность расхода — к предметной модели.
Если смешать их в одном методе, каждый новый интерфейс будет копировать проверки.

Добавляется самостоятельная библиотека ExpenseLedger.Core. В ней нет Main:
другие проекты вызывают её публичные типы. Классическая структура csproj:

```xml
<Project Sdk="Microsoft.NET.Sdk" />
```

В примерах курса net10.0 и остальные настройки наследуются от Directory.Build.props.
При создании отдельного проекта вне examples используйте `dotnet new classlib --framework net10.0`
или явно задайте TargetFramework в собственном csproj.

## Зависимости проектов

```text
TypesAndQueries (демонстрационный клиент) → ExpenseLedger.Memory → ExpenseLedger.Core
                 └───────────────────────────────────────────────────────┘
CoreChecks (проверки) ───────────────────→ обе библиотеки
```

Стрелка означает ProjectReference. Core объявляет IExpenseStore, потому что описывает
операции, нужные сервису. Memory реализует этот контракт через Dictionary.
Core не ссылается на конкретное хранилище, Console, чтение файлов или другой клиент.

Такое направление не требует фреймворка. Клиент явно создаёт хранилище и передаёт его
в конструктор сервиса. Подмена тестовой реализацией не меняет расчёт.

## Типы и их обещания

| Тип | Обещание |
| --- | --- |
| Money | Неотрицательная величина одной условной денежной единицы, точность до сотых, default=0 |
| Expense | Непустой Id, нормализованная категория, положительная сумма не выше 999999.99 |
| `Result<T>` | Успех со значением либо отказ со стабильным кодом |
| IExpenseStore | Добавление по уникальному Id и отдельный read-only снимок |
| LedgerService | Добавление с уведомлением и детерминированный месячный отчёт |
| CategoryTotal | Неизменяемые данные строки сформированного отчёта |

L02 не смешивает разные валюты. Если нужны валюты, контракт Money должен включить валюту,
запрет смешения и правила конвертации. Не угадывайте валюту по культуре ОС.

Expense — record class с get-only свойствами. With не должен позволять присвоить недопустимую сумму.
Внешний код не получает List, принадлежащий хранилищу. IReadOnlyList сам по себе не гарантирует
неизменность: реализация возвращает обёртку над собственной копией элементов.
Поскольку Expense неизменяем, такой снимок достаточен для текущего контракта.

## Ожидаемый отказ и исключение

Повторный Id — ожидаемый результат Add: Failure("duplicate_id").
Нарушение контракта конструктора, например отрицательный Money, приводит к исключению.
Result не должен заставлять вызывающего молча игнорировать ошибку:
сначала проверьте IsSuccess, затем обращайтесь к Value.

Событие Added поднимается после сохранения. На дубле уведомления нет.
Если обработчик бросит исключение, добавление уже произошло и отката нет.
Не используйте такой event как надёжную очередь бизнес-событий.
Проект однопоточный; проверка уникальности нескольких одновременно работающих клиентов — задача более позднего блока.

## Построение отчёта

1. Проверьте year/month даже при пустом хранилище.
2. Получите один снимок расходов.
3. Выберите записи нужного месяца и года.
4. Сгруппируйте нормализованные категории, посчитайте число и сумму.
5. Отсортируйте Ordinal и материализуйте готовые строки.
6. Верните отдельное read-only представление результата.

Сумма строится через Aggregate(Money.Zero, ...), поэтому не нужен неявный переход Money в decimal.
Группы LINQ в памяти можно перебрать несколько раз: они уже накоплены GroupBy.
Повторное перечисление исходного внешнего источника — другое действие с иной стоимостью.

## Демонстрация и проверки

```powershell
dotnet run --project examples/TypesAndQueries -- 18
dotnet run --project examples/CoreChecks
python tools/verify.py
```

Ожидаемая демонстрация:

```text
duplicate_id
food=20.00 (2)
travel=30.00 (1)
notifications=4
```

Три расхода относятся к январю, четвёртый — к февралю. В отчёте за январь только три.
Повторное добавление первого расхода не меняет данные и не увеличивает notifications.

Тесты проверяют не внутренний Dictionary, а обещания интерфейса.
Один набор контрактных проверок применяется к двум реализациям: Dictionary-хранилищу и
независимому тестовому варианту на List. Это выявляет случайную зависимость сервиса от деталей хранения.

## Практика

**18-A.** Создайте собственные Core, Memory и консольный клиент.
Критерий: зависимости направлены к Core, а расчёт не обращается к Console или File.

**18-B.** Выполните L02 целиком. Критерии: дубликат не перезаписывает данные,
снимок и готовый отчёт не меняются после следующего Add, неверный месяц отклоняется даже на пустом входе.

**18-C.** Добавьте минимальный фильтр по категории в новый метод отчёта.
Зафиксируйте, нормализуется ли вход фильтра. Критерии: food/FOOD дают один результат,
некорректный фильтр отклоняется, исходный метод сохраняет поведение.
Готовый образец реализует основной договор A/B; расширение выполните самостоятельно.
