# 41. ADO.NET и Dapper

**Результат:** вы управляете соединением, параметрами и транзакцией; понимаете, что Dapper
автоматизирует, а что остаётся вашим SQL. Нужны главы 20, 27, 31 и 40.
Полный пример — [SqlLedger](../../examples/Data/Persistence/SqlLedger.cs).

## Соединение, команда, reader

ADO.NET задаёт общий набор типов: DbConnection, DbCommand, DbDataReader, DbTransaction.
Провайдер реализует их для конкретной БД. Здесь Microsoft.Data.Sqlite 10.0.13;
для PostgreSQL используется Npgsql, для SQL Server — Microsoft.Data.SqlClient.
Одинаковый базовый класс не устраняет отличия SQL, типов параметров и исключений.

```csharp
// Фрагмент с using Microsoft.Data.Sqlite; path указывает на готовую БД.
using var connection = new SqliteConnection(
    new SqliteConnectionStringBuilder {
        DataSource = path, Mode = SqliteOpenMode.ReadWrite,
        ForeignKeys = true, Pooling = false
    }.ToString());
connection.Open();
using var command = connection.CreateCommand();
command.CommandText = """
    SELECT COALESCE(SUM(AmountMinor), 0)
    FROM Expenses WHERE CategoryName = $category
    """;
command.Parameters.AddWithValue("$category", "food");
long total = (long)command.ExecuteScalar()!;
```

ExecuteScalar возвращает первое значение; ExecuteNonQuery — число изменённых строк
для соответствующей команды; ExecuteReader открывает последовательное чтение результата.
Reader.Read переводит курсор к следующей строке. GetInt64/GetString читают ожидаемый тип столбца;
для nullable столбца сначала нужен IsDBNull, поскольку SQL NULL представлен через DBNull.
При ошибке или досрочном выходе reader, command и connection всё равно должны освобождаться.

Строку подключения собирайте штатным builder: имя файла с `;` не должно стать новой настройкой.
В курсе Pooling=false упрощает изоляцию временных файлов и освобождение handles в тестах.
Серверный pooling обычно позволяет Dispose вернуть соединение в пул; открывать одно соединение
на весь процесс для всех запросов не требуется. Пул соединений и пул DbContext — разные механизмы.
Не держите соединение, пока пользователь думает или выполняется независимый HTTP-запрос.

## Параметры передают значения

Если вставить введённую категорию в SQL через конкатенацию, кавычка может изменить структуру запроса.
Параметр связывает значение отдельно от SQL: строка `food' OR 1=1; --` остаётся строкой.
В тесте с этой строкой возвращается ноль, таблица и обычный отчёт сохраняются.
[Параметры SQLite](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/parameters).

Параметры не заменяют имена таблиц, столбцов и направление сортировки.
Для выбора сортировки сопоставьте пользовательское значение с закрытым набором констант SQL.
Тип и размер параметра влияют на преобразования и планы; AddWithValue в коротком SQLite-примере
не означает, что вывод типов всегда оптимален для SQL Server.

Для SQL NULL присвойте параметру DBNull.Value. Не передавайте форматированную локальную строку
вместо числа или даты, если провайдер поддерживает нужный тип.
SqlLedger явно преобразует Money в long сотых и DateOnly в DayNumber; Guid сохраняет в формате D.
В серверном варианте лучше выбрать native uuid/date/numeric и проверить mapping на целевой БД.

## Dapper оставляет SQL видимым

Dapper 2.1.89 добавляет extension-методы к соединению. Execute выполняет изменение,
Query сопоставляет строки с объектами, QuerySingle требует ровно одну строку,
QuerySingleOrDefault допускает отсутствие, но не несколько строк.
Свойства результата должны соответствовать именам/alias столбцов и совместимым типам.

```csharp
// Фрагмент с using Dapper, уже открытым connection и transaction.
var existing = connection.QuerySingleOrDefault<StoredExpense>(
    "SELECT * FROM Expenses WHERE ExternalId = @Id",
    new { Id = expense.Id.ToString("D") }, transaction);
```

Анонимный объект задаёт параметры. Dapper не отслеживает изменённые свойства и не вызывает
SaveChanges: для UPDATE нужен ваш SQL. Он также не выбирает границы транзакции,
не создаёт миграции и не превращает несколько отдельных команд в атомарную операцию.
[Репозиторий и примеры Dapper](https://github.com/DapperLib/Dapper).

## Все команды одной транзакции

В L05 импорт выполняет: прочитать квитанцию → проверить/добавить расходы → записать квитанцию → commit.
Каждая Dapper-команда получает тот же transaction, который принадлежит тому же connection.
Вызов отдельного helper, который открывает новое соединение, уже не участвует в этой транзакции.

```csharp
// Схема операции; конкретные SQL-команды показаны в SqlLedger.Import.
using var transaction = connection.BeginTransaction(deferred: false);
connection.Execute(sql, parameters, transaction);
token.ThrowIfCancellationRequested();
transaction.Commit();
```

Без commit Dispose откатывает незавершённую транзакцию. Ошибка после первой вставки не должна
оставлять ни расход, ни созданную категорию, ни успешную квитанцию. Проверка выполняется с отдельного
соединения после выхода из метода. `deferred: false` — особенность SQLite, не переносимый рецепт ADO.NET.
У серверного провайдера нужно отдельно выбрать уровень изоляции и способ разрешения гонки UNIQUE.

ON CONFLICT(Name) DO NOTHING используется только для ожидаемого совпадения категории.
Общее «игнорировать любую ошибку вставки» скрыло бы нарушение CHECK и потерю записи.
Исключения SQLite имеют общий и расширенный коды: в тестах проверяются UNIQUE 2067,
FOREIGN KEY 787 и CHECK 275. Текст исключения не должен быть единственным классификатором.

## Async, отмена и граница провайдера

У сетевых провайдеров OpenAsync, ExecuteReaderAsync и ReadAsync позволяют не держать поток
во время ожидания I/O. Передайте один CancellationToken через весь путь и await каждую операцию.
У Dapper async-команд token можно передать в CommandDefinition:

```csharp
// Образец для открытого серверного соединения с async-провайдером.
var command = new CommandDefinition(
    "SELECT Id FROM Expenses WHERE CategoryName = @category",
    new { category }, transaction: transaction,
    commandTimeout: 10, cancellationToken: token);
var ids = await connection.QueryAsync<Guid>(command);
```

Этот фрагмент показывает API, а не готовый запрос к SQLite-схеме курса: там столбец называется ExternalId
и хранится текстом. Провайдер и тип результата должны соответствовать реальной таблице.
CommandTimeout и token решают разные задачи; отмена запроса не доказывает отмену уже выполненного COMMIT.

Microsoft.Data.Sqlite выполняет async-методы синхронно, поскольку движок не предоставляет async I/O.
Поэтому низкоуровневый импорт и backup здесь синхронные. Token проверяется до операции, между строками
и перед commit; прерывание уже выполняющегося native-вызова не обещается.
EF-примеры сохраняют async API для дальнейшего серверного приложения, но не заявляют неблокирующее
SQLite-выполнение. [Ограничения async](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/async).

## Буферизация и время жизни результата

Обычный Dapper Query буферизует строки: после получения списка соединение можно закрыть.
Это удобно для ограниченной страницы до 100 записей. Для большого экспорта нужен потоковый подход:
reader и соединение остаются открытыми до завершения перечисления.

SqlLedger.StreamByDate — iterator с using внутри. Ресурсы создаются при перечислении,
а foreach с break освобождает enumerator и выполняет finally, созданные using.
Нельзя открыть reader в using, вернуть зависимую от него последовательность и закрыть ресурсы
до её первого использования. Нельзя также хранить такой потоковый результат как обычный готовый список.
Медленный consumer удерживает соединение дольше; ограничивайте длительность экспорта и учитывайте нагрузку.

## Практика

**41-A.** Реализуйте ADO.NET-итог по категории. Проверьте food, отсутствующую категорию,
строку с кавычкой и SQL-фрагментом. Критерий: число передаётся точным типом, результат пустого набора — 0,
ввод не меняет SQL и не повреждает таблицу.

**41-B.** Выполните две вставки одной транзакцией и вызовите ошибку после первой.
Критерий: новое соединение не видит ни одной вставки; успешный вариант сохраняет обе;
все команды используют одно соединение и один transaction.

**41-C.** Напишите ограниченный потоковый экспорт и сравните его с буферизацией.
Критерий: досрочное завершение освобождает reader/connection, отмена имеет описанную границу,
память не растёт со всем набором строк; для серверного варианта отдельно проверены provider types и async.
