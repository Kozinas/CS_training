# 43. Практикум надёжного хранения

**Результат:** вы объединяете ключи, транзакции, версии, миграции и восстановление в проверяемый
договор хранения. Нужны главы 36–42. Полные условия — [L05](../../labs/05-durable-storage/README.md),
команды — [Data README](../../examples/Data/README.md).

## Сначала сформулируйте, что нельзя потерять

Требования не сводятся к «данные сохраняются в SQLite»:

1. Повтор Id расхода не создаёт вторую запись и не заменяет первую другим содержимым.
2. Импорт фиксирует пакет целиком вместе с его результатом либо не фиксирует ничего.
3. Повтор того же запроса после потери ответа возвращает сохранённый результат.
4. Устаревшее изменение суммы не затирает уже подтверждённое изменение другого клиента.
5. Обновление схемы сохраняет старые записи, а backup действительно можно прочитать после восстановления.

Это отдельные гарантии с отдельными тестами. UNIQUE решает первую задачу на уровне ключа,
но сам по себе не сохраняет результат запроса и не обнаруживает потерю обновления.
Version защищает UPDATE, но не заменяет транзакцию нескольких INSERT.

## Два разных идентификатора

ExternalId идентифицирует расход. BatchId идентифицирует запрос импорта.
Новый BatchId с уже известными одинаковыми расходами даёт duplicates.
Прежний BatchId с тем же содержимым возвращает исходные added/duplicates и Replayed=true,
даже если позже сумма расхода была изменена отдельной командой.

```text
Первый запрос:        added=3, duplicates=1, replayed=false
Тот же BatchId:       added=3, duplicates=1, replayed=true
Новый BatchId:        added=0, duplicates=4, replayed=false
```

Повторная квитанция сообщает итог прежнего запроса; она не описывает новые записи текущего запуска.
Если тот же BatchId пришёл с другим содержимым, результат — batch_id_conflict.
Это предотвращает случайное применение старого ключа к другой команде.

Fingerprint строится из нормализованных Id, Day, Category и суммы с двумя знаками,
в порядке входных записей, с префиксом версии формата. UTF-8 представление хешируется SHA-256.
Разделитель безопасен здесь благодаря ограничениям полей; произвольный текст потребовал бы
однозначной сериализации или явных длин. Перестановка записей считается другим содержимым запроса.
Если поменять канонизацию в будущем, потребуется совместимость старых квитанций, а не просто смена hash-функции.

## Одна точка фиксации

Все строки сначала проверяются моделью L02. В отличие от частичного импорта L03,
ошибка любой строки L05 отменяет весь пакет. После проверки внешних данных начинается короткая
immediate-транзакция SQLite: поиск квитанции, проверка расходов, вставки и новая квитанция.
Все команды используют одно соединение. Commit предшествует stdout-отчёту.

| Ситуация | Ожидаемое состояние |
| --- | --- |
| Структурная ошибка или неверная запись | Импорт не начинается |
| Конфликт Id после нескольких INSERT | Весь новый пакет откатывается |
| Исключение между вставкой и квитанцией | Нет частичной записи и квитанции |
| Отмена замечена до commit | Незавершённая транзакция откатывается |
| Ответ потерян после commit | Повтор BatchId возвращает квитанцию |

В тесте AfterInsert внедряет ошибку или отмену на определённом шаге. Этот internal hook доступен
тестовой сборке и не является флагом пользовательского CLI. Успех после commit нельзя отменить
задним числом: token представляет запрос на отмену, а не механизм возврата истории.

При занятости базы провайдер ограниченно ожидает блокировку; DefaultTimeout=5 секунд.
Не превращайте любую ошибку в бесконечный retry. Повтор транзакции должен заново читать актуальные данные,
быть ограничен по числу/времени и сохранять BatchId. SQLite-реализация этого выпуска не добавляет
собственный автоматический retry поверх провайдера.

## Что доказывают конкурентные тесты

Два потока доходят до барьера перед импортом. Каждый открывает своё соединение.
При одинаковом BatchId создаётся одна квитанция; второй участник получает replay.
При разных BatchId и одном расходе создаётся один расход и две квитанции с различными итогами.
Проверка отдельными CLI-процессами дополнительно исключает зависимость от общего static-lock C#.

Для обновления суммы два контекста сначала читают Version=0. После барьера оба пытаются записать
новое значение и Version=1. Проходит ровно один, второй получает DbUpdateConcurrencyException.
Так проверяется конкретное перекрытие операций; простой последовательный запуск двух успешных UPDATE
не проверил бы потерю обновлений.

Серверная СУБД потребует того же договора, но другой реализации блокировок и обработки ошибок.
Не переносите BeginTransaction(deferred:false) в PostgreSQL буквально.
Полезное расширение — реализовать порт хранения на Npgsql и запустить эти сценарии через Testcontainers.
Пример инфраструктуры есть в главе 36. В этом выпуске L05 выполнена на реальной SQLite,
но серверный перенос и контейнерное выполнение L05 **не заявляются**.

## Страницы по ключу

OFFSET описывает позицию в изменяемом наборе: удаление ранней строки может сдвинуть следующие страницы.
Keyset хранит значения последней строки и выбирает следующие по полностью определённому порядку.
В L05 порядок — Day, затем уникальный Sequence; даты расхода после вставки не меняются.

```sql
WHERE Day > @Day OR (Day = @Day AND Sequence > @Sequence)
ORDER BY Day, Sequence LIMIT @size
```

Реальный запрос использует равносильную форму с явным Day >= @Day для диапазона индекса.
Сортировка только по дате теряла бы расходы с той же датой на границе страницы.
Тест добавляет запись с более ранней датой между страницами и проверяет отсутствие сдвига
у оставшихся исходных записей. [Pagination](https://learn.microsoft.com/en-us/ef/core/querying/pagination).

Keyset не обещает единый снимок всех страниц: новые более поздние записи могут появиться,
удалённые исчезнуть, суммы измениться. Если нужен экспорт строго на один момент,
выберите подходящую транзакцию/снимок или заранее зафиксированный набор ключей.
Cursor будущего сетевого API также должен учитывать фильтр, порядок и проверку входных значений.

## Миграции в поставке

CI восстанавливает зависимости по lock, проверяет отсутствие pending model changes,
генерирует SQL и сравнивает его с сохранённым скриптом.
Тесты создают пустую базу, обновляют прежнюю схему с расходом и повторно вызывают Migrate.
Вторая миграция добавляет nullable Note без изменения старых значений.

Для production изменения обычно разделяют: сначала совместимое расширение схемы,
затем новая версия приложения/перенос данных, и только после перехода всех клиентов — удаление старого.
Обратная миграция, удаляющая столбец, не восстанавливает его содержимое.
Прочтите SQL и оцените блокировки на реальном объёме; успешная миграция трёх учебных строк
не измеряет длительность изменения большой таблицы.
Проверки GitHub Actions здесь работают на GitHub-hosted Windows runner; автоматического применения
к внешней базе и CD-развёртывания не настроено.

## Backup считается проверенным после restore

SqliteConnection.BackupDatabase создаёт согласованную копию открытой БД.
Обычное копирование основного файла работающей WAL-базы может пропустить данные из журнала.
Команда backup требует нового имени назначения и отказывается перезаписывать существующий файл.
Если сам backup оборвётся после создания назначения, неполный файл нельзя считать готовой копией.
[Online backup](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/backup).

Тест создаёт backup, затем меняет исходную базу. Копия восстанавливается под другим именем:
сверяются отчёт, версия, история миграций, квитанция импорта и PRAGMA integrity_check/foreign_key_check.
Так обнаруживается ситуация «файл создан, но нужное состояние не восстановлено».
Проверка структуры не доказывает правильность бизнес-данных, поэтому нужен и предметный отчёт.

Backup в той же папке не защищает от потери устройства. План эксплуатации дополнительно задаёт
место хранения, периодичность, допустимую потерю данных и время восстановления.
Проверка курса не моделирует физическое отключение питания, повреждение диска и восстановление сервера.

## Диагностика без потери смысла

В журнале полезны BatchId, этап, длительность, количество строк и код конфликта.
SQL-текст и число обращений помогают увидеть N+1; значения параметров могут содержать приватные данные.
Успешная запись лога не заменяет квитанцию в транзакции.
После ошибки отличайте «не удалось открыть БД», «конфликт версии» и «неверный документ»:
они требуют разных действий пользователя.

## Практика

**43-A.** Выполните первый импорт, replay, новый BatchId и конфликтный пакет.
Критерий: точные исходы из L05, три расхода после отказа, нет частичной категории books.

**43-B.** Реализуйте L05 самостоятельно. Добавьте барьеры для двух писателей и сбой между вставками.
Критерий: один расход при конкурирующих импортах, один победитель при stale-update,
откат пакета и сохранение receipt после повторного открытия процесса.

**43-C.** Перенесите договор на PostgreSQL или SQL Server и запустите его в изолированной БД.
Проверьте миграцию, серверный конфликт, план запроса и backup/restore выбранными инструментами.
Критерий: provider-specific коды и типы проверены на настоящем сервере, ограничения среды явно записаны,
успешные SQLite-тесты не подменяют эти результаты.
