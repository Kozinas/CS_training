## Таблица хранит факты с ограничениями

В файловой L03 программа сама проверяла всю историю Id перед заменой checkpoint.
В БД ключи и ограничения действуют для всех клиентов, которые обращаются к одной базе.
Проверка в C# всё равно нужна для понятной ошибки; база служит последней границей целостности.

Таблица — набор строк с именованными столбцами. Порядка строк без ORDER BY нет.
Первичный ключ идентифицирует строку, UNIQUE запрещает повтор значения, внешний ключ связывает
строку с существующей строкой другой таблицы. NOT NULL требует значение, CHECK проверяет выражение.
Правила допуска NULL в UNIQUE и CHECK надо изучать у выбранной СУБД; одно слово «ключ» не описывает их полностью.

Схема курса содержит:

| Таблица | Ключ | Смысл |
| --- | --- | --- |
| Categories | Name | Нормализованная категория |
| Expenses | Sequence | Строка расхода; ExternalId дополнительно уникален |
| ImportReceipts | BatchId | Итог уже зафиксированного запроса импорта |

Sequence — внутренний возрастающий INTEGER PRIMARY KEY AUTOINCREMENT SQLite.
Он используется как однозначный порядок, а не как номер без пропусков.
ExternalId — внешний Guid в строковом формате D: приложение проверяет Guid и приводит его
к одному написанию. Ограничение БД проверяет длину и уникальность строки; оно не является полным UUID-парсером.
У PostgreSQL есть uuid, у SQL Server — uniqueidentifier: перенос требует явного отображения типов.

AmountMinor хранит целое число сотых одной расчётной единицы: 12.50 превращается в 1250.
Это точное представление для согласованной точности L02. Оно не моделирует несколько валют,
курсы или произвольное число дробных знаков. Day — DateOnly.DayNumber, а не локальное время события.
Полный DDL находится в [migrations.sql](../../examples/Data/sql/migrations.sql).

```sql
-- Сокращённый фрагмент: полный CREATE TABLE также содержит ключи.
AmountMinor INTEGER NOT NULL
    CHECK (typeof(AmountMinor) = 'integer'
           AND AmountMinor BETWEEN 1 AND 99999999)
```

У SQLite гибкая типизация: объявление INTEGER само по себе не заменяет все проверки.
Здесь дополнительно проверяется фактический тип значения. Foreign Keys=True в строке подключения
включает проверку внешних ключей для каждого соединения курса.
Удаление категории с расходами запрещено через RESTRICT; каскадное удаление было бы другим договором.

## SELECT, WHERE и NULL

```sql
SELECT ExternalId, AmountMinor
FROM Expenses
WHERE AmountMinor >= 2000
ORDER BY Day, Sequence;
```

FROM определяет источник, WHERE отбирает строки, SELECT задаёт возвращаемые столбцы,
ORDER BY задаёт порядок. SELECT * удобно для исследования схемы, но публичный отчёт лучше
ограничить нужными столбцами: изменение таблицы не должно незаметно менять контракт вывода.

Note — необязательная заметка второй миграции. NULL означает отсутствие значения, не пустую строку
и не ноль. В SQL есть TRUE, FALSE и UNKNOWN. Сравнение Note = NULL даёт UNKNOWN,
а WHERE сохраняет только TRUE. Поэтому для отсутствующих заметок нужен IS NULL.
NOT UNKNOWN тоже UNKNOWN; это особенно важно для NOT IN, если подзапрос может вернуть NULL.
В такой задаче часто понятнее NOT EXISTS с явной связью строк.

```sql
SELECT ExternalId FROM Expenses WHERE Note IS NULL;
SELECT ExternalId FROM Expenses WHERE Note IS NOT NULL;
```

COALESCE выбирает первое ненулевое значение. COUNT(*) считает строки,
COUNT(Note) — только ненулевые Note. SUM по пустому набору может вернуть NULL:
если договор отчёта требует ноль, напишите COALESCE(SUM(AmountMinor), 0).

## JOIN и GROUP BY

INNER JOIN оставляет совпавшие пары строк. LEFT JOIN сохраняет каждую строку слева,
даже если справа нет совпадения: правые столбцы тогда NULL.
Если поставить условие правой таблицы в WHERE, строки без пары могут исчезнуть;
условие принадлежности пары часто должно находиться в ON.

```sql
SELECT c.Name, COUNT(e.Sequence) AS Count,
       COALESCE(SUM(e.AmountMinor), 0) AS AmountMinor
FROM Categories AS c
LEFT JOIN Expenses AS e ON e.CategoryName = c.Name
GROUP BY c.Name
ORDER BY c.Name;
```

Для категории без расходов COUNT(e.Sequence) равен 0, а COUNT(*) был бы 1 из-за строки LEFT JOIN.
GROUP BY объединяет строки по ключу; агрегаты вычисляют значение для группы.
WHERE работает до группировки, HAVING отбирает группы после неё.
Не выбирайте неагрегированный столбец, который не определяется ключом группировки:
послабление одной СУБД не делает результат осмысленным или переносимым.
[SELECT в SQLite](https://www.sqlite.org/lang_select.html).

```sql
SELECT CategoryName, SUM(AmountMinor) AS TotalMinor
FROM Expenses
GROUP BY CategoryName
HAVING SUM(AmountMinor) >= 2000
ORDER BY CategoryName;
```

При соединении двух связей «один ко многим» строки могут перемножиться и завысить SUM.
Сначала определите, что представляет одна строка результата; при необходимости агрегируйте
каждую дочернюю таблицу отдельно и только затем соединяйте итоги.

## Нормализация и индексы

Нормализация устраняет повторное хранение независимых фактов. Название/описание категории
должно зависеть от категории, а не повторяться в каждой записи расхода.
Первая нормальная форма требует подходящих атомарных значений, вторая устраняет зависимости
от части составного ключа, третья — транзитивные зависимости неключевых атрибутов.
«Атомарный» определяется задачей: список Id через запятую мешает ссылочной целостности и запросам.
Денормализованный итог может ускорить чтение, но требует договора обновления и восстановления.

Индекс — дополнительная структура поиска. В схеме есть уникальный индекс ExternalId,
индекс внешнего ключа CategoryName и составной индекс (Day, Sequence) для страниц по дате.
Каждая вставка должна поддерживать их, поэтому индекс на каждый столбец не является универсальной оптимизацией.
Для составного индекса важен порядок столбцов и фактические условия запроса.

```sql
EXPLAIN QUERY PLAN
SELECT Sequence, ExternalId FROM Expenses
WHERE Day >= $day AND (Day > $day OR Sequence > $sequence)
ORDER BY Day, Sequence LIMIT 20;
```

Параметры передаёт приложение. В проверенном запуске план содержит SEARCH с
IX_Expenses_Day_Sequence. Команда CLI `plan` показывает фактический план, а проверочный скрипт
сохраняет его в .artifacts/data/query-plan.txt. Формат вывода плана может меняться;
наличие индекса не доказывает приемлемую задержку на большой базе.
[EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html).

## Транзакция и изоляция

Транзакция объединяет изменения: COMMIT фиксирует их, ROLLBACK отменяет незавершённые.
Atomicity — неделимость группы, consistency — сохранение заданных инвариантов,
isolation — правила наблюдения конкурентной работы, durability — сохранение подтверждённого результата
при условиях работы выбранной СУБД и хранилища. Слово ACID не задаёт автоматически бизнес-инварианты.

Dirty read читает чужую незавершённую запись; non-repeatable read получает новое значение
при повторном чтении; phantom — иной набор строк при повторном условии.
При Serializable успешный итог должен соответствовать некоторому последовательному порядку транзакций.
Это не обещает отсутствие конфликтов: иногда нужно повторить целую транзакцию.
[Изоляция PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html).

В обычной конфигурации SQLite одновременно пишет один участник. WAL позволяет читателям
работать параллельно с писателем, но не превращает SQLite в систему многих одновременных писателей.
Импорт L05 начинает immediate-транзакцию до чтения истории, поэтому два импортёра не принимают
решение на основании одного устаревшего состояния. Короткая транзакция важнее дополнительного Task.Run.
[Изоляция SQLite](https://www.sqlite.org/isolation.html).

| Платформа | Что учитывать при переносе |
| --- | --- |
| SQLite | Файл, один писатель, ограничения типов и ALTER TABLE |
| PostgreSQL | Сервер, uuid/numeric, MVCC, провайдер Npgsql |
| SQL Server | Сервер, uniqueidentifier/decimal, rowversion, Microsoft.Data.SqlClient |

Синтаксис LIMIT/TOP, генерация ключей, collation, уровни изоляции и коды ошибок различаются.
Набор тестов SQLite не подтверждает поведение PostgreSQL или SQL Server.
