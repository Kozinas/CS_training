# 42. Entity Framework Core

**Результат:** вы отображаете модель на таблицы, контролируете SQL, обновляете схему и обнаруживаете
конфликт изменений. Нужны главы 16, 37 и 40–41. Используется EF Core **10.0.13**;
полный пример — [LedgerDbContext](../../examples/Data/Persistence/LedgerDbContext.cs).

## Контекст — одна работа с данными

DbContext объединяет модель, запросы и отслеживание изменений. DbSet представляет набор сущностей,
а не уже загруженную таблицу. LINQ-запрос строится до materialization через ToList/Single/перечисление.
SaveChanges обнаруживает изменения отслеживаемых сущностей и отправляет команды провайдеру.

Создавайте короткоживущий контекст на логическую работу и освобождайте после неё.
Не храните его в static и не выполняйте Task.WhenAll с несколькими запросами одного контекста.
Даже если каждый метод async, DbContext не становится потокобезопасным.
В будущем ASP.NET Core обычная граница — request scope; worker создаёт scope или использует фабрику.
[Время жизни DbContext](https://learn.microsoft.com/en-us/ef/core/dbcontext-configuration/).

В тесте конкуренции два участника имеют разные контексты, но читают одну строку одной физической БД.
Барьер гарантирует, что оба прочитали старую версию до обновления. Это проверка конкурентного договора,
а не попытка одновременно использовать один экземпляр DbContext.

## Entity, DTO и доменная модель

ExpenseRow имеет изменяемые свойства для хранения. Expense из L02 — проверенный неизменяемый
доменный объект; ExpenseSummary и CategoryTotal — результаты чтения для клиента.
Разделение позволяет добавить колонку Version или внутренний ключ Sequence без изменения ввода L03.
Не возвращайте EF-сущность прямо как сетевой DTO: navigation может раскрыть лишние данные,
создать цикл сериализации или спровоцировать загрузку дополнительных объектов.

```csharp
// Фрагмент OnModelCreating: внешний Id уникален, категория обязательна.
model.Entity<ExpenseRow>(b =>
{
    b.HasKey(e => e.Sequence);
    b.HasIndex(e => e.ExternalId).IsUnique();
    b.HasIndex(e => new { e.Day, e.Sequence });
    b.Property(e => e.Version).IsConcurrencyToken();
    b.HasOne(e => e.Category).WithMany(e => e.Expenses)
        .HasForeignKey(e => e.CategoryName)
        .OnDelete(DeleteBehavior.Restrict);
});
```

Fluent mapping задаёт то, что нельзя оставлять неявным соглашением. Navigation Category связывает
объекты, CategoryName хранит значение внешнего ключа. Объявление navigation ещё не означает,
что связанный объект загружен. Optional Note допускает null; остальные строковые поля модели required.
Полная модель также задаёт таблицы, CHECK и точное поведение ключей.

SQLite не имеет всех тех же типов и возможностей, что серверные СУБД.
В примере long сотых позволяет SUM и сравнения без перехода к двоичной floating-point сумме.
Для приложения с decimal на сервере задавайте precision/scale и тестируйте перевод запросов выбранным
провайдером. Value converter меняет представление значения, но сам по себе не делает любой метод
вашего value object переводимым в SQL. [Ограничения SQLite](https://learn.microsoft.com/en-us/ef/core/providers/sqlite/limitations).

## Tracking и снимки чтения

При обычном запросе entity попадает в ChangeTracker. Повторная загрузка того же ключа обычно
возвращает уже отслеживаемый экземпляр: это identity resolution, а не гарантия свежего состояния БД.
Если другой контекст изменил сумму, прежний объект не обновится автоматически.
При необходимости явно перечитайте значения или создайте новый контекст.

AsNoTracking подходит для чтения без дальнейшего сохранения через этот экземпляр.
AsNoTrackingWithIdentityResolution устраняет дубликаты экземпляров в результате, не прикрепляя их
к основному ChangeTracker. Проекция только скаляров/DTO ещё лучше выражает ограниченный договор чтения.
Если внутри DTO возвращается сама entity, она всё ещё может отслеживаться.

```csharp
// Фрагмент с using Microsoft.EntityFrameworkCore.
var page = await db.Expenses.AsNoTracking()
    .OrderBy(e => e.Day).ThenBy(e => e.Sequence)
    .Select(e => new ExpenseSummary(
        e.Sequence, e.Category.Name, e.AmountMinor))
    .Take(20).ToListAsync(token);
```

На границе приложения возвращается готовый ограниченный результат. Возврат IQueryable наружу
передаёт вызывающему коду право достроить запрос и связывает его со временем жизни контекста.
После Dispose такой запрос не становится автономной коллекцией.

## Загрузка связей и N+1

Eager loading через Include загружает нужные связи вместе с основным запросом или набором split queries.
Explicit loading через Entry(...).Reference/Collection.Load выполняет отдельную загрузку.
Lazy loading, если его специально включить, может выполнить SQL при чтении свойства.
В курсе lazy-loading proxies не установлены.

Набор из трёх расходов с тремя разными категориями в тесте создаёт четыре запроса:
один SELECT расходов и три explicit Load внутри цикла. Это N+1.
Проекция ExpenseSummary получает нужные поля одним SQL-запросом; interceptor проверяет число команд.
Простой перенос цикла в async не устраняет N+1.
[Эффективные запросы](https://learn.microsoft.com/en-us/ef/core/performance/efficient-querying).

Include нескольких коллекций может размножать строки JOIN. Split query уменьшает такое размножение,
но выполняет несколько обращений; требование согласованного снимка нужно рассмотреть отдельно.
Выбирайте стратегию по составу результата и измерениям, а не правилу «всегда Include».

## Перевод LINQ в SQL

IQueryable содержит expression tree, который переводит провайдер. Произвольный C#-метод,
доступ к файлу или непонятная провайдеру операция в WHERE не становятся SQL автоматически.
ToQueryString помогает исследовать запрос; фактически выполняемые команды лучше смотреть в логах
или DbCommandInterceptor. Не включайте значения чувствительных параметров в общие журналы.

При разработке отчёта курса сортировка по свойству DTO после вызова его record-конструктора
не перевелась в SQL. Исправление — сортировать группу по ключу до создания DTO:

```csharp
var totals = await db.Expenses.AsNoTracking()
    .GroupBy(e => e.CategoryName).OrderBy(g => g.Key)
    .Select(g => new CategoryTotal(
        g.Key, g.Count(), g.Sum(e => e.AmountMinor)))
    .ToListAsync(token);
```

Добавление ToList перед GroupBy скрывает ошибку перевода, но переносит все строки в память.
Такой переход допустим только как осознанное решение с ограниченным набором данных.
Тест на настоящем SQLite-провайдере выявляет проблемы перевода; коллекция List или EF InMemory этого не делает.

## Оптимистическая конкуренция

Клиент читает Version=0, готовит изменение и передаёт expectedVersion=0.
Если другой клиент уже обновил строку, операция должна завершиться конфликтом.
Сравнение версии только в C# недостаточно: между проверкой и UPDATE есть окно гонки.

IsConcurrencyToken добавляет исходную версию в условие UPDATE. Приложение увеличивает Version
при изменении суммы; ноль затронутых строк вызывает DbUpdateConcurrencyException.
В EfLedger предварительная проверка быстро обнаруживает уже устаревший запрос,
а токен в SQL защищает от изменения после чтения. [Concurrency](https://learn.microsoft.com/en-us/ef/core/saving/concurrency).

```sql
-- Смысл команды EF; фактический SQL может включать RETURNING.
UPDATE Expenses
SET AmountMinor = @newAmount, Version = @nextVersion
WHERE Sequence = @sequence AND Version = @originalVersion;
```

Конфликт не следует автоматически превращать в «перезаписать последним пришедшим значением».
Верните его клиенту или заново прочитайте данные и пересчитайте операцию по договору.
Ошибка уникального ключа при INSERT имеет другой тип и не является concurrency exception EF.
В SQL Server rowversion может обновляться самой БД; это бинарная версия, не дата/время.
[rowversion](https://learn.microsoft.com/en-us/sql/t-sql/data-types/rowversion-transact-sql).

## Миграции и проверка обновления

Миграции курса созданы инструментом dotnet-ef 10.0.13. ModelSnapshot нужен для сравнения моделей,
а __EFMigrationsHistory хранит применённые переходы в конкретной базе.
Команды выполняются из examples/Data; tool manifest закрепляет локальный инструмент.

```powershell
dotnet tool restore
$efArgs = @("--project", "Persistence", "--startup-project", "DataCli",
    "--configuration", "Release", "--no-build")
dotnet ef migrations has-pending-model-changes @efArgs
dotnet ef migrations script 0 @efArgs
```

Для новой модели в своей копии сначала соберите проект и выполните migrations add с новым именем,
изучите сгенерированный diff, затем проверьте пустую базу и обновление предыдущей версии с данными.
В курсе оба перехода уже созданы: повторять add InitialCreate не требуется.
Команда CLI init применяет готовые миграции к явно указанному файлу.

EnsureCreated не ведёт ту же историю, что Migrate; не смешивайте эти способы для обновляемой базы.
SQLite не поддерживает обычные idempotent migration scripts EF. Генерируемый script 0 подходит
для пустой базы; для существующей нужен известный исходный переход или Migrate.
Runtime migrations удобны в локальном CLI, но production-поставка требует отдельного шага,
проверенных прав и согласования с работающими версиями приложения.
[Применение миграций](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/applying).

## Транзакции и массовые изменения

Один SaveChanges при поддержке провайдером выполняется транзакционно.
Несколько SaveChanges или смесь EF/Dapper требуют общей явно организованной транзакции,
если должны фиксироваться вместе. Общая строка подключения не означает общую транзакцию.

ExecuteUpdate/ExecuteDelete выполняют команду сразу, минуя ChangeTracker; SaveChanges после них
не требуется. Отслеживаемые объекты сохраняют прежние значения. Токен конкуренции для bulk-команды
нужно включить в WHERE самостоятельно, проверить affected rows и изменить версию.
Тест обновляет Note и Version, проверяет отказ устаревшей bulk-команды и последующий конфликт
старого tracked-объекта. [Массовые операции](https://learn.microsoft.com/en-us/ef/core/saving/execute-insert-update-delete).

## Практика

**42-A.** Отобразите категорию и расход с ключом, внешним ключом и уникальным ExternalId.
Критерий: миграция создаёт ограничения, экземпляр повторного tracking-запроса совпадает,
AsNoTracking-результат не прикреплён к контексту.

**42-B.** Воспроизведите 1+3 explicit-запроса и замените их проекцией.
Критерий: interceptor подтверждает один SELECT, поля и порядок результата сохранены,
нет предварительной загрузки всей таблицы в память.

**42-C.** Добавьте новую nullable-колонку и проверьте обновление старой базы с данными.
Затем организуйте двух писателей, прочитавших одну версию.
Критерий: данные пережили миграцию; сохраняется одно изменение, второй получает явный конфликт,
сумма и версия победителя не затираются.
