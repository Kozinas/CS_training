# 51. Blazor: компоненты и состояние веб-клиента

**Результат:** вы строите интерактивный компонент, объясняете место исполнения его C# и проверяете
загрузку, ошибки и отмену через bUnit. Нужны главы 31, 44–46 и 50.
Исполняемый пример — [BlazorClient](../../examples/Specializations/BlazorClient/Components/ReportPanel.razor).

## Компонент как договор

Razor-компонент соединяет разметку и C#-состояние. Render создаёт описание UI; framework согласует его
с DOM. Не нужно вручную записывать innerHTML после каждого события. У компонента есть входные параметры,
обратные события и владелец жизненного цикла. Он не должен незаметно менять чужой объект-параметр.

```razor
<button @onclick="Choose">@Caption</button>
@code {
    [Parameter] public string Caption { get; set; } = "Выбрать";
    [Parameter] public EventCallback<string> Selected { get; set; }
    private Task Choose() => Selected.InvokeAsync(Caption);
}
```

Родитель передаёт Caption, дочерний компонент сообщает действие через EventCallback.
Для редактируемого значения действует пара Value/ValueChanged; синтаксис `@bind-Value` связывает их.
`@key` сохраняет соответствие DOM и устойчивого Id при перестановке элементов. Индекс строки не подходит,
если вставка в начало должна сохранить фокус именно у прежнего объекта.
[Компоненты](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/?view=aspnetcore-10.0).

## Где исполняется C#: render mode

| Режим Blazor Web App | Где выполняется интерактивная логика | Практическое следствие |
| --- | --- | --- |
| Static SSR | Интерактивной сессии компонента нет | HTML и обычные формы, C# onclick сам не работает |
| Interactive Server | На сервере; браузер связан circuit | Задержка сети и память на пользователя важны |
| Interactive WebAssembly | В .NET runtime браузера | Клиентский код и данные доступны пользователю |
| Interactive Auto | Первый интерактивный запуск на сервере, последующие могут использовать WASM | Нужны обе среды и совместимые зависимости |

Auto не переносит текущий живой объект с сервера в WASM посередине события. Нельзя считать один
singleton одновременно серверным и браузерным. WASM требует клиентского проекта и API-границы;
секреты и прямое подключение к БД в него не помещают.
[Render modes](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/render-modes?view=aspnetcore-10.0).

Пример использует Interactive Server. App формирует оболочку, а ReportPanel получает интерактивный режим
с `prerender: false`. Мы явно отказываемся от предварительного выполнения панели, чтобы первый учебный
запрос был связан с кнопкой. В приложении с prerender следует учитывать отдельные фазы и повторный запуск
инициализации; сохранение предварительно загруженного состояния — осознанная задача.

## Жизненный цикл и повторное использование

OnInitialized подходит для настройки экземпляра. OnParametersSet нужен для реакции на новые параметры:
один компонент может получить другой Id без уничтожения. OnAfterRenderAsync вызывают, когда можно
обращаться к элементам DOM; параметр firstRender помогает не запускать одно и то же действие бесконечно.
Освобождение ресурсов выполняется через IDisposable/IAsyncDisposable. Порядок прихода результата
запроса и Dispose нельзя считать фиксированным.

Обработчики событий обычно вызывают повторный render автоматически. Callback от таймера или внешнего
сервиса должен войти через InvokeAsync. В примере уведомления view model переводятся в
`InvokeAsync(StateHasChanged)`, а Dispose отписывается и отменяет активную команду.
Не оставляйте подписку на PropertyChanged после удаления компонента.
[Жизненный цикл](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/lifecycle?view=aspnetcore-10.0).

Для нескольких страниц добавьте Router, RouteView и маршруты `@page "/expenses/{Id:guid}"`;
ограничение guid отсекает неправильный формат маршрута, но не проверяет ownership записи.
NavigationManager выполняет переходы, NavLink отмечает активную ссылку. Единственная страница нашего
примера сознательно обходится без отдельного дерева маршрутов.

## Формы, ошибки и HTML

EditForm создаёт контекст редактирования. InputText связан с моделью, DataAnnotationsValidator проверяет
атрибуты, ValidationSummary показывает ошибки, OnValidSubmit вызывается только после успешной проверки.
В ReportPanel токен ограничен 8192 символами. Это помощь пользователю, а сервер всё равно проверяет
подпись/срок и права. Static SSR-формы имеют дополнительный договор HTTP POST, имени формы и antiforgery;
их нельзя смешивать с интерактивным событием без понимания жизненного цикла.

Razor выводит строку категории как текст с HTML-кодированием. Не превращайте ответ API в MarkupString,
чтобы «поправить» отображение: тогда недоверенный текст становится разметкой. У таблицы есть caption,
у статуса — aria-live, у ошибки — role=alert. Доступность является частью договора компонента.
[Формы](https://learn.microsoft.com/en-us/aspnet/core/blazor/forms/?view=aspnetcore-10.0).

## DI, сессия и аутентификация

В Interactive Server scoped-зависимость обычно принадлежит circuit, а не одному клику и не каждому
HTTP-запросу API. Singleton с текущим токеном смешает пользователей. View model в примере создаётся
для панели; токен передаётся в HTTP-заголовке конкретного запроса. У API-адреса один источник — серверная
конфигурация Ledger:Api. Пользователь не задаёт произвольный URL, который сервер начнёт посещать.

AuthenticationStateProvider сообщает UI состояние пользователя; AuthorizeView управляет видимостью
фрагмента. Скрытая кнопка не защищает endpoint. Проверка доступа остаётся на сервере L06. Учебная панель
принимает временный bearer-токен L06, но полноценный сайт должен согласовать вход, cookie/OIDC,
выход и передачу полномочий внешнему API. Token refresh в примере не реализован.
[DI в Blazor](https://learn.microsoft.com/en-us/aspnet/core/blazor/fundamentals/dependency-injection?view=aspnetcore-10.0),
[состояние аутентификации](https://learn.microsoft.com/en-us/aspnet/core/blazor/security/authentication-state?view=aspnetcore-10.0).

## Граница JavaScript

IJSRuntime нужен для browser API, которых нет в компонентах .NET. Вызов через InvokeAsync передаёт
сериализуемые аргументы; ссылка на произвольный C#-объект сама по себе не является DOM-узлом.
ElementReference становится пригоден после render. Модуль JS импортируют, хранят его IJSObjectReference
и освобождают при завершении. Для callback через DotNetObjectReference тоже нужен Dispose.

Не редактируйте из JS тот же фрагмент DOM, которым управляет Blazor: следующая сверка может нарушить
предположения обеих сторон. Вызовы JS в Server идут через соединение и могут завершиться
JSDisconnectedException при исчезновении circuit. Пример отчёта не требует своего JS-модуля;
его добавление для focus/clipboard вынесено в практику.
[JS interop](https://learn.microsoft.com/en-us/aspnet/core/blazor/javascript-interoperability/?view=aspnetcore-10.0).

## Запуск и bUnit

```text
dotnet run --project examples/Specializations/BlazorClient -- --urls http://localhost:5080
python tools/verify_specializations.py
```

Для локального HTTP установите DOTNET_ENVIRONMENT=Development в текущем терминале; полноценный порядок
есть в [README](../../examples/Specializations/README.md). Без Ledger:Api работают демонстрационные данные.
Внешнее развёртывание требует HTTPS и корректной конфигурации прокси.

bUnit 2.12.5 создаёт BunitContext, рендерит компонент, регистрирует тестовый IReportSource и отправляет
события формы. Тест проверяет видимый DOM: Loading, отключённую кнопку, Ready, отмену и сообщение ошибки.
Управляемое завершение Task делает переход воспроизводимым. WaitForAssertion ждёт ожидаемый render,
а не произвольную секунду. Проверка двух панелей ловит общий статический state; проверка строки со
`<script>` ловит непреднамеренный вывод HTML.
[Тестирование компонентов](https://bunit.dev/docs/getting-started/writing-tests.html).

Скрипт дополнительно поднимает настоящий Kestrel и читает HTML и blazor.web.js. Это не browser e2e:
он не исполняет JS и не проверяет переподключение SignalR или layout. Для этого нужен отдельный браузерный
сценарий, например через Playwright, с явной проверкой действий и видимых результатов.

## Типичные ошибки и контрольные вопросы

Повторная подписка в OnParametersSet без отписки удваивает события. Singleton с Rows публикует чужие
данные. Запрос в каждом OnAfterRenderAsync без условия создаёт цикл. `.Result` блокирует обработку circuit.
Проверка только CSS-класса Loading пропустит возможность повторной отправки через форму.

1. Чем scoped в API-запросе отличается от scoped в Interactive Server?
2. Почему кнопка с C#-обработчиком не оживает в Static SSR?
3. Какие ошибки bUnit обнаружит, а какие требуют настоящего браузера?

## Практика

**51-A.** Вход: успешный отчёт, пустой ответ, HttpRequestException. Ожидаются Ready, Empty и Error.
Добавьте тест пустой таблицы и проверьте доступность обеих кнопок. Критерий: тесты смотрят DOM и не
привязаны к приватным полям компонента.

**51-B.** Выделите таблицу в компонент с Rows и EventCallback выбора категории, добавьте страницу
`/category/{name}`. Вход: две категории и переход назад. Ожидается сохранённое выбранное значение,
корректное кодирование имени и обработка неизвестной категории. Критерий: параметры не мутируются,
маршрут не даёт доступа к чужим данным, есть bUnit-проверки.

**51-C.** Добавьте JS-модуль фокуса после ошибки и browser e2e для загрузки/отмены/выхода пользователя.
Вход: медленный API и оборванное соединение. Критерий: UI объясняет потерю связи, ресурсы JS освобождаются,
старые строки не появляются после выхода, тесты явно различают bUnit, HTTP smoke и браузер.
[Подсказки](../appendices/hints.md).
