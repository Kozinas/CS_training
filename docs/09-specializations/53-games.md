# 53. C# в игровых движках

**Результат:** вы отделяете игровые правила от сцены, сохраняете инвентарь с проверкой версии,
обрабатываете delta time и понимаете границы совместимости Unity/Godot. Нужны главы 14, 19–20, 27, 31, 34 и 36.
Примеры: [GameRules](../../examples/Specializations/GameRules/Inventory.cs),
[GodotClient](../../examples/Specializations/GodotClient/Main.cs),
[UnityAdapter](../../examples/Specializations/UnityAdapter/InventoryBehaviour.cs).

## Язык, API и runtime — три разных ограничения

Установленный на компьютере SDK .NET 10 не обновляет автоматически runtime игрового проекта.
Движок выбирает компилятор, набор доступных API, формат сериализации, pipeline сборки и платформенные
ограничения. Код с C# 14 и net10.0 нельзя считать переносимым только потому, что его файл называется .cs.

В качестве конкретной границы совместимости рассматривается Unity 6.0 (6000.0), документация которого
описывает C# 9 с ограничениями отдельных возможностей. Это версия для сравнения, а не заявление о
самой новой Unity. Godot-пример закреплён на Godot.NET.Sdk 4.6.2, target net8.0, C# 12.
Общая GameRules собрана для netstandard2.1 с C# 9 и не зависит от движка.
[Компилятор Unity 6.0](https://docs.unity3d.com/6000.0/Documentation/Manual/csharp-compiler.html),
[C# в Godot 4.6](https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/c_sharp_basics.html).

Netstandard описывает доступную поверхность API библиотеки, а не установленный runtime.
Обычный конструктор класса может создавать Inventory, но компонент движка создаётся по правилам
движка. MonoBehaviour нельзя полноценно заменить `new MyBehaviour()`, а Godot Node нужно включить
в дерево, если его логика зависит от _Ready и SceneTree.

## Сцена и жизненный цикл

| Задача | Unity | Godot |
| --- | --- | --- |
| Подготовить экземпляр/связи | Awake, затем Start с учётом порядка | _EnterTree, _Ready |
| Обработать обычный кадр | Update | _Process(delta) |
| Шаг физики | FixedUpdate | _PhysicsProcess(delta) |
| Подписаться/отписаться | OnEnable / OnDisable | Вход/выход из дерева, _ExitTree |

Это ориентир обязанностей, а не взаимно однозначное соответствие всех гарантий порядка.
Ссылка на объект сцены может стать недействительной после удаления; lifetime managed-обёртки
и native-объекта не всегда совпадает. Не используйте сохранённую ссылку на уничтоженный Node после await.
[Порядок событий Unity](https://docs.unity3d.com/6000.0/Documentation/Manual/ExecutionOrder.html),
[Node](https://docs.godotengine.org/en/4.6/classes/class_node.html).

В GodotClient _Ready создаёт контролы и подписывается на Inventory.Changed; _ExitTree отписывается.
GameRules знает только событие Action. Оно вызывается синхронно после успешного изменения, поэтому
подписчик не должен бросать исключение или незаметно повторно менять модель. Для сложной игры полезна
очередь событий с явной точкой обработки, но она не нужна для этого маленького примера.

## Движение и время кадра

Присваивание `x += 3` в каждом Update означает три единицы на кадр: на 144 FPS объект быстрее, чем на 30.
Если скорость равна трём единицам в секунду, шаг равен `3 * delta`. Для диагонали вектор (1,1)
имеет длину больше единицы; без нормализации движение ускоряется.

```csharp
double length = Math.Sqrt(axisX * axisX + axisY * axisY);
double scale = 3 * delta / Math.Max(1, length);
X += axisX * scale;
Y += axisY * scale;
```

Motion ограничивает оси диапазоном [-1,1], delta — [0,0.25], отклоняет NaN и infinity.
Это кинематическая демонстрация, не полноценная физика. При большом stall выбирают политику:
ограничить визуальный шаг, выполнить несколько фиксированных шагов с лимитом или догонять иначе.
Молча проигнорировать секунду или бесконечно догонять очередь одинаково опасно для разных игр.
Тесты 30/60/144 шага сравнивают итоговую дистанцию с допуском; это не доказательство одинаковой
физики столкновений или детерминизма между платформами.

## Инвентарь как проверяемый автомат

Пример хранит до 100 монет, идентификаторы уже собранных объектов и события успешных изменений.
PickUp возвращает false для повтора spawnId или переполнения. Неуспешный pickup не помечает объект
собранным: его можно забрать позже, освободив место. Spend не допускает отрицательного остатка.

```csharp
var bag = new Inventory();
bag.PickUp("level-1:coin-1", 10); // true
bag.PickUp("level-1:coin-1", 10); // false: тот же объект
bag.Spend(3);                    // остаток 7
```

SpawnId должен быть устойчивым идентификатором объекта уровня, а не новым Guid на каждом столкновении.
UI-кнопка в Godot-демонстрации создаёт новые учебные pickup; в настоящей сцене Id задаётся уровнем.
История ограничена 1000 Id. Для большой игры требуется политика хранения по уровням/checkpoints;
бесконечный HashSet не является масштабируемой моделью сохранений.

## Сохранение и версия

SaveData — отдельный DTO: Version, Coins, Pickups. Сохранять весь граф сцены с контролами и ссылками
на ресурсы не нужно. Snapshot сортирует Id для воспроизводимого файла. Restore сначала проверяет весь
вход, затем заменяет живое состояние; неправильная версия или повтор Id не должны оставить половину данных.

CLI сериализует DTO через System.Text.Json, ограничивает вход 128 KiB и пишет временный файл рядом
с целевым, затем переименовывает. Это пример одного писателя; он не обещает сохранность при потере питания
и не разрешает конкуренцию двух процессов. Следующий формат требует явной миграции Version, проверки
ограничений и тестов старых сохранений. Локальный JSON не защищает от изменения игроком; авторитетные
правила многопользовательской игры проверяются сервером.

Unity сериализует поля по своим правилам; обычные properties, Dictionary, generic-типы и полиморфизм
требуют внимательного выбора поддерживаемого механизма. SerializeField и SerializeReference решают
разные задачи. Godot export/resources также не являются System.Text.Json. Разделение DTO и сценового
представления позволяет выбрать формат без переписывания инвентаря.
[Сериализация Unity](https://docs.unity3d.com/6000.0/Documentation/Manual/script-serialization-rules.html).

## Coroutine, Task и кадр

Unity coroutine с yield распределяет работу по кадрам, но сама по себе не создаёт фоновый поток.
Task представляет завершение операции; async HTTP не означает, что можно менять сцену с ThreadPool.
После await требуется корректный контекст движка и проверка lifetime объекта. Фоновая CPU-задача
должна работать над независимыми данными, а результат применяться на главном потоке.
Godot-сигналы можно ожидать через ToSignal; при удалении владельца ожидание и подписки требуют
осознанного завершения, особенно если источник сигнала живёт дольше сцены.

В горячем цикле избегайте создания LINQ-цепочек, новых строк и временных массивов на каждый кадр.
Это не запрет LINQ во всей игре: сначала измерьте allocations и время на целевом устройстве.
Boxing структуры в object, замыкание и обновление текста каждый кадр могут оказаться дороже арифметики.
Пулы требуют возврата и сброса объектов; большой удерживаемый пул тоже расходует память.
[Оптимизация GC в Unity](https://docs.unity3d.com/6000.0/Documentation/Manual/performance-garbage-collection-best-practices.html).

## Как выполнить пример

```text
dotnet run --project examples/Specializations/Scenarios -- game .artifacts/game-save.json
dotnet run --project examples/Specializations/Scenarios -- game .artifacts/game-save.json
```

Первый запуск нового файла: Coins=10, Added=true. Второй: Coins=10, Added=false.
Для независимого опыта выберите новый путь; `.artifacts` уже создаётся проверяющим скриптом.

Godot 4.6.2 .NET:

```text
dotnet build examples/Specializations/GodotClient -c Debug
godot-dotnet --path examples/Specializations/GodotClient
godot-dotnet --headless --path examples/Specializations/GodotClient -- --verify
```

Имя executable зависит от установки; вариант с полным путём есть в README. Headless-проверка реально
загружает сцену, создаёт C# Node, восстанавливает JSON и проверяет движение. Рендеринг, ввод, звук и экспорт
ею не проверяются. В CI Godot-проект компилируется; запуск движка требует установленного Godot и параметра
`--godot` скрипта. UnityAdapter дан для переноса в Assets вместе с GameRules.dll; Unity Editor в этом
выпуске не запускался. Экспорт C#-проекта Godot на web нельзя обещать по аналогии с GDScript.
