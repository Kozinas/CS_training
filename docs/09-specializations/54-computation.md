# 54. Вычисления и обработка данных

**Результат:** вы получаете воспроизводимый численный отчёт, отделяете точные суммы от статистических
оценок, проверяете SIMD по эталону и выбираете границу с ML/Python. Нужны главы 23, 25–27, 33–34 и 36.
Код — [ExpenseAnalysis](../../examples/Specializations/Analysis/ExpenseAnalysis.cs), запуск — Scenarios.

## Сначала смысл числа

Отчёт принимает целые копейки, а не произвольные числа с плавающей точкой. Так сумма расходов остаётся
точной и не зависит от округления double. Для исходного decimal сначала проверяют допустимую точность
и диапазон, затем преобразуют в minor units. Округление не должно молча исправлять неправильный вход.

Статистическая оценка имеет другой договор. Среднее и стандартное отклонение могут быть дробными,
поэтому пример переводит проверенные значения в double. В выбранном диапазоне одна сумма до 99 999 999
копеек точно представима в double; последующие вычисления всё равно округляются. Checked проверяет
переполнение целого total, а не точность статистики.

Для 100, 200, 300 копеек точная сумма равна 600, среднее — 200. Выборочная дисперсия делит сумму
квадратов отклонений на n−1: (10000+0+10000)/2=10000; стандартное отклонение равно 100.
Дисперсия генеральной совокупности использовала бы n. Это разные вопросы, а не две взаимозаменяемые функции.
При n=1 выборочная дисперсия не определена; наш договор отклоняет вход короче двух значений.

## Math.NET и проверка известным ответом

MathNet.Numerics 5.0.0 предоставляет статистику, матрицы, разложения, интерполяцию и другие численные
алгоритмы. В примере вызываются Mean и StandardDeviation. Мы проверяем их маленьким набором с ручным
ответом, а не тестом «результат совпал с другим вызовом той же функции».
[Статистические методы Math.NET](https://numerics.mathdotnet.com/api/MathNet.Numerics.Statistics/Statistics.htm).

```csharp
long total = checked(totalBefore + amountMinor);
double mean = values.Mean();
double deviation = values.StandardDeviation();
```

Не вычисляйте дисперсию наивно как mean(x*x)−mean(x)*mean(x), если значения велики, а разброс мал:
вычитание близких чисел теряет значащие разряды. Для потоковой обработки можно использовать алгоритм
с последовательным обновлением среднего и суммы квадратов отклонений, затем сравнить его с эталонными
наборами. Математическая формула ещё не гарантирует численную устойчивость реализации.

Для линейной алгебры предпочитайте решение системы через подходящее разложение прямому вычислению
обратной матрицы. Сингулярная/плохо обусловленная матрица, масштаб признаков и невязка требуют проверки.
Добавление библиотеки не делает любое статистическое предположение справедливым.
[Линейная алгебра Math.NET](https://numerics.mathdotnet.com/Matrix).

## Ограниченный конвейер данных

CLI читает JSON-массив целых копеек. Файл ограничен 2 MiB, набор — 100 000 значениями, каждое значение —
положительной суммой в диапазоне. Сначала проверяется весь вход, затем печатается один JSON-отчёт.
Ошибка позднего элемента не должна оставить stdout с похожим на успешный частичным результатом.

Для больших наборов используйте потоковый JSON/NDJSON или CSV-парсер из [главы 27](../04-libraries/27-formats.md).
Не разбирайте CSV через Split(','): кавычки и переводы строки внутри поля нарушат такой алгоритм.
Задайте encoding, культуру, валюту, формат дат, политику пропусков/дубликатов и лимиты до распараллеливания.
Параллельный неправильный парсер лишь быстрее создаёт неверные данные.

Воспроизводимый артефакт анализа включает версию кода и схемы, хэш/версию входа, параметры,
использованные пакеты и описание обработки пропусков. Fixed random seed помогает повторить случайное
разбиение, но не обещает побитового совпадения разных CPU, native-провайдеров или параллельных редукций.
Не смешивайте отдельно проведённые измерения разных наборов в одну таблицу без их идентификации.

## System.Numerics и SIMD

Vector2/Vector3/Matrix4x4 удобны для геометрии. `Vector<T>` использует аппаратно зависимую ширину для
однотипных операций над несколькими числами. Векторизация не равна запуску нескольких Task:
один поток обрабатывает несколько элементов за инструкцию. Intrinsics дают более точный контроль
над инструкциями, но повышают требования к fallback и переносимости.
[SIMD в .NET](https://learn.microsoft.com/en-us/dotnet/standard/simd).

VectorSum обрабатывает полные блоки Vector.Count, затем хвост. Число элементов не обязано делиться
на ширину вектора. Тесты включают 0, 1, 17 и 100003 значения; ширина не зашита числом 4 или 8.

```csharp
var sum = Vector<double>.Zero;
int i = 0;
for (; i <= values.Length - Vector<double>.Count;
       i += Vector<double>.Count)
    sum += new Vector<double>(values.Slice(i, Vector<double>.Count));
double result = Vector.Sum(sum);
for (; i < values.Length; i++) result += values[i];
```

Порядок сложения изменился. Для floating point `(a+b)+c` может отличаться от `a+(b+c)`:
например, большие положительное и отрицательное значения рядом с маленьким числом дают потерю разрядов.
Поэтому сравнение общего численного алгоритма использует абсолютный и относительный допуски:

```text
abs(actual - expected) <= absolute + relative * max(abs(actual), abs(expected))
```

Вблизи нуля важен absolute; для большого масштаба — relative. Оба допуска выбирают из требований,
а не увеличивают до прохождения теста. NaN и infinity отклоняются явно. VectorSum — демонстрационная
редукция над подготовленными данными; она не обещает устойчивость на произвольном наборе с сильной компенсацией.

## Измерение без выдуманного ускорения

```text
dotnet run -c Release --project examples/Specializations/Scenarios -- measure
```

Команда создаёт одинаковый набор, прогревает обе функции, выполняет по 200 повторов и печатает время,
allocations, runtime, аппаратную поддержку и ширину Vector. Result используется, чтобы вычисление
не было бессмысленным с точки зрения вызывающего кода. Stopwatch и оболочка измерения сами дают
небольшие накладные расходы. Это короткое наблюдение, не замена BenchmarkDotNet из главы 34.

CI проверяет правильность результатов и сохраняет измерения, но не требует «SIMD минимум вдвое быстрее».
Виртуальная машина, питание, JIT, кэш, объём данных и конкурирующая нагрузка меняют числа.
Перед усложнением кода найдите реальное узкое место: если время уходит в чтение CSV, ускорение суммы
не ускорит приложение в той же пропорции. Дайте сравниваемым вариантам одинаковую работу.

## ML.NET: обучение отличается от обычного отчёта

ML.NET позволяет описать вход через IDataView, построить pipeline преобразования признаков и обучения,
выполнить Fit, оценить модель и сохранить её вместе с преобразованиями. Модель расходов может оценивать
вероятную категорию или аномалию, но предсказание не заменяет бухгалтерское правило проверки суммы.

Разделите обучение, подбор параметров и окончательную проверку. Если данные имеют время, случайное
перемешивание будущих покупок с прошлыми создаст утечку. Преобразования, зависящие от статистики,
обучают только на train. Для классификации важны ошибки по классам, для регрессии — подходящие метрики
и сравнение с простым baseline. Высокая точность на train сама по себе ничего не доказывает.
[Обучение и оценка ML.NET](https://learn.microsoft.com/en-us/dotnet/machine-learning/how-to-guides/train-machine-learning-model-ml-net).

PredictionEngine не следует хранить как произвольный общий объект конкурентного сервиса без проверки
его потоковой модели. Для сервиса применяют предусмотренный пул или пакетное преобразование данных.
Версия модели, признаки и нормализация входят в контракт так же, как схема API.
ML.NET здесь рассмотрен как маршрут расширения; обученная модель в комплект не включена.

## ONNX Runtime, tensors и batching

ONNX Runtime исполняет совместимую модель через InferenceSession. Сначала прочитайте имена, типы
и формы входов/выходов. Тензор `[batch, features]` и `[features, batch]` имеют одинаковое число элементов,
но разный смысл. Для изображения важны NHWC/NCHW, порядок RGB/BGR, масштаб и нормализация.
Случайный массив нужной длины не является корректным входом модели.

Session обычно создают один раз на выбранную конфигурацию, а не на каждый запрос. OrtValue и результаты
могут удерживать native-память; освобождайте их по документированному lifetime. Поддержка GPU требует
совместимых runtime, drivers и execution provider. Успешный CPU inference не доказывает GPU-запуск.
[C# API ONNX Runtime](https://onnxruntime.ai/docs/tutorials/csharp/basic_csharp.html).

Batching объединяет несколько объектов в один inference, уменьшая накладные расходы. За это платят
задержкой ожидания batch, памятью и необходимостью разделить ответы обратно по запросам. Нужны лимит
размера, максимальное время ожидания, отмена и backpressure. Этому помогают Channels из главы 33.
ONNX-пакеты/модель в обязательный пример не добавлены: он проверяет статистику, а не заявляет проверенный ML pipeline.

## Где провести границу C# и Python

Python удобен для исследовательского анализа и обучения; C# может обслуживать API, UI и интеграции.
Для передачи результата сначала рассмотрите версионированный JSON/CSV/Parquet или экспорт ONNX.
Если нужен отдельный процесс, задайте протокол stdin/stdout, framing, encoding, таймаут и коды ошибок;
не склеивайте пользовательские аргументы в shell-команду. HTTP/gRPC дают сетевую границу с собственными
ограничениями повторов и доступности. Встраивание Python приносит native runtime и lifetime, которые
обычный ProjectReference не решает.

Для проверки границы возьмите маленький фиксированный вход и сравните оба результата с независимым
ожидаемым ответом. Зафиксируйте порядок колонок, типы, пропуски, timezone и допуск. Число `1234` без
указания рублей/копеек может пройти все JSON-парсеры и всё равно испортить смысл отчёта.

## Практический запуск, вопросы и задания

Создайте UTF-8 файл `.artifacts/amounts.json` с `[100,200,300]` и выполните:

```text
dotnet run --project examples/Specializations/Scenarios -- analyze .artifacts/amounts.json
python tools/verify_specializations.py
```

Ожидаются Count=3, TotalMinor=600, MeanMinor=200, SampleDeviationMinor=100.
Вход `[100,1.5]`, пустой массив, отрицательная сумма и повреждённый JSON завершаются ошибкой без отчёта.

1. Почему для точной суммы и оценки разброса выбраны разные типы?
2. Почему SIMD может дать другой последний разряд и не обязано ускорять весь pipeline?
3. Как временное разбиение данных защищает оценку модели от знания будущего?

**54-A.** Вход: `[100,200,300]`, `[500,500]`, `[100]`. Ожидаются известные средние/отклонения и отказ
для одного значения. Критерий: ручной расчёт совпадает с кодом, объяснено деление на n−1 и отсутствие
частичного stdout при ошибке.

**54-B.** Добавьте потоковое чтение NDJSON, устойчивое обновление среднего/дисперсии и сравнение с Math.NET.
Вход: 100000 строк, пропуск в середине, большие близкие значения и отмена. Критерий: память ограничена,
политика ошибок явная, точная сумма не заменена double, допуски обоснованы; измерены одинаковые наборы.

**54-C.** Реализуйте анализ по категориям и одну дополнительную ветку: ML.NET-классификацию с честным
train/test либо ONNX-inference с документированной моделью. Вход: версионированный набор и отдельный
контрольный набор. Критерий: есть baseline, метрики/эталон, schema и provenance модели, лимиты batch,
учёт native-ресурсов и воспроизводимый запуск; скорость не достигается изменением результата.
