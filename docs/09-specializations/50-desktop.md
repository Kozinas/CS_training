# 50. Windows desktop и кроссплатформенный desktop

**Результат:** вы создаёте окно отчёта, отделяете правила от представления, показываете загрузку,
ошибку и отмену, проверяете поведение без ручного нажатия кнопок. Нужны главы 14, 29, 31, 36 и 49.
Запускаемый пример: [Specializations](../../examples/Specializations/README.md), проекты ClientCore и DesktopClient.

## Как выбрать UI и не потерять общую логику

Desktop-приложение живёт дольше одного HTTP-запроса. Окно удерживает состояние, подписки и незавершённые
операции; закрытие окна становится границей владения ресурсами. Предметная модель по-прежнему не должна
знать, какая кнопка её вызвала. В нашем клиенте HTTP возвращает ReportRow, view model задаёт состояния,
а XAML описывает вид. Такой разрез позволяет проверить ошибку сети без запуска всего приложения.

| Среда | Модель работы | Что проверить перед выбором |
| --- | --- | --- |
| WinForms | Формы, контролы, события, дизайнер | Windows, существующая кодовая база, требования к интерфейсу |
| WPF | XAML, привязки, команды, стили и шаблоны | Windows, MVVM, доступность, сложные представления данных |
| Avalonia | XAML-подобная разметка и собственный UI stack | Поддержку нужных ОС, контролов, ввода и средств доставки |

WPF и WinForms из .NET не превращаются в Linux-приложения при смене RuntimeIdentifier.
Avalonia позволяет переиспользовать привычные идеи, но это отдельная библиотека с отличиями в свойствах,
стилях и XAML. В этой главе исполняется WPF; порт на Avalonia — задание с отдельной проверкой.
[WPF](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/),
[WinForms](https://learn.microsoft.com/en-us/dotnet/desktop/winforms/overview/),
[Avalonia](https://docs.avaloniaui.net/docs/get-started/).

## Привязка: источник, путь, направление, уведомление

В WPF DataContext задаёт обычный объект-источник. `{Binding State}` читает его свойство State.
Когда свойство меняется, представление должно узнать об этом через INotifyPropertyChanged.
Само присваивание обычному полю не обновляет экран. Если вы заменили всю коллекцию, нужно уведомление
о свойстве; если меняете элементы коллекции, обычно нужен ObservableCollection и уведомления элементов.

Направление OneWay достаточно для текста отчёта, TwoWay нужно для редактирования. UpdateSourceTrigger
определяет момент переноса изменения в модель: у TextBox это может быть потеря фокуса или каждый ввод.
Не полагайтесь на одинаковые значения по умолчанию у всех контролов. Ошибка привязки часто появляется
в diagnostic output, а не как исключение в обработчике кнопки.
[Механика binding](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/data/).

```xml
<TextBlock Text="{Binding State}" />
<Button Content="Загрузить" Command="{Binding LoadCommand}" />
<Button Content="Отмена" Command="{Binding LoadCancelCommand}" />
<DataGrid ItemsSource="{Binding Rows}" IsReadOnly="True" />
```

Command объединяет действие и условие доступности. CanExecute влияет на кнопку; его изменение требует
CanExecuteChanged. Это удобнее, чем вручную согласовывать пять IsEnabled в разных обработчиках.
При этом команда не заменяет серверную авторизацию или проверку инвариантов.

## MVVM и CommunityToolkit

Model хранит данные и правила; ViewModel готовит состояние для UI; View связывает его с контролами.
Маленькое окно может иметь code-behind для настройки DataContext, фокуса и закрытия. Переносить туда
HTTP, SQL и доменные решения ради короткой view model не следует.

В [ReportViewModel](../../examples/Specializations/ClientCore/ReportViewModel.cs) используются генераторы
CommunityToolkit.Mvvm 8.4.2. Partial-класс обязателен: генератор дописывает свойства и команды.

```csharp
[ObservableProperty] private string state = "Idle";

[RelayCommand(IncludeCancelCommand = true)]
private async Task LoadAsync(CancellationToken token)
{
    // Полный метод в ClientCore обрабатывает состояния и отмену.
    var result = await source.ReadAsync(Token, token);
    Rows = result;
}
```

Из LoadAsync получается LoadCommand; поддержка отмены создаёт LoadCancelCommand.
AsyncRelayCommand сообщает IsRunning и хранит ExecutionTask. Обычная команда не разрешает новый запуск
через UI во время предыдущего. Прямой вызов ExecuteAsync из вашего кода всё равно требует дисциплины:
CanExecute — договор UI, а не универсальная блокировка многопоточности.
[Асинхронные команды](https://learn.microsoft.com/en-us/dotnet/communitytoolkit/mvvm/asyncrelaycommand).

## Состояния должны иметь однозначный смысл

```text
Idle -> Loading -> Ready | Empty | Error | Canceled
                закрытие владельца -> отмена, отписка, освобождение
```

Перед запросом пример очищает Rows и Error. После успеха непустой результат означает Ready, пустой — Empty.
Пользовательская отмена не показывается как авария сети. Timeout — отдельная ошибка ожидания.
Если приложение сохраняет старый отчёт во время обновления, оно должно явно пометить его как устаревший
и не перепутать владельцев после выхода из аккаунта. Здесь выбран более простой договор: старые строки убираются.

CancellationToken — просьба прекратить работу, не откат сервера. Даже после отмены HTTP сервер мог закончить
запись. Для изменяющих операций нужен ключ идемпотентности из L06, а не надежда на кнопку Cancel.
После получения результата view model ещё раз проверяет token: транспорт мог проигнорировать отмену.

## UI thread и async

Контролы WPF принадлежат dispatcher-потоку. В обработчике UI обычный await возвращает продолжение
в захваченный контекст. Поэтому view model, запускаемая с UI, может после await обновить свои свойства.
Код транспортной библиотеки может использовать ConfigureAwait(false), но нельзя механически перенести
его в метод, который затем изменяет привязанные данные. Вызов из фонового callback следует маршалировать
через Dispatcher.InvokeAsync. CPU-тяжёлую работу можно вынести в Task.Run, соблюдая владение данными.

`.Result` и `.Wait()` на UI блокируют обработку сообщений и способны создать deadlock. `async void`
допустим на границе обычного UI-события, где его требует сигнатура; внутренние методы должны возвращать Task.
Исключения из такой границы обрабатываются явно. Пример использует async-команду и ожидаемый Task.
[Потоковая модель WPF](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/threading-model).

## Запуск и связь с API

Из корня репозитория на Windows:

```text
dotnet run --project examples/Specializations/DesktopClient
python tools/verify_specializations.py
```

По умолчанию показываются две демонстрационные категории и сумма 5000 копеек. Для L06 задайте LEDGER_API
с завершающим `/` и LEDGER_TOKEN в текущем процессе, затем запустите окно. Полный порядок входа дан в
[README примеров](../../examples/Specializations/README.md). Это учебная передача короткоживущего токена;
готовый продукт требует полноценного входа, выхода и обновления сессии.

LedgerHttpClient не кладёт токен в общие DefaultRequestHeaders, ограничивает ответ 64 KiB, время 10 секундами
и не следует redirect. HTTP разрешён только для loopback-упражнения; внешний адрес требует HTTPS.
Сертификаты не отключаются. Ошибку доступа UI показывает без содержимого токена и внутренних сообщений сервера.

## Что и как проверено

Тесты view model управляют завершением запроса через TaskCompletionSource: видно Loading, можно отменить
операцию, вернуть пустой результат или ошибку. Они не ждут произвольное время ради воспроизведения гонки.
DesktopClient с `--verify` создаёт Application, Window и настоящий dispatcher, проверяет XAML-привязки
после загрузки и отмены. Окно не выводится на экран. Это проверка поведения, а не визуальная приёмка
масштабирования, клавиатурной навигации и screen reader.

Доставка требует отдельного решения: framework-dependent или self-contained, архитектура, подпись,
установщик, права, расположение пользовательских данных и откат обновления. ClickOnce/MSIX — варианты,
а не гарантия совместимости любого приложения. Не храните БД в каталоге установки и не меняйте схему
без плана совместимости со старой версией. Поставка продолжится в блоке 55–60.

## Типичные ошибки

- Несколько повторных запросов перезаписывают UI в порядке завершения: запретите параллельный запуск
  или используйте номер запроса, прежде чем принимать результат.
- Подписка долгоживущего сервиса удерживает закрытое окно: отписывайтесь и отменяйте работу при закрытии.
- Коллекцию меняют из ThreadPool: верните изменение состояния на UI context.
- Любое исключение проглатывают и показывают Empty: ошибка и отсутствие данных должны различаться.

## Практика

**50-A.** Запустите демонстрацию. Вход: Ready с food=2000, travel=3000 и отменяемый повторный запрос.
Ожидаются Loading, Ready и Canceled с пустой таблицей после отмены. Критерий: кнопки имеют правильную
доступность, тест проверяет порядок состояний без Thread.Sleep.

**50-B.** Добавьте фильтр по минимальной сумме и ошибку валидации. Вход: 2500, 0 и текст `abc`.
Ожидаются travel, обе категории и понятная ошибка соответственно. Критерий: исходные данные не меняются,
невалидный ввод не запускает сеть, тесты не требуют Window.

**50-C.** Подключите L06, добавьте вход/выход и перенесите представление на Avalonia либо расширьте WPF
доступной клавиатурной навигацией. Вход: две учётные записи, медленная сеть, закрытие окна в Loading.
Критерий: данные аккаунтов не смешиваются, закрытие освобождает подписки, есть инструкция установки
на чистой целевой системе и протокол ручной проверки UI. [Подсказки](../appendices/hints.md).
