# 28. HTTP и сетевые клиенты

**Результат:** вы получаете данные с ограничением размера и времени, различаете ошибки
и проверяете повторы без внешнего сервиса. Нужны главы 20, 26–27.
Код — [ImportHttpClient](../../examples/Integration/ImportCli/ImportHttpClient.cs).

## Договор запроса и ответа

HTTP-запрос имеет метод, адрес, заголовки и иногда тело. Ответ содержит статус, заголовки и тело.
GET читает ресурс; POST обычно инициирует действие; PUT и DELETE имеют другие договоры повторения.
«Идемпотентный» означает, что повтор приводит к тому же предполагаемому эффекту,
а не обязательно к тому же статусу или отсутствию журналирования.

2xx обозначает успешную обработку на уровне HTTP, 3xx — перенаправление,
4xx — проблему запроса или доступа, 5xx — сбой обработки сервером.
200 с HTML вместо ожидаемого JSON не является успешным импортом.
EnsureSuccessStatusCode проверяет статус, а Content-Type, структуру и модель проверяет наш код.

Не передавайте секреты в URL: они легко попадают в журналы и историю.
В образце нет аутентификации и автоматически не следуются redirects.
Разрешены HTTPS и HTTP для loopback-упражнений. Сертификаты HTTPS проверяются стандартным механизмом;
проверка сертификата нигде не отключается.

## HttpClient и время жизни соединений

Частое создание и уничтожение клиента с собственным handler мешает повторному использованию
соединений. Другой крайний случай — бесконечная жизнь соединений без учёта обновления DNS.
Обычные подходы: долгоживущий HttpClient с PooledConnectionLifetime
или короткоживущие клиенты IHttpClientFactory с управляемым временем жизни handler.

Dispose клиента, созданного фабрикой, не означает немедленного уничтожения общего пула.
Не удерживайте typed client в singleton без оценки зависимостей и обновления handler.
CookieContainer тоже связан с handler; у нашего клиента UseCookies=false.
[Правила HttpClient](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/http/httpclient-guidelines).

В ImportServices зарегистрирован именованный клиент import и typed client ImportHttpClient.
Фабрика и DI подробно рассматриваются в следующей главе; сейчас достаточно понимать,
что конфигурация транспорта отделена от операции загрузки.

## Заголовки готовы — тело ещё читается

```csharp
// Фрагмент DownloadAsync; deadline.Token охватывает весь метод.
using var response = await client.GetAsync(
    uri, HttpCompletionOption.ResponseHeadersRead, deadline.Token);
response.EnsureSuccessStatusCode();
await using var stream =
    await response.Content.ReadAsStreamAsync(deadline.Token);
return await BoundedFiles.ReadAsync(
    stream, options.Value.MaxBytes, deadline.Token);
```

Режим ResponseHeadersRead возвращает управление после получения заголовков.
Это позволяет проверять размер и читать поток, но время чтения тела нужно ограничивать отдельно.
DownloadAsync создаёт связанный CancellationTokenSource и задаёт deadline на весь метод,
включая повторы и чтение тела. Сам HttpClient.Timeout отключён, чтобы не создавать
ещё один плохо различимый срок поверх этого договора.

Content-Length проверяется заранее, если он известен; счётчик ReadAsync нужен даже при его отсутствии.
Автоматическая распаковка отключена. Для клиента с gzip пришлось бы дополнительно ограничивать
декомпрессированный поток и учитывать его стоимость.

## Отмена, timeout и классификация ошибок

| Событие | Поведение образца |
| --- | --- |
| Пользователь отменил операцию | OperationCanceledException, CLI-код 130 |
| Истёк собственный HTTP-deadline | TimeoutException, CLI-код 5 |
| Ошибка сети или неприемлемый статус | Ошибка получения, CLI-код 5 |
| Неподходящий Content-Type или слишком большое тело | Ошибка входа, CLI-код 3 |
| JSON повреждён после успешной загрузки | Ошибка документа, CLI-код 3 |

Отмена — совместный протокол. Передавайте один token вниз по вызовам, не заменяйте его default
при чтении тела. Не ловите OperationCanceledException как обычный повод повторить запрос.
Ошибка, возникшая после записи состояния, требует понимать границу фиксации;
повторный запуск L03 рассчитан на распознавание уже принятых Id.

## Ограниченный повтор

Microsoft.Extensions.Http.Resilience 10.11.0 предоставляет интеграцию с HttpClient
и использует Polly. В образце добавлен один standard resilience handler:
не более одной повторной попытки, задержка с jitter и отключение повторов unsafe-методов.

```csharp
// Фрагмент настройки AddStandardResilienceHandler.
options.Retry.MaxRetryAttempts = 1;
options.Retry.Delay = TimeSpan.FromMilliseconds(100);
options.Retry.UseJitter = true;
options.Retry.DisableForUnsafeHttpMethods();
```

Стандартный handler включает также rate limiter, timeouts и circuit breaker.
В нашем договоре попытка ограничена 5 секундами, pipeline — 15 секундами;
общий deadline DownloadAsync может прервать операцию раньше и покрывает чтение тела.
На задержку может влиять Retry-After. Нельзя считать «две попытки по 5 секунд»
единственным выражением времени всего импорта.
[HTTP resilience](https://learn.microsoft.com/en-us/dotnet/core/resilience/http-resilience).

Не повторяйте каждый 4xx: неверный URL или токен обычно не исправляются ожиданием.
Не повторяйте POST, если сервер не предоставил безопасный договор, например idempotency key.
Не складывайте несколько retry-handler: число запросов перемножится.
Backoff уменьшает частоту повторов, jitter рассеивает их во времени;
circuit breaker временно останавливает обращения к регулярно падающей зависимости.
Это разные механизмы, а не разные названия одного retry.

## Проверка настоящего транспорта

IntegrationChecks поднимает TcpListener на 127.0.0.1 и свободном порту.
Сервер выдаёт заранее заданные ответы, затем освобождается через await using.
Он нужен только для тестов и не является шаблоном production HTTP-сервера.

Проверяются 503→200 и ровно два GET, 404 без повтора, POST без повтора при 503,
слишком большое тело с Content-Length и без него, неверный тип содержимого,
redirect, задержка тела после заголовков и пользовательская отмена.
Отдельная проверка CLI использует локальный HTTP-сервер Python.

```powershell
python tools/verify_integration.py
```

Тесты не обращаются к публичному сервису; интернет нужен первому restore пакетов.
Чтение JSON и изменение checkpoint проверяются отдельно от транспорта, поэтому сетевой сбой
не должен создавать частично принятые расходы.

## Слои ниже и другие протоколы

DNS разрешает имя в адреса; TCP даёт поток байтов, TLS защищает соединение и проверяет стороны
согласно настройкам. HttpClient работает поверх этих слоёв и сам управляет их деталями.
Для постоянного обмена сообщениями может понадобиться ClientWebSocket:
тогда нужно учитывать фрагментацию сообщений, закрытие и ограничения размера.
Socket/TcpClient нужны при собственном протоколе, где приложение само задаёт framing и границы сообщений.
Ни одна операция Receive не обязана вернуть «ровно одно сообщение приложения».

## Практика

**28-A.** Получите версию 1 JSON с локального сервера через ResponseHeadersRead.
Критерий: response и поток освобождаются, слишком большое тело отвергается даже без Content-Length.

**28-B.** Настройте сервер сначала на 503, потом на 200; отдельно на постоянный 404.
Ожидаются две и одна попытка соответственно. Критерий: счётчик запросов проверяется сервером,
а не выводом клиента; повреждённый JSON после 200 не повторяется автоматически.

**28-C.** Задержите тело после заголовков и отмените запрос token; затем повторите опыт с deadline.
Ожидаются различимые отмена и timeout, checkpoint остаётся прежним.
Критерий: тест завершает сервер и освобождает соединения; POST при 503 не повторяется.
