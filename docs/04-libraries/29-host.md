# 29. Host, DI, настройки и журналы

**Результат:** вы собираете импортёр из зависимостей, проверяете конфигурацию при старте
и завершаете его с освобождением ресурсов. Нужны главы 11, 18, 20 и 27–28.
Точка сборки приложения — [ImportCli/Program.cs](../../examples/Integration/ImportCli/Program.cs).

## Где создаются объекты

В L02 LedgerService получал IExpenseStore через конструктор. Это уже dependency injection:
сервис использует предоставленную зависимость, а не создаёт её сам.
Контейнер DI автоматизирует создание графа объектов, но не заменяет проектирование интерфейсов.

Generic Host объединяет контейнер, конфигурацию, журналирование и управление жизнью приложения.
Build создаёт host, StartAsync запускает его службы, StopAsync запрашивает корректное завершение.
Dispose освобождает принадлежащие host ресурсы.
Для долгоживущей службы удобен RunAsync; наш CLI выполняет одну операцию между Start и Stop.
[Generic Host](https://learn.microsoft.com/en-us/dotnet/core/extensions/generic-host).

Composition root — место регистрации зависимостей. Бизнес-правила не должны обращаться
к IServiceProvider за произвольным сервисом: конструктор лучше показывает потребности объекта.
В текущем решении Core не зависит ни от Host, ни от Serilog, ни от HTTP.

## Три времени жизни

| Регистрация | Когда создаётся экземпляр | Типичная ошибка |
| --- | --- | --- |
| Transient | При каждом разрешении | Считать, что все потребители разделяют одно состояние |
| Scoped | Один в пределах scope | Получить из root provider и удерживать до конца приложения |
| Singleton | Один для контейнера | Захватить scoped-зависимость или изменяемое состояние без синхронизации |

Singleton, который держит scoped-сервис, создаёт captive dependency.
Например, объект обработки одной операции начинает жить весь срок приложения.
ValidateScopes и ValidateOnBuild помогают обнаружить такие ошибки, но не доказывают
потокобезопасность и корректность всех фабрик.

Контейнер освобождает созданные им disposable-объекты согласно scope.
Не вызывайте Dispose чужой внедрённой зависимости ради «очистки после метода».
Экземпляр, созданный вручную и переданный в контейнер, имеет отдельный договор владения.
[Рекомендации DI](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/guidelines).

```csharp
// Фрагмент регистрации и выполнения в ImportCli.
builder.Services.AddSingleton(TimeProvider.System);
builder.Services.AddImportHttp();
builder.Services.AddScoped<ImportRunner>();

using var scope = host.Services.CreateScope();
var runner = scope.ServiceProvider.GetRequiredService<ImportRunner>();
```

Scope относится к одному запуску импорта. В BackgroundService, зарегистрированном как singleton,
создавайте scope на операцию через IServiceScopeFactory, а не внедряйте scoped Runner напрямую.
Подробный фоновый конвейер появится в L04.

## Настройки как проверяемый контракт

Host по умолчанию объединяет источники конфигурации. Более поздний источник может переопределить
ключ предыдущего. В образце ContentRootPath равен AppContext.BaseDirectory:
appsettings.json ищется рядом с собранным приложением и копируется туда при build.

Дополнительно подключён префикс CS_IMPORT_. Переменная
`CS_IMPORT_Import__MaxBytes` переопределяет `Import:MaxBytes`;
двойное подчёркивание задаёт вложенность. Аргументы CLI разбирает System.CommandLine,
они не передаются повторно в Host как произвольные настройки.

```csharp
builder.Services.AddOptions<ImportSettings>()
    .Bind(builder.Configuration.GetSection("Import"))
    .Validate(settings => settings.IsValid(), "Invalid import limits.")
    .ValidateOnStart();
```

Проверяются MaxBytes от 128 до 16 MiB, MaxRecords от 1 до 100000,
TimeoutSeconds от 1 до 120. Неверное значение приводит к отказу старта до чтения входа.
Значение по умолчанию не должно молча исправлять отрицательный пользовательский лимит.
[Options pattern](https://learn.microsoft.com/en-us/dotnet/core/extensions/options).

IOptions представляет настройки для обычного получения значения;
IOptionsSnapshot рассчитан на scope, IOptionsMonitor — на наблюдение обновлений.
Перезагрузка не делает изменение всех настроек одной транзакцией.
Для одного запуска импортёра подходит стабильная конфигурация, а не меняющийся в середине batch лимит.

## Секреты и окружение

User secrets предназначены для локальной разработки, хранятся вне репозитория и не являются
шифрованным production-хранилищем. Инициализируйте их в собственной копии проекта, когда появится
секретный параметр, и подключайте только нужному окружению.
В текущем импортёре секретов нет; не добавляйте фиктивные токены в appsettings.

Переменные среды тоже могут быть доступны процессам и инструментам диагностики.
Выбирайте production secret store по среде развёртывания, передавайте минимально необходимые значения
и исключайте их из журналов. Конфигурация описывает параметры, а не должна содержать произвольный исполняемый код.

## Структурированные журналы

```csharp
logger.LogInformation(
    "Import finished: {Added} added, {Failed} rejected",
    report.Added, report.Failed);
```

Added и Failed остаются именованными полями. При интерполяции строки значения заранее смешиваются
с текстом, и провайдеру сложнее искать события по полям.
Используйте устойчивые шаблоны, уровни и EventId там, где это помогает сопровождению.

BeginScope добавляет контекст batch. Serilog.Extensions.Hosting подключает Serilog к ILogger,
а Serilog.Sinks.Console направляет диагностические события в stderr.
В stdout остаётся машинный JSON-отчёт либо явно выбранная таблица.
В примере нет логирования содержимого входных записей, тела HTTP-ответа или полного URL.

Enrich.FromLogContext переносит свойства scope в событие; outputTemplate определяет,
что видно в консоли. В журнале выводится BatchId, чтобы различать операции.
Более сложные sinks и централизованное хранение рассматриваются позже.
[Serilog с Host](https://github.com/serilog/serilog-extensions-hosting).

## Старт, завершение и границы проверки

Команда создаёт host, проверяет Options, связывает token команды с ApplicationStopping,
создаёт scope и выполняет Runner. В finally вызывается StopAsync с отдельным сроком 5 секунд:
уже отменённый рабочий token не должен немедленно отменять саму очистку.

Если источник ещё читается, отмена препятствует изменению checkpoint.
Если файл уже заменён, корректное восстановление — повторный запуск с дедупликацией.
Файл состояния не является транзакцией вместе с выводом в терминал.

IntegrationChecks проверяет время жизни объектов DI и отказ при captive dependency.
CLI-проверки передают неверные и корректные значения через environment.
Логи и коды завершения проверяются отдельно от бизнес-расчёта.
Установка как Windows Service/systemd unit относится к разделу поставки; текущий пример — консольный Host.

```powershell
python tools/verify_integration.py
```

## Практика

**29-A.** Зарегистрируйте три счётчика экземпляров: transient, scoped, singleton.
Разрешите их дважды внутри scope и затем во втором scope.
Критерий: transient различаются, scoped совпадает только внутри scope, singleton общий.

**29-B.** Переопределите MaxBytes через CS_IMPORT_Import__MaxBytes.
Для 0 и abc ожидается код 2 до изменения checkpoint; для допустимого числа загрузка работает.
Критерий: appsettings остаётся неизменным, тест восстанавливает окружение после себя.

**29-C.** Перенесите запуск в собственную службу IHostedService с одной операцией импорта.
Критерий: scoped-сервис создаётся внутри scope, остановка передаёт отмену, диагностические
события имеют общий BatchId, ресурсы освобождаются при исключении.
Запуск службы ОС и параллельная обработка пока не требуются.
