# 30. Практикум утилиты импорта

**Результат:** вы поставляете CLI, которая читает файл или HTTP, принимает правильные записи,
сохраняет checkpoint и повторяется без дублирования данных. Нужны главы 19–29 и L02.
Полный договор — [лабораторная L03](../../labs/03-import-tool/README.md).

## Сборка уже изученных частей

```text
System.CommandLine → Generic Host → ImportRunner
                                      ├→ InputFormats → ExpenseLedger.Core
                                      ├→ ImportHttpClient → HttpClient/resilience
                                      └→ checkpoint + export
```

Core по-прежнему отвечает за Money/Expense. InputFormats переводит внешнее представление в DTO,
а затем в доменную модель. ImportEngine принимает решения над данными в памяти.
Runner координирует I/O и владение ресурсами. Program связывает команды, DI и код завершения.

В готовом примере импортируется JSON версии 1. CSV, XML и ZIP изучены в главе 27
и остаются упражнениями на расширение; их поддержка в CLI не заявляется.

## Аргументы как публичный интерфейс

System.CommandLine 2.0.13 разбирает команды import/export, опции, обязательные аргументы и --help.
У import должен быть ровно один источник: --file или --url.
--state задаёт checkpoint, --pretty включает человекочитаемую таблицу.
У export обязательны --state и --output.

```csharp
// Упрощённый фрагмент регистрации, типы System.CommandLine.
var state = new Option<string>("--state")
{
    Required = true,
    Description = "Checkpoint and accepted records"
};
var import = new Command("import") { state };
```

SetAction получает ParseResult и token; GetValue читает типизированную опцию.
Дополнительное правило «ровно один источник» проверяется до чтения данных.
Не пишите второй самостоятельный парсер args для тех же аргументов.
API стабильной версии отличается от старых beta-примеров с SetHandler:
ориентируйтесь на закреплённый пакет и работающий Program.
[System.CommandLine](https://learn.microsoft.com/en-us/dotnet/standard/commandline/).

## Частичный успех и приоритет ошибок

Сначала проверяется весь документ: лимит байтов, JSON-схема, версия и число записей.
Структурная ошибка завершает операцию без изменения checkpoint.
Затем записи идут по порядку; неправильная получает код и позицию в errors.

Для корректного Expense:

1. Новый Id добавляется в план.
2. Уже известный Id с теми же нормализованными полями считается duplicate.
3. Такой же Id с другими полями даёт id_conflict; прежняя запись сохраняется.

Следовательно, повторное появление Id внутри одного файла учитывается так же,
как Id из прежнего checkpoint. Проверка поля предшествует дедупликации:
ошибочная запись не становится «хорошим дубликатом» только из-за совпавшего Id.

## Checkpoint — подтверждённое состояние

Checkpoint содержит принятую модель, а его Id одновременно служат историей дедупликации.
Так не приходится синхронизировать два файла «данные» и «обработанные идентификаторы».
Перед загрузкой состояния Runner берёт эксклюзивную блокировку state.json.lock
и держит её до завершения фиксации. Конкурирующий запуск завершается ошибкой I/O.
Пустой lock-файл остаётся на диске намеренно: важен открытый handle, а не само существование файла.

Изменения сначала вычисляются в памяти. Если превышен лимит итогового состояния,
ничего не сохраняется. При наличии новых записей создаётся временный файл и заменяется checkpoint.
Если добавлений нет, состояние не переписывается. Это делает повторный запуск проверяемым даже по байтам.

Ошибка записи не должна печатать отчёт об успешной фиксации.
Сбой после замены и до печати отчёта возможен: при повторном запуске принятые Id станут duplicates.
Это восстанавливаемый договор, а не обещание exactly-once исполнения всех побочных эффектов.
В L05 файл будет заменён хранилищем с транзакциями.

## Запуск на готовых данных

Команды выполняются из корня репозитория. work предназначен для ваших результатов.

```powershell
$importArgs = @("import", "--file", "labs/03-import-tool/data/mixed.json",
    "--state", "work/l03/state.json")
dotnet run --project examples/Integration/ImportCli -- @importArgs
$exportArgs = @("export", "--state", "work/l03/state.json",
    "--output", "work/l03/export.json")
dotnet run --project examples/Integration/ImportCli -- @exportArgs
```

Первый запуск на отсутствующем state добавляет две записи, находит один duplicate
и три ошибочные записи. Код завершения 4 означает частичный успех, а не повреждение checkpoint.
Повтор той же команды добавляет 0, находит 3 duplicates и снова сообщает те же три ошибки:
неправильные записи не считаются обработанными успешно.

```json
{
  "added": 2,
  "duplicates": 1,
  "failed": 3,
  "total": 2,
  "errors": [
    {"record": 4, "code": "invalid_date"},
    {"record": 5, "code": "invalid_amount"},
    {"record": 6, "code": "id_conflict"}
  ]
}
```

JSON в stdout может быть записан одной строкой; сравнивайте структуру, а не отступы.
Сообщения ILogger/Serilog идут в stderr. Export проверяет checkpoint и создаёт
такой же формат версии 1, пригодный для нового импорта.

## UI не должен менять договор импорта

--pretty использует Spectre.Console 0.57.2 для таблицы счётчиков.
Коды завершения, записи состояния и решение об ошибках остаются прежними.
Для внешнего текста используется Text, а не интерпретация строки как markup.
Машинные сценарии должны выбирать обычный JSON-вывод.
[Spectre.Console Table](https://spectreconsole.net/widgets/table/).

Пока CLI обрабатывает один ограниченный документ в памяти.
Нет SQL, авторизации, daemon-режима, расписания и параллельной обработки.
Это осознанная граница L03; последующие работы добавят именно эти ответственности.

## Практика

**30-A.** Запустите mixed.json дважды в собственной папке.
Ожидаются счётчики 2/1/3/2 и 0/3/3/2, а checkpoint между запусками одинаков по байтам.
Критерий: сохранены коды завершения и объяснены все шесть решений по записям.

**30-B.** Реализуйте весь договор L03 в собственных проектах и экспортируйте состояние.
Критерий: импорт экспорта не добавляет дубликатов; повреждённый checkpoint не перезаписывается;
stdout остаётся пригодным для JSON-парсера даже при включённом журналировании.

**30-C.** Добавьте --dry-run с отчётом о предполагаемых изменениях.
Для mixed.json ожидаются обычные счётчики, но ни новый, ни существующий checkpoint не изменяется.
Критерий: сетевые и форматные ошибки сохраняют классификацию, повтор dry-run воспроизводим,
обычный импорт по-прежнему проходит прежние проверки. Готовый CLI эту опцию не реализует.
