# 27. Файлы, потоки и сериализация

**Результат:** вы читаете ограниченный вход, отделяете формат от модели и сохраняете прежний файл
при ошибке до замены. Нужны главы 09, 20–23 и 26.
Код — [InputFormats](../../examples/Integration/InputFormats/Documents.cs).

## Stream описывает байты

File и Directory предоставляют операции с файлами и каталогами, Path — операции над путями.
Stream представляет последовательность байтов; источником могут быть файл, память, сеть или архив.
Не всякий Stream поддерживает Seek, Length и повторное чтение.
Проверьте CanRead/CanSeek, когда алгоритм действительно требует этих возможностей.

Read может вернуть меньше запрошенного количества, хотя данные ещё не закончились.
Ноль означает конец потока. Для фиксированного заголовка полезен ReadExactly;
для неизвестного размера нужен цикл с контролем общего объёма.
Буферизация уменьшает количество обращений к источнику, но FileStream и StreamReader уже имеют
свои механизмы. Дополнительный BufferedStream не гарантирует ускорение.
[Файлы и потоки](https://learn.microsoft.com/en-us/dotnet/standard/io/).

Path.Combine не создаёт каталог, не проверяет разрешения и не защищает от выхода за разрешённую папку.
Внешний абсолютный компонент может изменить результат комбинации.
В L03 пути задаёт пользователь CLI; загрузки в серверный каталог потребуют отдельного
договора имён, проверки пути и учёта символических ссылок.

## Небольшой мост к async

Сетевые и современные потоковые API часто возвращают Task или ValueTask.
Это представление операции, которая может ещё выполняться; await получает её результат,
а при сбое распространяет исключение. async позволяет использовать await внутри метода.
Само слово async не создаёт отдельный поток.

CancellationToken передаёт запрос отмены. Операция должна наблюдать token; отмена не откатывает
уже выполненную запись. await using ожидает DisposeAsync, когда ресурс поддерживает такой протокол.
В этом блоке используем последовательные await без параллельного конвейера.
Подробная модель выполнения, контексты и композиция задач — в главе 31.

```csharp
// Фрагмент BoundedFiles.ReadPathAsync.
await using var stream = new FileStream(
    path, FileMode.Open, FileAccess.Read, FileShare.Read,
    8192, FileOptions.Asynchronous | FileOptions.SequentialScan);
return await BoundedFiles.ReadAsync(stream, maxBytes, token);
```

ReadAsync из примера проверяет каждый прочитанный блок до добавления в MemoryStream.
Content-Length или длина файла — только предварительная подсказка: фактический счётчик остаётся нужен.
Метод возвращает byte[], поэтому вход намеренно ограничен, по умолчанию 1 MiB.
Потоковую обработку больших наборов добавим в L04. .Result и Wait в этом коде не нужны.

## Контракт JSON и проверка модели

Формат L03 содержит version и records; сумму передаём строкой с invariant-точкой:

```json
{
  "version": 1,
  "records": [
    {
      "id": "11111111-1111-4111-8111-111111111111",
      "date": "2026-01-10",
      "category": "food",
      "amount": "12.50"
    }
  ]
}
```

System.Text.Json преобразует внешний документ в DTO. Успешная десериализация ещё не доказывает,
что дата существует, Id непустой или расход положителен.
Documents.TryExpense проверяет поля, затем вызывает конструкторы Money и Expense из L02.
RawExpense хранит исходные строки, чтобы неверное значение одной записи не разрушало весь отчёт.

Уровни ошибок различаются. Сломанный JSON, неизвестная версия, повторное имя свойства,
неожиданное поле или число вместо строкового amount — ошибка структуры всего документа.
Строка amount="1.234", некорректная категория или невозможная дата — ошибка отдельной записи.
Номер ошибки — позиция в массиве records, не номер физической строки файла.
[System.Text.Json](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/overview).

## Явные настройки сериализатора

Контекст ImportJsonContext объявлен partial и помечен JsonSerializable для известных DTO.
Генератор создаёт метаданные, а код использует overload с JsonTypeInfo.
Это сокращает зависимость от runtime reflection, но само по себе не доказывает
AOT-совместимость всего приложения с Host, HTTP и сторонними пакетами.
[Source generation для JSON](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation).

Настройки примера: camelCase, чувствительность к регистру, глубина до 16, запрет неизвестных
и повторных свойств. Required на Version/Records обнаруживает отсутствие поля;
явный records=null проверяется отдельно. По умолчанию некоторые из этих ограничений мягче.
Параметр AllowDuplicateProperties доступен в выбранной .NET 10 и проверяется тестом.

MoneyJsonConverter отдельно показывает преобразование Money в строку "12.50".
Он проверяет TokenType, точность и диапазон decimal, затем создаёт значение.
Конвертер выбирается через JsonSerializerOptions.Converters; нельзя считать, что наличие класса
конвертера автоматически подключает его ко всем операциям приложения.

Для чтения отдельных полей пригодны JsonDocument/JsonElement; документ нужно освобождать,
а элемент связан с его временем жизни, если не сделан Clone.
JsonNode удобен для изменяемого дерева; Utf8JsonReader — для последовательного чтения токенов.
Выбирайте DTO, когда схема известна, и явно версионируйте изменения формата.

## XML, CSV и ZIP

LINQ to XML (XDocument/XElement) позволяет читать и собирать XML с экранированием.
Пример использует XmlReader с запрещённым DTD, без XmlResolver и с лимитом символов.
Имена с namespace сравниваются как XName; одинаковое локальное имя в разных namespace
не означает одинаковый элемент. Схему и обязательные поля проверяют отдельно.

CSV нельзя корректно читать через Split(','): внутри quoted field допустимы запятая,
удвоенная кавычка и перевод строки. CsvHelper 33.1.0 читает логические записи и учитывает quoting.
В примере закреплены InvariantCulture, разделитель, точный заголовок и число полей;
полученные строки всё равно проходят отдельную проверку предметной модели.
[CsvHelper](https://joshclose.github.io/CsvHelper/getting-started/).

ZIP сжимает байты, но не ограничивает объём после распаковки.
OtherFormats читает единственную запись report.txt, не извлекает произвольные пути на диск
и ограничивает фактически прочитанный распакованный поток.
Для общего архиватора нужны ограничения числа записей, суммарного размера и пути каждой записи.

Небезопасные десериализаторы, восстанавливающие произвольные runtime-типы, не подходят для входа извне.
BinaryFormatter не следует включать обходными настройками; современная платформа выводит его из употребления.
Используйте явный формат и допустимые DTO.
[Риски BinaryFormatter](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide).

## Замена файла и двоичный формат

Нельзя сначала стереть рабочий файл, а потом пытаться записать новый.
BoundedFiles.ReplaceAsync пишет временный файл рядом с назначением, закрывает и сбрасывает поток,
проверяет отмену, затем выполняет File.Move с overwrite.
При обычном сбое до Move прежний файл остаётся; временный удаляется в finally.

Это не общая транзакция для произвольной файловой системы и потери питания.
Две независимые записи «данные» и «checkpoint» также не становятся атомарными.
Поэтому L03 хранит и записи, и их Id в одном файле; взаимное исключение обеспечивается отдельной блокировкой.
Для строгой устойчивости и нескольких процессов далее понадобятся транзакции БД и эксплуатационные проверки.

Если проект требует двоичного протокола, задайте порядок байтов явно:
BinaryPrimitives.WriteInt32BigEndian/ReadInt32BigEndian работают с Span.
MemoryMarshal.AsBytes не определяет переносимую схему файла. Длина, версия и каждое поле
должны иметь согласованный формат и проверки границ.

```powershell
dotnet run --project examples/Integration/BclLab -c Release -- 27
python tools/verify_integration.py
```

Ожидается: food,office; tea & milk; ledger — по строке на результат CSV, XML и ZIP.
Тесты дополнительно моделируют короткие чтения и отменённую замену checkpoint.

## Практика

**27-A.** Прочитайте CSV с полем `"tea,""milk"""` и XML с текстом `tea &amp; milk`.
Ожидаются строки с буквальными кавычками и амперсандом.
Критерий: разбор выполняют библиотеки формата, а не цепочка Replace.

**27-B.** Реализуйте JSON round trip одного Expense через DTO версии 1.
Проверьте неизвестную версию, duplicate property, records=null, неверный amount и повреждённый UTF-8.
Критерий: структурные и построчные ошибки различены, правила Money не обходятся.

**27-C.** Замените существующий файл экспортом через временный файл.
Имитируйте ошибку до замены и заранее отменённый token.
Критерий: старые байты сохранены, временные файлы убраны, при успехе повторный разбор даёт те же расходы.
Отдельно назовите, какие сценарии аварии эта проверка не доказывает.
