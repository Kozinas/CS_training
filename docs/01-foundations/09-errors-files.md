# 09. Ошибки, ресурсы и первые файлы

**Результат:** вы разделяете неверные данные и сбой операции, закрываете ресурсы и читаете текстовый файл.
Нужна глава [08](08-classes.md).

## Когда возвращать результат, когда бросать исключение

Неправильная строка из пользовательского файла ожидаема: Try-метод сообщает об отказе и причине.
Вызов конструктора с нарушенным контрактом — ошибка использования API: уместно исключение.
Отказ файловой системы нельзя предсказать полной предварительной проверкой: его нужно обработать.

Исключение прерывает обычное выполнение и ищет подходящий catch по стеку вызовов.
Если подходящего обработчика нет, процесс обычно завершится с ошибкой.
Не используйте пустой catch: он превращает сбой в незаметно неверный результат.

```csharp
try
{
    string text = File.ReadAllText("expenses.txt");
    Console.WriteLine(text);
}
catch (FileNotFoundException)
{
    Console.Error.WriteLine("Файл расходов не найден.");
}
catch (UnauthorizedAccessException)
{
    Console.Error.WriteLine("Недостаточно прав для чтения файла.");
}
catch (IOException ex)
{
    Console.Error.WriteLine($"Ошибка чтения: {ex.Message}");
}
```

Более конкретный catch пишут перед общим. Сообщение полезно человеку,
но программа не должна разбирать локализованный текст Exception.Message для принятия решения.
Данные для диагностики — тип, stack trace и контекст операции.

## Повторное выбрасывание и finally

В catch запись `throw;` передаёт то же исключение выше, сохраняя исходный стек.
`throw ex;` меняет информацию о месте повторного выбрасывания и затрудняет диагностику.
Новое исключение с исходным в InnerException уместно, когда нужно выразить другой уровень абстракции.

`finally` выполняет завершающие действия при нормальном выходе и при обычном раскручивании стека.
Это не гарантия при аварийном завершении процесса или отключении питания.
Фильтр `catch (IOException ex) when (...)` принимает исключение только при истинном условии;
не включайте в фильтр побочные действия, на которые рассчитывает программа.

## Ресурс и сборщик мусора

Файл, сокет и подключение могут владеть ограниченным ресурсом ОС.
GC управляет памятью; он не обещает немедленного закрытия файлов при выходе переменной из области видимости.
`IDisposable.Dispose` выражает освобождение, а using обеспечивает вызов Dispose на выходе из блока.

```csharp
using System.Text;

using (StreamReader reader = new(
    "expenses.txt",
    new UTF8Encoding(false, true),
    detectEncodingFromByteOrderMarks: false))
{
    string? line;
    while ((line = reader.ReadLine()) is not null)
    {
        Console.WriteLine(line);
    }
}
```

Здесь UTF-8 декодер отклоняет некорректные байты. Режим с BOM требует отдельного решения;
контракт лабораторной допускает UTF-8 BOM и удаляет его явно.
Форма `using var reader = ...;` освобождает ресурс в конце текущей области видимости.
Она удобна, но большой метод может удерживать файл дольше, чем требуется.

## Рабочая директория и путь

Относительный путь считается от рабочей директории процесса, которая не обязана совпадать
с папкой исходника или исполняемого файла. Для диагностики полезен `Environment.CurrentDirectory`.
Для составления пути используйте `Path.Combine(folder, "expenses.txt")`,
для явного абсолютного представления — `Path.GetFullPath(path)`.

`File.Exists` не делает последующее чтение безопасным: между проверкой и открытием файл
может исчезнуть, права могут измениться. Обрабатывайте ошибку самой операции.
Не вставляйте произвольное пользовательское имя в доверенный путь без проверки границ:
в веб-приложениях это особенно важно.

`File.ReadAllLines` загружает все строки в память.
`File.ReadLines` перечисляет лениво: ошибка может возникнуть во время foreach, поэтому
try должен охватывать перечисление, а не только создание последовательности.

## Коды завершения

Обычный результат пишут в stdout, диагностику — в stderr.
В top-level программе `return 0;` сообщает успех, `return 1;` — ошибку по договору приложения.
Разным категориям ошибок можно назначить разные коды. Это позволяет автоматизации
понять результат, не разбирая текст сообщения.

Не печатайте итоговый успешный отчёт после частичной ошибки, если контракт требует
обработать файл целиком. Сначала прочитайте и проверьте данные, затем формируйте результат.

## Практика

**09-A.** Создайте UTF-8 файл из трёх строк, прочитайте его using+StreamReader.
Критерий: ровно три строки в исходном порядке; после выхода из using файл можно снова открыть.

**09-B.** Напишите утилиту подсчёта непустых строк. Контракт: путь — один аргумент,
успех → число в stdout и код 0; ошибка аргументов → stderr и код 2;
ошибка чтения → stderr и код 3. Критерии: пустой файл → 0,
файл `a/пустая строка/b` → 2, отсутствующий файл → код 3 без результата в stdout.

**09-C.** Добавьте strict UTF-8 и приём файла с неверным байтом. Он должен завершаться
диагностикой декодирования, не подменяя байт символом замены.
Продемонстрируйте освобождение ресурса при исключении внутри блока чтения.
Критерий: повторное открытие файла после catch возможно.
