# 57. Публикация и CI/CD

**Результат:** вы собираете проверяемый дистрибутив, запускаете опубликованные API и UI,
отделяете конфигурацию/данные от бинарных файлов и планируете откат. Нужны главы 38, 43, 49–51 и 55.
Практический договор — [L07](../../labs/07-client-release/README.md), инструмент — [package_release.py](../../tools/package_release.py).

## Build, publish и deploy

Build проверяет и компилирует проект. Publish формирует набор файлов для исполнения с выбранными
runtime, архитектурой и оптимизациями. Deploy размещает этот набор в окружении и переключает на него
пользовательскую работу. Успешный build не доказывает наличие wwwroot, native DLL, сертификатов и схемы БД
в опубликованном приложении. Проверять следует тот артефакт, который вы собираетесь передавать.
[Публикация .NET](https://learn.microsoft.com/en-us/dotnet/core/deploying/).

| Вариант | Что находится в поставке | Что требуется от окружения |
| --- | --- | --- |
| Framework-dependent | Приложение и его зависимости | Совместимый .NET/ASP.NET Core runtime |
| Self-contained | Приложение и выбранный runtime | Подходящие ОС, архитектура и системные библиотеки |
| Single-file | Упаковка приложения в bundle | Требования зависят от FDD/SC и native-зависимостей |
| Trimmed | Удалена часть недостижимого кода | Проверенная совместимость используемых API с trimming |
| Native AOT | Заранее собранный native executable | Целевая ОС/ABI и native-зависимости |

Это не пять взаимоисключающих флагов: single-file можно сочетать с self-contained и trimming.
Self-contained включает runtime, но не делает приложение независимым от ОС и системных библиотек.
Его runtime нужно обновлять новым выпуском самого приложения. Single-file не является обещанием
«на диске всегда ровно один файл»: символы, native-библиотеки и внешняя конфигурация имеют свои правила.
[Single-file](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview).

## RID и совместимость

RID вроде win-x64 или linux-x64 описывает целевую платформу. Native-зависимость выбирается под её ABI.
Смена RID не переносит WPF на Linux и не решает различия glibc/musl. TargetFramework описывает API .NET,
RuntimeIdentifier — другую ось. Выбор C# 14 тоже не обещает наличие любого native-компонента на ARM64.
[Каталог RID](https://learn.microsoft.com/en-us/dotnet/core/rid-catalog).

В InteropProbe закреплён win-x64: упражнение использует Win32. Проверка выпуска выполняет три публикации
с одними входами: FDD, self-contained/single-file/trimmed и Native AOT. Во всех случаях читается файл
с Unicode-именем, закрывается handle и проверяется native-ошибка отсутствующего файла.
Размеры записываются в publication.json; меньший exe не доказывает большую скорость во всех сценариях.

После restore решения пример AOT можно опубликовать вручную:

```text
dotnet publish examples/Delivery/InteropProbe -c Release -r win-x64 --self-contained true -o .artifacts/manual-aot
.artifacts/manual-aot/InteropProbe.exe size README.md
```

Для повторяемой проверки используйте verify_delivery.py: он согласует lock-файлы, параметры и временные
каталоги. AOT требует C++ toolchain; warnings IL2xxx/IL3xxx — сигнал проверить reflection/dynamic code.
Проверка только JIT-пути не заменяет запуск AOT executable. Пустой DOTNET_ROOT в тесте для SC/AOT —
полезная проверка независимости от этого пути, но не полноценная чистая виртуальная машина.

## Дистрибутив L07: API и выбранный клиент

Мы продолжаем L06 и выбираем Blazor из главы 51. Script package_release.py публикует два настоящих
проекта в новую папку, добавляет release.json с версией и SHA-256 каждого файла. Существующий каталог
не перезаписывается. Версии 1.0.0 и 1.1.0 в упражнении имеют одинаковый договор и схему; номер меняет
metadata сборки, позволяя проверить замену артефакта без отдельной миграции БД.

```text
python tools/package_release.py create 1.0.0 .artifacts/releases/1.0.0
python tools/package_release.py verify .artifacts/releases/1.0.0
```

Проверка отвергает другой hash, лишний файл, отсутствующий файл и попытку выхода пути из каталога.
Manifest нужен для целостности и идентификации. Он не является цифровой подписью: атакующий, который
может заменить и файлы, и manifest, способен пересчитать SHA-256. Для доверенной поставки нужен
защищённый канал, provenance/подпись и управление доступом к артефактам.

В выпуске лежат api и ui, а SQLite, Data Protection keys и журналы находятся отдельно.
После запуска проверяются неизменность файлов релиза, health, HTTP-отчёт и опубликованный Blazor asset.
Если обычный запуск с рабочим каталогом проекта работал, а publish потерял static files, такая проверка
это обнаружит. UI-компоненты проверены ранее через bUnit; опубликованный browser e2e остаётся отдельным уровнем.

## Конфигурация, секреты и права

Передавайте параметры окружения без пересборки: путь БД, API endpoint, log level, порты.
В .NET разделитель `__` в имени переменной соответствует вложенному ключу, например Ledger__Path.
Определите приоритет источников и проверяйте обязательные параметры при старте. Неверная конфигурация
должна давать диагностируемый отказ, а не незаметный переход на production-адрес по умолчанию.

Секреты не входят в release.json, source control, Docker ARG/слои и открытые журналы.
User Secrets — удобство локальной разработки, не production-хранилище. Для эксплуатации выбирайте
secret store окружения и минимальные права процесса. Data Protection keys нужны для чтения выданных
Identity-токенов/данных; backup расходов не заменяет продуманный lifecycle этих ключей.

Учебный процесс работает на loopback с Web__AllowHttp=true. Публичная поставка требует HTTPS,
доверенного сертификата, правильного proxy forwarding и ограничения доступа. Эти настройки не
создаются скриптом курса автоматически. Нельзя объяснять ошибку TLS предложением отключить проверку сертификата.

## CI и CD — разные обязанности

CI в репозитории запускается GitHub Actions на GitHub-hosted windows-latest. Это временный runner
GitHub, а не self-hosted агент на компьютере автора или учащегося. Job восстанавливает версии,
собирает проекты, выполняет проверки, пересобирает PDF и сохраняет отчёты. Скрипты также можно
запустить локально, но локальный запуск не называется удалённым CI.

CD означал бы доставку артефакта в выбранное окружение с его секретами, миграциями, health gates и
процедурой переключения/отката. В этом репозитории публичный CD не настроен; L07 моделирует поставку
локально. Для реальной системы старайтесь переносить уже проверенный артефакт между средами,
а не пересобирать разные бинарные файлы из того же тега на каждом шаге.
[Workflow курса](../../.github/workflows/verify.yml),
[GitHub-hosted runners](https://docs.github.com/en/actions/using-github-hosted-runners/about-github-hosted-runners).

## Контейнер: образ, процесс, данные

В [Dockerfile](../../examples/Delivery/Dockerfile) две стадии: SDK собирает, runtime-образ запускает
опубликованный API под непривилегированным пользователем. В build context не должны попадать Books,
секреты, .git, bin/obj и личные work; рядом лежит Dockerfile.dockerignore.
Для воспроизводимого релиза закрепляют image digest, проверяют его поддержку и обновляют осознанно.
[Контейнеризация .NET](https://learn.microsoft.com/en-us/dotnet/core/docker/build-container).

Контейнер не хранит долговечные данные автоматически. Нужен volume с правильными правами для SQLite
и отдельно ключи/backup. Миграция выполняется отдельным шагом до readiness; её нельзя запускать без
координации в каждом replica. Наш Dockerfile — дополнительное упражнение Linux: контейнер не запускался
в обязательной проверке и не заменяет проверку libc, файловых прав, сигналов и TLS-прокси.

## Миграции и rollback

Rollback приложения и rollback данных — разные действия. Если новая версия удалила колонку, возврат
старой DLL может не восстановить работоспособность. Подход expand/contract сначала добавляет совместимые
элементы, переводит чтение/запись и только позже удаляет старое. Нужны совместимость соседних версий,
план backfill, оценка блокировок и поведение при частичном шаге.

В L07 обе версии читают L06-InitialWeb. Перед переключением выполняются manifest check, отдельная
миграция и readiness. Затем проверяются прежний access token, отчёт и повтор receipt. Откат на 1.0.0
использует ту же внешнюю БД. Это доказательство same-schema rollback; оно не подтверждает откат
произвольной разрушительной миграции.

Типичные ошибки: хранить БД внутри каталога релиза; выдавать отсутствие предупреждений build за AOT-проверку;
использовать mutable latest-tag как идентификатор артефакта; перезапускать все узлы из-за необязательной
внешней зависимости; считать контейнер или checksum готовой защитой секрета.

**57-A.** Вход: один 256-байтный файл и три публикации InteropProbe. Ожидается одинаковый JSON во всех.
Критерий: сравнены состав/размеры артефактов, указаны runtime и ABI, запуск выполнен из publish-папки.

**57-B.** Соберите релиз API/UI и измените копию одного опубликованного файла. Ожидается отказ verify;
после восстановления — успех и работа health/UI asset. Критерий: данные и ключи вне релиза,
источник версии известен, checksum не назван цифровой подписью.

**57-C.** Выполните L07, затем выберите чистую VM либо Linux-контейнер как дополнительную цель.
Вход: готовый артефакт, внешние настройки, пустая БД и предыдущая версия. Критерий: другой человек
воспроизводит установку/обновление/откат, схема совместима, ключи не опубликованы; факт проверки целевой
системы подтверждён отдельно от локальной сборки. [Подсказки](../appendices/hints.md).
