# 19. Сборки и модель исполнения

**Результат:** вы объясняете путь исходника до выполнения и находите сборку, тип и IL метода.
Нужны главы 11–18. Полный пример — [RuntimeLab](../../examples/RuntimeLab/RuntimeExamples.cs).

## Что получается после build

Компилятор разбирает C#, связывает имена с типами и проверяет правила языка.
Обычная сборка .NET содержит IL — инструкции для CLR — и метаданные: имена типов,
сигнатуры, ссылки на другие сборки, атрибуты. Файл использует формат PE, в том числе на Linux.
Расширение DLL само по себе не говорит, является ли библиотека управляемой.

Assembly — единица поставки и идентичности; namespace — способ группировать имена в исходниках.
Два проекта могут объявлять типы в одном namespace. Полное имя типа ещё не задаёт его идентичность:
важны сборка и контекст загрузки. Module — часть структуры сборки; обычный SDK-проект создаёт один модуль.
Исторические multi-module сборки .NET Framework не нужны для разделения нашего решения:
для этого уже есть проекты Core и Memory. [Устройство сборок](https://learn.microsoft.com/en-us/dotnet/standard/assembly/).

В каталоге Release найдите следующие файлы:

| Файл | Для чего нужен |
| --- | --- |
| RuntimeLab.dll | Управляемая сборка с точкой входа и типами |
| RuntimeLab.exe на Windows | Apphost, запускающий приложение |
| RuntimeLab.runtimeconfig.json | Требования и настройки runtime |
| RuntimeLab.deps.json | Описание зависимостей |
| RuntimeLab.pdb | Символы для связи выполнения с исходниками |

Не переименовывайте DLL зависимостей как способ исправить загрузку: ссылка содержит идентичность,
а приложение имеет собственные правила разрешения зависимостей.

## Общая система типов

CTS задаёт общие правила типов CLR, поэтому библиотеку C# можно вызывать из F#.
CLS — более узкий набор правил для публичного API, удобного разным .NET-языкам.
Например, публичный контракт на unsigned-типах не всегда CLS-совместим.
В библиотеке можно включить проверку атрибутом сборки; это не означает, что все детали реализации
обязаны укладываться в CLS.

```csharp
// Фрагмент отдельной библиотеки, до объявлений namespace/type.
[assembly: CLSCompliant(true)]
```

`internal` ограничивает обычный доступ текущей сборкой. Другой проект не становится «своим»
от совпадения namespace. Для тестов иногда объявляют friend assembly:

```csharp
[assembly: System.Runtime.CompilerServices.InternalsVisibleTo("MyLibrary.Tests")]
```

Имя относится к сборке, а не каталогу. Для strong-named сборок нужны дополнительные правила ключей.
Friend-доступ открывает все internal-члены указанной сборке; это не механизм изоляции недоверенного кода.
Сначала предпочитайте проверки публичного контракта, как в L02.

## От IL к машинному коду

```text
.cs → компилятор C# → IL + metadata → загрузка CLR → JIT → код процессора
```

JIT компилирует нужные методы во время выполнения. Tiered compilation может сначала создать быстрый
в компиляции вариант, затем заменить его оптимизированным. Поэтому «первый вызов» и steady state
имеют разную стоимость. Оптимизатор вправе встроить метод и убрать отдельный вызов.

ReadyToRun добавляет заранее скомпилированный код для ускорения старта, но сохраняет роль JIT.
Native AOT компилирует приложение при publish под конкретную ОС и архитектуру; JIT при запуске нет.
Это меняет допустимость генерации кода и динамической загрузки, а не синтаксис арифметики.
Полная AOT-публикация требует платформенного toolchain и отдельной проверки приложения.
Текущие примеры собраны как обычные JIT-приложения.
[Ограничения Native AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/).

## Наблюдаемый пример

```powershell
dotnet run --project examples/RuntimeLab -c Release -- 19
dotnet run --project examples/RuntimeLab -c Release -- 19-il
```

Первая команда выводит `RuntimeLab`, `42`, `True`, `7`, `7`, `1` на отдельных строках.
Последняя единица — число выполнений статического конструктора Initialized.
Вторая команда печатает IL метода Twice и результат его вызова:

```csharp
[System.Runtime.CompilerServices.MethodImpl(
    System.Runtime.CompilerServices.MethodImplOptions.NoInlining)]
public static int Twice(int value) => value * 2;
```

На проверенном SDK Release-байты — `02 18 5A 2A`:
`ldarg.0` кладёт аргумент на вычислительный стек IL, `ldc.i4.2` кладёт 2,
`mul` снимает операнды и кладёт произведение, `ret` возвращает результат.
Вычислительный стек IL — модель инструкций, а не обещание конкретного расположения в памяти процессора.
Debug-сборка может содержать дополнительные инструкции.

Посмотреть JIT-код можно в отдельном PowerShell-процессе; настройки действуют только до его закрытия:

```powershell
$env:DOTNET_JitDisasm = "Course.RuntimeLab.RuntimeExamples:Twice"
$env:DOTNET_TieredCompilation = "0"
dotnet examples/RuntimeLab/bin/Release/net10.0/RuntimeLab.dll 19
```

Найдите удвоение аргумента и возврат. Конкретные регистры и инструкции зависят от архитектуры и runtime;
в отчёт задачи запишите свою среду. Это диагностический режим, не настройка приложения для production.

## Статическая инициализация и версии

Явный статический конструктор выполняется CLR однократно для данного типа; для разных закрытых
generic-типов статическое состояние раздельно. Инициализаторы полей работают до его тела.
Не стройте взаимозависимые циклы и не выполняйте блокирующие ожидания в таком конструкторе.
Ошибка инициализации обычно проявляется через TypeInitializationException, а повторный доступ
не является механизмом повторной попытки. Без явного конструктора runtime имеет больше свободы
в выборе момента инициализации (beforefieldinit).
[Статические конструкторы](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/static-constructors).

Различайте AssemblyVersion (идентичность), FileVersion (версию файла) и InformationalVersion
(описание выпуска, часто с commit id). Номер NuGet-пакета — ещё одна величина.
Смена версии не чинит удалённый публичный метод: двоичная совместимость требует сохранить контракт.
В современной .NET зависимостями управляют приложение и контексты загрузки;
правила GAC и binding redirects из книг о .NET Framework нельзя переносить автоматически.

## Практика

**19-A.** Для RuntimeLab и ExpenseLedger.Core выпишите AssemblyName, namespace одного типа,
имя модуля и наличие точки входа. Ожидается: у библиотеки нет Main, совпадение namespace не требуется.
Критерий: сведения получены через Type/Assembly, а не угаданы по папке.

**19-B.** Замените умножение в своей копии Twice на сложение двух аргументов.
Для входа 21 получите 42, сопоставьте исходник, IL и JIT-код. Критерий: в отчёте есть
Release-команда, версия SDK и объяснение различия IL и машинных инструкций.

**19-C.** Создайте библиотеку с public и internal методами и отдельный клиент.
Вызов internal должен дать ошибку доступа; затем добавьте точное имя friend assembly и повторите.
Критерий: объяснено, почему одинаковый namespace не помог и почему это не граница безопасности.
