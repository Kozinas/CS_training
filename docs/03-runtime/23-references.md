# 23. Ссылки, span и unsafe

**Результат:** вы используете диапазон памяти без лишних копий, соблюдаете время жизни
и сравниваете два парсера по одному контракту. Нужны главы 05, 12–13, 19–20.
Исходники — [PairParser](../../examples/RuntimeLab/PairParser.cs) и
[RuntimeExamples](../../examples/RuntimeLab/RuntimeExamples.cs).

## Значение и ссылка на ячейку

Обычное присваивание int копирует значение. Ref local становится ещё одним именем той же ячейки.
Ref return возвращает доступ к хранилищу вызывающего кода, а не копию результата.

```csharp
int[] numbers = [2, 3];
ref int first = ref RuntimeExamples.FirstRef(numbers);
first = 8;
Console.WriteLine(numbers[0]); // 8
```

Метод FirstRef возвращает `ref values[0]`. Для пустого диапазона обращение недопустимо.
`ref readonly` позволяет читать через ссылку, не записывая через неё;
это не делает исходный массив неизменяемым. `in` передаёт readonly-ссылку на аргумент,
но может потребовать временное значение или защитную копию при вызове изменяющего члена структуры.
Не считайте in автоматическим ускорением маленьких значений.

`scoped` ограничивает возможность выхода ссылки/значения за текущую область допустимого времени жизни.
В `Sum(scoped ReadOnlySpan<int> values)` метод получает данные на время вызова и возвращает число.
Компилятор проверяет escape rules: нельзя вернуть span на локальный stackalloc.
Это гарантия времени жизни ссылок в безопасном коде, а не счётчик владельцев.
[Ref locals и scoped](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/declarations).

## Span — представление, а не владелец

Span содержит ссылку на начало и длину непрерывного диапазона.
Источник может быть массивом, стековой или unmanaged-памятью.
Срез Span меняет представление без копирования элементов; ToArray создаёт отдельный массив.
ReadOnlySpan запрещает запись через это представление, но иной владелец всё ещё может менять источник.

Span — ref struct: его нельзя упаковать в object, захватить лямбдой или хранить полем обычного класса.
Memory/ReadOnlyMemory можно хранить в объекте и переносить между асинхронными операциями;
для короткой обработки берут свойство Span. Memory не продлевает аренду буфера автоматически.
С C# 13 некоторые локальные ref struct разрешены в async/итераторах, но нельзя сохранять их
через границу приостановки await/yield. Подробная async-модель будет в главе 31.
[Ограничения ref struct](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/ref-struct).

Ref struct может реализовать интерфейс, но преобразование в интерфейсную переменную потребовало бы
boxing и запрещено. В примере NumberReader передаётся generic-методу с ограничением
`where T : INumberReader, allows ref struct`: это разрешение принять ref struct и обязанность
соблюдать ограничения его времени жизни внутри метода.

## Небольшой стековый буфер и пул

```csharp
Span<int> scratch = stackalloc int[4];
scratch.Clear();
scratch[0] = 2;
scratch[3] = 5;
Console.WriteLine(RuntimeExamples.Sum(scratch)); // 7
```

Для stackalloc с Span не нужен unsafe. До чтения память надо инициализировать.
Размер стека ограничен: не выделяйте объём из непроверенного пользовательского ввода,
не размещайте stackalloc в длинном цикле. Для больших данных выбирайте массив или аренду.
[Правила stackalloc](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/stackalloc).

ArrayPool уменьшает частоту создания массивов, но вводит протокол Rent/Return.
BufferOwner из главы 20 возвращает ровно один массив, не отдаёт запасную часть аренды и запрещает
новый доступ после Dispose. Сохранённое ранее представление остаётся ответственностью потребителя.
При async-вызове аренда должна жить до завершения потребления.
[Правила владения Memory](https://learn.microsoft.com/en-us/dotnet/standard/memory-and-spans/memory-t-usage-guidelines).

## Контракт парсера важнее реализации

Формат упражнения: два неотрицательных Int32 через один `;`, только ASCII-цифры.
Знаки, пробелы, дроби, пустые поля, лишние разделители и переполнение суммы запрещены.
При ошибке возвращаются false и sum=0. Ведущие нули допустимы.

TrySumWithSplit создаёт массив строк и подстроки. TrySum работает со срезами входного ReadOnlySpan.
Оба используют одинаковую проверку числового поля; длинная сумма вычисляется в long,
после чего проверяется диапазон Int32. Нельзя заменить TryParse на Parse и молча изменить
обещание «не бросать на ошибочном тексте».

```powershell
dotnet run --project examples/RuntimeLab -c Release -- 23
dotnet run --project examples/RuntimeLab -c Release -- 23-alloc
dotnet run --project examples/RuntimeChecks -c Release
```

Первый вывод: `True`, `42`, `False`, `9`, `7`.
Эксперимент выделений сначала прогревает оба пути, затем считает байты текущего потока.
Для 10 000 входов `12;30` контрольные суммы должны быть 420000 у обоих.
В проверенной среде Split выделил 1 040 000 байт, span-вариант — 0 в измеряемом участке.
Точное число не является переносимым контрактом; это не сравнение времени и не полноценный benchmark.
Общие аллокации процесса и других потоков этим счётчиком не измеряются.

## Указатели и границы unsafe

Unsafe-контекст разрешает операции, которые CLR не может полностью проверить на безопасность.
В проекте нужен AllowUnsafeBlocks. Указатель `int*` не равен управляемой ref-ссылке:
выход за диапазон или использование после конца закрепления может повредить память.

PointerSum в примере фиксирует массив на время цикла:

```csharp
// Фрагмент unsafe-метода; values — int[], sum — int.
fixed (int* pointer = values)
{
    for (int i = 0; i < values.Length; i++)
        sum = checked(sum + pointer[i]);
}
```

Пустой массив не разыменовывается. Указатель не сохраняется после fixed.
Обычный foreach здесь проще; unsafe нужен для понимания interop, а не для улучшения этого суммирования.
`sizeof(T)` даёт размер unmanaged-представления допустимого типа; это не размер object в куче.
Unmanaged constraint исключает поля с managed-ссылками, но не гарантирует формат сетевого протокола.
[Unsafe в спецификации](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/unsafe-code).

Function pointer объявляется `delegate* managed<int, int>` либо
`delegate* unmanaged[Cdecl]<int, int>`. В отличие от делегата он не хранит захваченный объект.
Адрес метода берётся через &. Calling convention должна совпадать с вызываемой функцией.
FunctionPointerResult проверяет оба вида: обычный Twice и Triple с UnmanagedCallersOnly.
Пример не загружает стороннюю native-библиотеку; её жизненный цикл и ABI будут в главе 55.
[Указатели на функции](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/unsafe-code).

## Inline arrays и переинтерпретация

`[InlineArray(4)]` на структуре с одним полем элемента задаёт встроенное хранилище четырёх элементов.
FourNumbers из примера преобразуется в span и суммируется без отдельного массива.
Если такая структура является полем объекта, её данные находятся внутри этого объекта.
Это ещё один пример того, почему struct не означает «обязательно стек».

MemoryMarshal позволяет получить байтовое представление либо переинтерпретировать допустимые
диапазоны. Эти API не проверяют смысл протокола: остаются вопросы порядка байтов, выравнивания,
размера, времени жизни и наличия managed-ссылок. Не сериализуйте произвольную структуру
как «её байты» для хранения на годы. Для формата явно задавайте поля и endianness;
работа с BinaryPrimitives появится в главе 27.

## Практика

**23-A.** Через ref return измените первый элемент `[2,3]` на 8.
Затем получите readonly-представление и измените исходный массив.
Ожидается, что чтение представления видит изменение. Критерий: объяснена разница read-only и immutable.

**23-B.** Реализуйте оба парсера договора выше. Входы: `0;0`, `12;30`, `2147483647;0`,
`2147483647;1`, `1;2;3`, строка `"\uFF11;2"` с полноширинной цифрой 1.
Ожидаемые пары: true/0, true/42, true/2147483647, затем false/0.
Критерий: одинаковое поведение в ru-RU, en-US и tr-TR.

**23-C.** Добавьте поток обработки 10 000 строк, повторно используя арендованный буфер
для промежуточных данных. Критерий: результат равен простой реализации, аренда возвращена при
исключении, нет чтения после Return. Отдельно сравните выделения после прогрева
и запишите ограничения измерения; точное число байт не должно решать, прошёл ли тест корректности.
