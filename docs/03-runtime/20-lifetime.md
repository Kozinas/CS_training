# 20. Память и время жизни

**Результат:** вы различаете достижимость объекта и владение ресурсом, находите удерживающую ссылку,
гарантируете освобождение через using. Нужны главы 09, 12, 14 и 19.
Пример — [Lifetime.cs](../../examples/RuntimeLab/Lifetime.cs).

## Где находится значение

Тип значения определяет копирование, но не универсальное правило «struct в стеке».
Поле структуры внутри класса находится вместе с объектом; элементы массива структур находятся в массиве.
Локальная переменная может быть размещена в регистре, стеке или преобразована компилятором.
Boxing создаёт объект с копией значения. Ссылка, лежащая в локальной переменной, сама не является объектом.

Стек вызовов нужен для выполнения методов и возврата из них. Управляемая куча хранит объекты,
за достижимостью которых следит GC. Полезная для диагностики схема:

```text
живой publisher → делегат события → target подписчика → его данные
```

Подписчик может быть уже не нужен интерфейсу, но всё ещё достижим. Это managed leak:
сборщик работает правильно, а программа удерживает лишнюю ссылку.

## Что делает GC

GC проходит граф от корней: например, статических полей и живых ссылок выполняющегося кода.
Недостижимые циклы сами по себе не мешают сборке. Поколения 0, 1 и 2 позволяют чаще обрабатывать
молодые объекты; пережившие сборку могут продвигаться. Это эвристика, не расписание по таймеру.
Большие объекты обычно попадают в LOH; ориентир по умолчанию — 85 000 байт размера объекта,
а не длины строки. LOH собирается вместе с поколением 2 и обычно не уплотняется автоматически.

При перемещении объекта GC обновляет управляемые ссылки. Pinning запрещает перемещение на время
использования фиксированного адреса, но длительные закрепления могут мешать уплотнению.
Не вызывайте GC.Collect после каждого запроса: сначала измерьте удержание и выделения.
Размер рабочего набора процесса не равен объёму живых объектов.
[Основы GC](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/fundamentals).

## У ресурса должен быть владелец

GC не знает, когда приложению больше не нужен открытый файл или арендованный буфер.
IDisposable даёт явный протокол завершения. `using` вызывает Dispose на выходе,
включая return и исключение; несколько ресурсов освобождаются в обратном порядке.

Наш BufferOwner арендует массив и возвращает его в пул. Dispose не уничтожает объект в памяти:
последующий доступ к Span отклоняется ObjectDisposedException, а повторный Dispose ничего не делает.
Смысл его реализации:

```csharp
// Фрагмент BufferOwner; _buffer — byte[]?, _pool — ArrayPool<byte>.
public void Dispose()
{
    if (_buffer is null) return;
    _pool.Return(_buffer, clearArray: true);
    _buffer = null;
}
```

Rent может дать массив больше запроса. Пользователь видит Span длины Length, а не весь массив.
Данные аренды могут быть не нулевыми: инициализируйте их перед чтением. В нашем примере Fill делает это явно.
После Return нельзя пользоваться ранее полученным Span: компилятор не отслеживает договор пула.
Владелец и потребители должны договориться о времени использования.

Пример рассчитан на один поток. Идемпотентность при последовательных вызовах не означает
безопасность одновременных Dispose. Синхронизация рассматривается в главе 32.

## Отписка как освобождение

PulseObserver сохраняет publisher и подписывает свой метод OnPulse. В Dispose он снимает
именно этот обработчик, затем обнуляет ссылку. Для лямбды пришлось бы сохранить экземпляр делегата:
новая похожая лямбда не обязательно снимает прежнюю подписку.

```powershell
dotnet run --project examples/RuntimeLab -- 20
dotnet run --project examples/RuntimeChecks
```

Демонстрация выводит `1`, `0`, `7`: одно полученное событие, ноль оставшихся обработчиков,
записанное значение буфера. Повторный Raise после Dispose больше не увеличивает счётчик.
Проверки также выбрасывают исключение внутри using: обработчик должен быть снят.

Это воспроизводимая проверка владения. Проверка «объект точно собран через 100 мс» ненадёжна:
оптимизации, отладчик и другие ссылки меняют время жизни.

## Finalizer, SafeHandle и асинхронное завершение

Finalizer `~Type()` не равен детерминированному деструктору C++.
Он нужен как резерв при непосредственном владении unmanaged-ресурсом и усложняет время жизни.
Не полагайтесь на его запуск перед завершением процесса и на доступность других финализируемых объектов.

Обычно обёртку ОС представляет SafeHandle: он централизует корректное освобождение дескриптора.
Если класс владеет только managed-объектами IDisposable, собственного finalizer обычно не нужно.
В наследуемом типе классический Dispose pattern разделяет публичный Dispose и защищённый
виртуальный Dispose(bool disposing): managed-поля освобождают при disposing=true.
Владение unmanaged-ресурсом в собственном finalizer требует отдельной аккуратной реализации.
После нормального освобождения финализацию такого объекта подавляют GC.SuppressFinalize(this).
Для sealed-обёртки из нашего примера сложная иерархия не требуется.
[Реализация Dispose](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/implementing-dispose).

IAsyncDisposable возвращает ValueTask из DisposeAsync: завершение может требовать неблокирующего I/O.
`await using` ожидает это завершение; обычный using автоматически не заменяет его.
Полная модель await и реализация такого владельца появятся в главе 31.
Передача ресурса в метод не означает передачу владения: явно указывайте, закрывает ли метод
полученный Stream, и учитывайте параметры наподобие leaveOpen.

## Слабая ссылка и диагностика

WeakReference не удерживает объект в живых. Сначала вызовите TryGetTarget и используйте полученную
сильную ссылку; отдельная проверка «жив ли он» не гарантирует доступность при следующем обращении.
Слабая ссылка подходит для необязательного кэша, но не заменяет владение файлом и не чинит
бесконечно растущий словарь ключей.

При росте памяти выясняйте: растут ли выделения, живые объекты после сборки, native-память
или удержание пула? Для подписчика сначала нарисуйте путь от корня и уберите ненужную подписку.
Подробные профилировщики и дампы рассматриваются в главе 35.

## Практика

**20-A.** Подпишитесь на PulseSource внутри using, вызовите Raise дважды, затем ещё раз после выхода.
Ожидаются Count=2 и SubscriberCount=0. Критерий: тот же результат при исключении внутри using.

**20-B.** Напишите владельца аренды на 16 байт с передаваемым тестовым пулом.
Ожидаются видимая длина 16, ровно один Return при двух Dispose и запрет нового доступа после Dispose.
Критерий: тестовый пул возвращает массив длины 32, чтобы обнаружить выдачу лишнего диапазона.

**20-C.** Создайте долгоживущий publisher и 100 временных наблюдателей.
Сначала оставьте подписки, затем исправьте завершение каждой подписки.
Ожидается переход числа обработчиков со 100 к 0. Критерий: объяснён граф удержания,
нет GC.Collect в рабочем пути и проверка не зависит от момента финализации.
WeakReference можно использовать для отдельного исследовательского опыта, не как таймер теста.
