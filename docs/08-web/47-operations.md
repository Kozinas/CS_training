# 47. Кэш, фоновые задачи и наблюдаемость

**Результат:** вы ускоряете чтение без смешивания пользователей, выполняете фоновую работу с понятным
временем жизни и связываете пользовательский симптом с логом, метрикой и trace.
Нужны главы 29, 31–35 и 44–46. Код — [LedgerService](../../examples/Web/LedgerWeb/LedgerService.cs)
и [Delivery](../../examples/Web/LedgerWeb/Delivery.cs).

## Кэш хранит производное состояние

Кэш имеет смысл, когда повторное вычисление дорого, а правила допустимой устарелости понятны.
Источник истины L06 — SQLite. Промах кэша вызывает SQL-запрос; потеря кэша не теряет расходы.
Ключ обязан включать все входы вычисления: владельца, фильтры, версию, а при необходимости язык и права.
Ключ report без Owner превратил бы оптимизацию в утечку данных между пользователями.

IMemoryCache хранит значения в одном процессе. IDistributedCache предоставляет byte[]/строковое
хранилище через общий backend, например Redis. HybridCache объединяет локальный слой с необязательным
распределённым слоем и координирует одновременное заполнение одного ключа внутри своего экземпляра.
Один общий Redis не превращает такую координацию в глобальную блокировку всех узлов.
[HybridCache](https://learn.microsoft.com/en-us/aspnet/core/performance/caching/hybrid?view=aspnetcore-10.0).

## Инвалидация и гонка заполнения

Простой порядок «прочитать БД, заполнить кэш» конфликтует с «записать БД, удалить ключ»:
старое чтение может завершиться после удаления и вновь положить старый результат.
В L06 у пользователя есть Revision. Каждое изменение расходов повышает её в той же транзакции.
Ключ отчёта — report:owner:revision. После подтверждённой записи новое чтение получает новый ключ.

```text
Чтение:   прочитать Revision -> получить report:owner:Revision
Изменение: expenses + outbox + Revision++ -> COMMIT
Следующее чтение: другой ключ -> актуальный отчёт
```

Перекрывающийся с записью запрос может вернуть состояние на более ранний момент своего выполнения.
Это не обещание, что все одновременные читатели увидят один снимок. Старые ключи доживают TTL 30 секунд.
Ревизия делает недостижимым старый ключ для чтения, начатого после commit; TTL ограничивает длительность
хранения производных значений. TTL не задаёт жёсткий предел памяти и не заменяет квоты числа ключей.

В фабрике HybridCache используется отдельный DbContext от IDbContextFactory. Фабрика может обслуживать
несколько ожидающих запросов: уничтожение scope одного запроса не должно уничтожать её контекст.
Переданный sharedToken относится к совместной работе; отмена одного читателя не обязательно отменяет
вычисление, нужное остальным. Не захватывайте HttpContext и scoped DbContext в такую фабрику.

Для Redis отдельно решают сериализацию, версионирование ключей, TTL, недоступность backend и конфиденциальность.
Отчёт можно пересчитать при сбое кэша, но бесконтрольный fallback под высокой нагрузкой может перегрузить БД.
Distributed lock требует срока, владения и обработки потери lease; это уже протокол, а не строка SetAsync.
Запускаемый L06 использует локальный слой HybridCache; Redis оставлен отдельным упражнением.

## Фоновая работа принадлежит Host

Task.Run из HTTP endpoint не делает работу долговечной: запрос уже завершился, scoped-сервисы уничтожены,
процесс может остановиться. В L06 HTTP-транзакция записывает Outbox. BackgroundService периодически
читает до 20 событий, создаёт scope для цикла и передаёт stoppingToken во все операции.

```csharp
await using var scope = scopes.CreateAsyncScope();
var dispatcher = scope.ServiceProvider
    .GetRequiredService<OutboxDispatcher>();
await dispatcher.Drain(stoppingToken);
```

Singleton worker не удерживает DbContext между циклами. PeriodicTimer задаёт интервал,
а последовательное ожидание не запускает неограниченное число параллельных Drain.
Остановка Host отменяет ожидание и незавершённые операции. Успех уже выполненного commit не исчезает
из-за последующей отмены: повторная доставка проверяет Inbox.

BackgroundService подходит работе, принадлежащей жизненному циклу сервиса. Quartz добавляет расписания
и понятия job/trigger, Hangfire — выполнение и управление фоновыми заданиями с хранилищем.
При выборе нужны требования к persistence, retry, кластеру, misfire, часовому поясу и версии/лицензии инструмента.
Ни один планировщик сам по себе не делает побочный эффект идемпотентным.

Постоянная ошибка одной записи требует отдельного решения: счётчика попыток, карантина, диагностики
и процедуры повторного запуска. В учебном worker SQLite-ошибка откладывает цикл на следующий tick;
универсальная очередь с dead-letter, распределёнными lease и SLA здесь не реализована.

## Состояние сервиса

Liveness отвечает на вопрос «процесс способен отвечать». Readiness — «экземпляр пригоден для работы».
L06 /health/live не обращается к БД, а /health/ready выполняет небольшой запрос к таблице Outbox.
Соединиться с пустым SQLite-файлом недостаточно: схема может отсутствовать.
Тест без миграции получает live=200 и ready=503.

Зависимость не всегда должна входить в readiness. Недоступный необязательный курс валют не делает
чтение расходов невозможным. Если каждая частичная ошибка снимает все экземпляры с балансировки,
частичный отказ можно превратить в полный. Health-ответ не должен раскрывать connection string и stack trace.

## Три разных вида свидетельств

| Сигнал | Отвечает на вопрос | Пример L06 |
| --- | --- | --- |
| Структурированный лог | Что случилось в операции | Import committed, Added, Duplicates |
| Метрика | Как меняется поток событий | ledger.imports.committed |
| Trace | Где потрачено время одного запроса | ASP.NET span -> ledger.import или HttpClient span |

Лог пишется шаблоном с параметрами, а не интерполированной строкой: backend сохраняет поля для поиска.
TraceId в ProblemDetails связывает ошибку клиента с диагностикой. ActivitySource добавляет предметный span,
Meter — счётчик. В L06 счётчик увеличивается после новой фиксации пакета, replay не увеличивает его.
Исключение до commit не должно выглядеть успешной записью в метрике.

OpenTelemetry подключает instrumentation ASP.NET Core/HttpClient и наш ActivitySource/Meter.
Ресурс service.name описывает сервис, span — операцию, tags — её признаки.
Сбор и экспорт — отдельные этапы: ActivitySource без слушателя может не создавать Activity,
а подключённый источник без exporter не отправляет trace в collector.
[OpenTelemetry для .NET](https://opentelemetry.io/docs/languages/dotnet/).

В примере консольный exporter включается Telemetry__Console=true. В рабочей среде выбирают OTLP endpoint,
sampling, срок хранения, ограничения доступа и обработку отказа collector.
Идентификатор пользователя не стоит делать label счётчика: он создаёт высокую кардинальность.
Пароли, токены, заметки и тела запросов не нужны для диагностики длительности импорта.

## Как найти медленную зависимость

1. Определите симптом: выросла длительность GET /api/v1/rate, а чтение /report нормально.
2. Найдите request span и его HttpClient child по traceId.
3. Сравните время до вызова, время внешнего HTTP и локальную обработку.
4. Проверьте статус, timeout и отмену, затем воспроизведите задержку локальным HTTP stub.

В L06 полный deadline внешнего чтения — две секунды, включая тело, размер — 8192 байта.
503, неверный JSON, слишком большое тело и deadline имеют разные результаты. Отмена клиента
передаётся дальше; её не переименовывают в timeout зависимости. Автоматические повторы не настроены,
поэтому один запрос не порождает скрытую серию обращений к уже перегруженному сервису.

## Конфигурация — часть договора запуска

Ledger__Path задаёт файл БД, Worker__Enabled включает доставку, Rates__BaseUrl задаёт доверенную базу URL,
Limits__ApiPermits определяет лимит, Telemetry__Console — экспорт. URL зависимости не принимается от клиента.
Указывать обязательные настройки явно полезнее, чем незаметно создать базу в случайной рабочей папке.
В большем сервисе оформите эти значения через Options и ValidateOnStart, определив допустимые диапазоны.

## Практика

**47-A.** Прочитайте отчёт, измените сумму, прочитайте отчёт снова. Отключите worker, выполните импорт
и сравните /report с /projection. Критерий: отчёт актуален, производная проекция догоняет после запуска worker.

**47-B.** Добавьте метрику backlog и длительности обработки без пользовательских labels.
Критерий: сбой доставки виден в метриках, перезапуск не удваивает финансовый результат.

**47-C.** Подключите Redis и OTLP collector в изолированной среде. Смоделируйте потерю каждого отдельно.
Критерий: определены допустимая устарелость, предел нагрузки fallback и сохранность основных данных,
медленный HTTP-вызов найден по trace, недоступность collector не превращается в потерю расхода.
