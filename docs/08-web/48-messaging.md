# 48. Связь между сервисами

**Результат:** вы выбираете между запросом, уведомлением и очередью, объясняете повторную доставку
и сохраняете один предметный эффект при повторе сообщения. Нужны главы 31–35, 43 и 44–47.
Примеры — [ReportRpc](../../examples/Web/LedgerWeb/ReportRpc.cs),
[proto-контракт](../../examples/Web/LedgerWeb/Protos/report.proto) и [Delivery](../../examples/Web/LedgerWeb/Delivery.cs).

## Сначала определите требование к связи

| Задача | Механизм | Важное ограничение |
| --- | --- | --- |
| Немедленно получить результат | HTTP JSON или gRPC | Клиент зависит от доступности ответа |
| Обновить экран подключённого клиента | SignalR | Соединение и уведомления могут потеряться |
| Передать работу переживающему отказ потребителю | Долговечная очередь | Доставка может повториться |
| Вызвать соседний модуль в одном процессе | Обычный интерфейс | Общий жизненный цикл процесса |

Не разбивайте модуль на отдельный сервис только ради слова «микросервис». Сеть добавляет сериализацию,
timeouts, отказ между двумя commit, совместимость контрактов и отдельную эксплуатацию.
Модульный монолит сохраняет явные границы, но позволяет выполнить несколько изменений в одной БД-транзакции.
Выделение сервиса оправдывают требования к независимому развитию, владению данными, масштабу и доступности.

## gRPC и Protobuf

gRPC определяет удалённые методы, Protobuf — типизированные сообщения. Из .proto генерируются серверные
и клиентские C#-типы. Unary-вызов получает один запрос и возвращает один ответ; также существуют server,
client и bidirectional streaming. Потоковая передача требует ограничения очередей, отмены и управления ресурсами.

```protobuf
syntax = "proto3";
package ledger.v1;
service Reports {
  rpc Get (ReportRequest) returns (ReportReply);
}
message ReportRequest { }
message ReportReply { repeated ReportLine lines = 1; }
message ReportLine {
  string category = 1;
  int32 count = 2;
  int64 amount_minor = 3;
}
```

Числа после знака равенства — номера полей в wire-контракте. После удаления поля его номер резервируют,
а не назначают новому смыслу. В proto3 обычное scalar-поле имеет default; когда требуется отличать отсутствие
от нуля, выбирают presence-aware представление, например optional. Денежная сумма передаётся целым числом
минимальных единиц; double не превращает транспорт в точную денежную модель.
[Правила Protobuf](https://protobuf.dev/programming-guides/proto3/).

ReportRpc получает владельца из проверенного principal и вызывает тот же LedgerService.Report.
GrpcChannel повторно используется клиентом, deadline ограничивает ожидание, CancellationToken передаёт отмену.
HTTP-статус и gRPC StatusCode — разные уровни протокола; клиент обрабатывает RpcException.
Тест вызывает сгенерированный клиент через TestServer: анонимный вызов даёт Unauthenticated,
чужой пользователь получает собственный пустой отчёт.

Для обычного gRPC нужен HTTP/2; при ручном запуске используйте HTTPS endpoint с согласованием протокола.
Проверка TestServer покрывает сериализацию, маршрутизацию, DI и права, но не TLS/HTTP/2 reverse proxy.
Браузерный клиент может потребовать gRPC-Web и соответствующую конфигурацию.
[Тестирование gRPC](https://learn.microsoft.com/en-us/aspnet/core/grpc/test-services?view=aspnetcore-10.0).

## SignalR — уведомление о возможном изменении

Hub связывает подключённых клиентов с сервером. SignalR выбирает поддерживаемый транспорт; это не синоним
WebSocket и не долговечный брокер сообщений. Группа пользователя удобна для нескольких его вкладок,
но имя группы не должно назначаться клиентом без проверки прав.

LedgerHub при подключении добавляет connection в группу Context.UserIdentifier.
После доставки события worker отправляет группе владельца уведомление changed с MessageId.
Клиент перечитывает API: уведомление не является единственным экземпляром финансовых данных.
Пропущенное сообщение после разрыва соединения восстанавливается чтением актуального состояния.

Интеграционный тест запускает два настоящих .NET HubConnection через LongPolling. Alice получает событие,
Bob его не получает; контрольное сообщение Bob подтверждает, что его соединение обработало очередь.
Это сильнее произвольного Sleep с предположением «ничего пока не пришло».

Bearer-политика Hub такая же, как API. .NET LongPolling-клиент передаёт Authorization header.
Браузерные WebSocket/SSE имеют ограничения на заголовки; перенос токена в query требует отдельной,
ограниченной конкретным hub-путём настройки authentication и исключения токена из логов.
Такой browser transport и reconnect в примере не настроены.
Права долгого соединения также требуют стратегии обновления и отзыва.
[Authentication SignalR](https://learn.microsoft.com/en-us/aspnet/core/signalr/authn-and-authz?view=aspnetcore-10.0).

## Почему сообщение может повториться

Представьте: потребитель записал результат в БД, но процесс умер до подтверждения доставки.
Отправитель не знает, произошло ли действие, и доставляет сообщение снова.
Если подтверждать заранее, возникает обратная проблема: сообщение считается выполненным, а результат не записан.

At-most-once допускает потерю, at-least-once допускает повтор. Выражение exactly-once нужно всегда связывать
с конкретной границей и хранилищем: транспортное обещание не делает отправку email и запись в отдельной БД атомарными.
В L06 один устойчивый эффект достигается через общий commit Inbox и проекции потребителя.

RabbitMQ различает publisher confirms и consumer acknowledgements. Первое относится к приёму публикации
брокером, второе — к обработке доставки потребителем; ни одно само по себе не подтверждает весь бизнес-процесс.
Prefetch ограничивает число неподтверждённых сообщений, повторная постановка без задержки может создать цикл.
[Acknowledgements и confirms](https://www.rabbitmq.com/docs/confirms).

MassTransit предоставляет модель consumers, маршрутизацию, middleware и механизмы outbox поверх транспорта.
Нужно выбирать совместимые версии и проверять действующие условия использования. Подключение библиотеки
не освобождает от решения, где находится commit бизнес-данных и когда можно подтвердить сообщение.
[Outbox MassTransit](https://masstransit.massient.com/concepts/outbox).

## Outbox и Inbox в L06

Импорт одной транзакцией сохраняет расходы, receipt, новую Revision и событие Outbox.
Событие содержит стабильный MessageId, Owner, CountDelta и AmountDelta.
Изменение суммы создаёт событие с CountDelta=0 и разницей сумм.
Повтор BatchId возвращает receipt и не создаёт второе событие.

```text
Транзакция производителя: expenses + receipt + revision + outbox
                         COMMIT
Доставка:                прочитать outbox -> вызвать consumer
Транзакция потребителя:  INSERT inbox ON CONFLICT DO NOTHING
                         если новая запись: изменить projection
                         COMMIT
Подтверждение:           отметить outbox Delivered
```

Inbox имеет уникальный MessageId. Его вставка и изменение проекции находятся в одной транзакции:
либо сохраняются оба, либо ни один. Два потребителя одного события не увеличивают сумму дважды.
Тест внедряет IOException после consumer commit, но до Delivered: повтор находит Inbox и только завершает
подтверждение. Проекция содержит count=1, а не 2.

Это локальный демонстратор двух границ commit в одной физической SQLite, без RabbitMQ и распределённой транзакции.
Прямой вызов consumer заменяет транспорт, но не объединяет commit производителя, потребителя и acknowledgement.
Реальный перенос потребителя в отдельную БД требует тестов сети, broker confirms, restart и duplicate delivery.
Inbox одного потребителя нельзя бездумно делить между независимыми подписчиками: им нужен ключ с ConsumerId.

## Согласованность и повторные попытки

/report читает основные расходы, /projection — отдельно обновляемую производную сумму.
При выключенном worker отчёт уже изменился, проекция ещё нет. После запуска worker она догоняет состояние.
Это eventual consistency с понятной точкой ожидания, а не разрешение произвольно терять данные.

Изменения проекции выражены дельтами: после доставки всех событий сумма не зависит от порядка,
но промежуточное состояние при другом порядке может отличаться. Для правил, требующих последовательности
состояний, нужны версия агрегата, partition key и обработка пропусков; одной дедупликации мало.

Retry должен иметь предел времени/попыток, backoff и jitter. Повторы одновременно в HTTP-клиенте,
gateway и worker перемножаются. Ошибку валидации повтор не исправит, а poison message требует карантина.
Для внешнего эффекта, например платежа, передают стабильный idempotency key и учитывают договор получателя.
Отдельный лог «отправлено» после вызова не закрывает окно сбоя между эффектом и логом.

## Практика

**48-A.** Выполните gRPC- и SignalR-тесты, затем сценарий сбоя после consumer commit.
Критерий: один эффект, одна Inbox-запись, повтор завершает Delivered.

**48-B.** Добавьте второго независимого потребителя с ключом (ConsumerId, MessageId).
Критерий: каждый применяет событие один раз, ошибка одного не делает другого завершённым.

**48-C.** Замените прямую доставку RabbitMQ и вынесите consumer в отдельный процесс/БД.
Критерий: остановка до/после commit, потеря ack и дубли не повторяют эффект; заданы prefetch,
retry budget, карантин, порядок сообщений и проверяемый сценарий восстановления.
