# 45. MVC, Razor Pages и браузер

**Результат:** вы создаёте серверную HTML-страницу с формой, сохраняете введённые данные при ошибке,
понимаете cookie и защищаете изменение состояния от подделанного запроса.
Нужна глава 44. Пример — [Pages](../../examples/Web/LedgerWeb/Pages/Index.cshtml) в том же LedgerWeb.

## Сервер возвращает HTML

В API ответ — данные для клиента. В server rendering сервер строит HTML, который браузер отображает.
Razor Pages связывает .cshtml со своим PageModel и обработчиками OnGet/OnPost. MVC разделяет маршрутизацию
через controller/action, модель представления и View. Оба подхода используют Razor для генерации HTML
и могут обращаться к одному прикладному сервису. Здесь LedgerService переиспользуется без HTTP-вызова к себе.

Для большой модели предметной области выделяют view model: только нужные странице данные и поля формы.
Передача EF-сущности в форму создаёт лишние возможности binding и связывает UI со схемой хранения.
В L06 список получает ExpenseView, а форма принимает Id, ExpectedVersion и Amount.

## Минимум браузерной модели

HTML задаёт смысл: заголовок, подпись, поле, кнопка, таблица. CSS управляет оформлением и адаптацией.
JavaScript нужен для поведения на клиенте; он не обязателен для обычной формы. DOM — дерево элементов,
а событие submit может вызвать стандартный HTTP POST или клиентский fetch.
Тип input=number и required помогают человеку, но запрос можно отправить без браузера: сервер проверяет всё повторно.

GET формы должен быть безопасным чтением. POST меняет состояние. После успеха сервер возвращает redirect,
браузер выполняет GET: Post/Redirect/Get уменьшает риск повторного POST при обновлении страницы.
Он не заменяет проверку версии и идемпотентность при сетевых повторах.

## Razor не является конкатенацией строк

```cshtml
@page
@model IndexModel
<h1>Мои расходы</h1>
<form method="post">
    <div asp-validation-summary="All" role="alert"></div>
    <label asp-for="Amount">Новая сумма</label>
    <input asp-for="Amount" step="0.01" />
    <button type="submit">Сохранить</button>
</form>
```

Директива @page делает файл endpoint Razor Pages. @model указывает тип PageModel.
Выражение @row.Note выводит значение с HTML-кодированием. Блок `@{ ... }` выполняет C# на сервере,
`@foreach` повторяет HTML для элементов. Ни C#-объекты, ни DbContext в браузер не отправляются.

Tag Helpers asp-for и asp-validation-summary связывают разметку с моделью.
_ViewImports подключает Tag Helpers и namespace; _ViewStart выбирает Layout.
_Layout задаёт общий каркас, partial _ExpenseTable выводит повторно используемую таблицу.
Partial не должен прятать непредсказуемые SQL-запросы: данные готовит PageModel.

## Привязка и ошибки формы

[IndexModel](../../examples/Web/LedgerWeb/Pages/Index.cshtml.cs) использует BindProperty и DataAnnotations.
ModelState содержит ошибки преобразования и проверок. Неверное число не должно незаметно превратиться в нулевую сумму.
При ошибке возвращают Page(), заново загружают список и сохраняют введённые значения для исправления.
При успехе — RedirectToPage(). Конфликт версии показывается как ошибка формы, без затирания новой суммы.

```csharp
if (!ModelState.IsValid)
{
    await OnGetAsync();
    return Page();
}
await ledger.Update(owner, Id,
    new UpdateInput(ExpectedVersion, Amount), HttpContext.RequestAborted);
return RedirectToPage();
```

Это сокращённая ветка: полный код дополнительно переводит ContractException в ModelState.
Владелец вновь берётся из principal, а hidden-поля Id/Version считаются недоверенными.
Даже если Id выбран из своей таблицы, следующий POST может содержать Id другого пользователя.

Культура server binding влияет на числа и даты. Для локализованного UI настройте request localization
и проверьте ввод с нужными разделителями. Транспортный JSON-договор и отображение суммы в HTML не обязаны
иметь один формат. Учебный UI показывает суммы invariant с двумя знаками.

## Cookie, session и статические файлы

Cookie хранится браузером и отправляется подходящему origin/path. Authentication cookie содержит защищённый
билет, а не пароль. HttpOnly препятствует чтению cookie обычным JavaScript; Secure ограничивает передачу HTTPS;
SameSite влияет на отправку между сайтами. Эти свойства решают разные задачи.

Session обычно хранит серверное состояние по идентификатору cookie. Это не место для единственного экземпляра
финансовых данных: session может истечь или исчезнуть. В ферме нужен согласованный backend session и ключи
Data Protection для cookie; локальная память одного процесса не создаёт общую сессию всех узлов.
L06 не использует session: расходы находятся в SQLite, вход — в authentication cookie.

Файлы из wwwroot/site.css открыты как статические ресурсы. Пароли, ключи, backup БД и пользовательские
документы туда не помещают. Для защищённой загрузки нужен endpoint, проверяющий владельца и Content-Type.
В L06 внешний CDN, JavaScript и сторонние шрифты не нужны для работы формы.

## CSRF и XSS — разные проблемы

CSRF использует автоматическую отправку browser cookie: сторонняя страница пытается выполнить действие
от имени уже вошедшего человека. В Razor Pages POST защищён antiforgery: сервер связывает cookie-токен
с токеном формы, а затем проверяет их и текущую идентичность. Form Tag Helper добавляет hidden-поле.
Токен анонимной страницы входа не подходит для POST от уже вошедшего пользователя.
[Защита форм](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0).

XSS выполняет навязанный скрипт в origin приложения. Razor-кодирование превращает заметку
`<script>alert(1)</script>` в отображаемый текст. Html.Raw для пользовательского текста отключил бы эту защиту.
Если продукт действительно разрешает HTML, нужен sanitizer с разрешённым набором элементов и атрибутов;
обычный Replace или удаление слова script не решают задачу. CSP дополняет кодирование, но не подменяет его.

В браузерном тесте L06 реальная страница выдаёт antiforgery-токен, затем выполняются вход, изменение суммы,
конфликт и выход. Отсутствующий, поддельный и старый анонимный токен дают 400. Заметка с script остаётся текстом.
Проверяется HTML и HTTP; это не автоматизация полноценного браузера, layout/JS-поведение требует отдельного e2e.

## Вход и возврат на страницу

LoginModel использует стандартный SignInManager с проверкой пароля и lockout. При успехе создаётся cookie
с Secure/HttpOnly и сроком билета 15 минут. Вход через HTTP для этой формы не предусмотрен: используйте
HTTPS и локальный dev certificate из инструкции. Тестовый TestServer моделирует HTTPS URI без TLS-handshake.

ReturnUrl контролирует пользователь. LocalRedirect применяется только после Url.IsLocalUrl; внешний адрес
заменяется на /. Иначе форма входа стала бы открытым redirect для ссылок на чужие сайты.
GET не выполняет выход: logout — POST с antiforgery. [Cookie authentication](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/cookie?view=aspnetcore-10.0).

## Практика

**45-A.** Выполните вход и изменение суммы через HTTPS. Удалите токен формы из повторного POST.
Критерий: успешное изменение заканчивается redirect, запрос без токена — 400 без изменения БД.

**45-B.** Добавьте форму фильтра списка через GET и отдельную view model. Покажите ошибки ввода рядом
с полем. Критерий: URL воспроизводит фильтр, неизвестная категория не вызывает 500, чужие записи отсутствуют.

**45-C.** Добавьте редактирование заметки и проверку через браузерный инструмент автоматизации.
Критерий: script/HTML отображаются текстом, CSRF и чужой Id отклоняются, ошибка сохраняет введённую заметку.
