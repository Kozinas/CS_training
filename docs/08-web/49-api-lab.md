# 49. Практикум ExpenseLedger API

**Результат:** вы передаёте другому разработчику сервис с HTTP-договором, изоляцией пользователей,
интеграционными тестами и воспроизводимым восстановлением после остановки процесса.
Нужны главы 44–48. Полные условия — [L06](../../labs/06-expense-api/README.md),
запуск — [Web README](../../examples/Web/README.md).

## Сначала договор, затем endpoint

Сквозной сервис сохраняет модель расхода L02 и гарантии хранения L05, добавляя границу пользователя
и HTTP. База Web отдельная: таблицы Identity, Owner, receipts и события требуют собственной схемы.
Файл L05 нельзя переименовать и открыть как Web-базу. Переезд реальных данных потребовал бы отдельной миграции
с назначением владельцев и проверкой исходных сумм.

Вход API — Bearer, вход браузерной формы — cookie. Обновление суммы использует ExpectedVersion.
Импорт ограничен 100 строками и 128 KiB; вся проверка доменных полей предшествует записи.
Повтор нормализованного пакета с тем же BatchId возвращает прежнюю квитанцию.
Fingerprint использует версию канонизации, Guid, DayNumber, нормализованную категорию, целые копейки и заметку;
12.50 и 12.5 равнозначны, порядок строк и текст заметки значимы.

HTTP-транзакция сохраняет outbox одновременно с расходами. Ответ 200 означает фиксацию импорта,
но не обещает, что фоновая проекция уже обновлена и все вкладки получили SignalR-уведомление.
Клиент, которому нужен текущий результат, читает основной /report; /projection демонстрирует отдельную доставку.

## Небольшое приложение с явными обязанностями

| Файл или узел | Ответственность |
| --- | --- |
| Program | Настройки, DI, pipeline, auth, HTTP-контракт |
| WebDb и миграция | Схема Identity/расходов/receipt/outbox/inbox |
| LedgerService | Проверки, транзакции, Owner, версии и отчёт |
| Pages | HTML, ModelState, antiforgery и redirect |
| ReportRpc и LedgerHub | Альтернативные транспортные границы |
| OutboxDispatcher | Приём события, дедупликация и подтверждение |
| DeliveryWorker | Scope, периодический запуск и остановка |

Количество проектов не является критерием архитектуры. Здесь один web-проект оставляет поток запроса обозримым,
а библиотека предметной модели переиспользуется. Если отдельный модуль получает независимые правила и команды,
его можно выделить без копирования аутентификации и транзакций в каждый endpoint.

## WebApplicationFactory проверяет настоящее приложение

Factory поднимает Program с другим окружением и настройками, создаёт HttpClient и даёт возможность
заменить конкретную внешнюю зависимость. TestServer обрабатывает запрос внутри процесса.
При этом работают routing, сериализация, middleware, Identity, EF и Razor, если вы сами их не заменили.
[Интеграционные тесты ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests?view=aspnetcore-10.0).

В Web.Tests каждый тест получает уникальный SQLite-файл и запускает настоящую миграцию.
Пользователь регистрируется и входит через HTTP. Проверка ownership с фиктивным handler, который всегда
выдаёт одного администратора, пропустила бы ошибки выдачи и проверки токена.
Внешний HTTP handler подменяется только в сценариях отказа зависимости; основной договор приложения остаётся.

```csharp
var alice = await factory.User();
var bob = await factory.User();
await Import(alice.Client, new(batchId, [row]));
var response = await bob.Client.GetAsync(
    $"/api/v1/expenses/{row.Id}", token);
Assert.Equal(HttpStatusCode.NotFound, response.StatusCode);
```

Отрицательная проверка обязана смотреть не только статус. После отказа UPDATE перечитайте запись Alice,
после конфликтного импорта посчитайте expenses/receipts/outbox. Иначе endpoint мог сначала записать данные,
а затем вернуть правильную ошибку.

## Матрица приёмки

1. Анонимный и поддельный токен — 401; отсутствие роли — 403; чужой Id — 404.
2. Списки, отчёты, gRPC и SignalR не смешивают владельцев.
3. Повтор пакета не создаёт расход и событие; другой payload с тем же ключом конфликтует.
4. Ошибка после первой строки откатывает весь новый пакет.
5. Два изменения одной ExpectedVersion имеют одного победителя.
6. После изменения отчёт не обслуживается из кэша прежней ревизии.
7. POST формы без правильного antiforgery-токена отклонён; заметка кодируется как текст.
8. Ошибка зависимости, большой ответ, deadline и отмена клиента имеют определённый исход.
9. Сбой после consumer commit не удваивает проекцию при повторе.
10. Readiness без схемы не выдаёт ложный успех; документ OpenAPI соответствует маршрутам.

Параллельные HTTP-запросы проверяют итог при конкурирующем обращении, но не доказывают все возможные
чередования. Для воспроизводимого окна outbox используется hook после consumer commit, а для остановки
зависимости — сигнал начала запроса и CancellationToken. Sleep не служит доказательством наступления состояния.

## Проверка за пределами TestServer

[verify_web.py](../../tools/verify_web.py) запускает настоящий Kestrel на свободном loopback-порту,
а зависимость — локальным HTTP stub. Скрипт применяет миграцию дважды, создаёт пользователя, выполняет импорт
и изменение суммы, затем завершает процесс с выключенным worker.

Новый процесс открывает ту же БД и тот же временный key ring. Старый access token читается,
receipt возвращает прежний ответ, worker догоняет проекцию. Так проверяется отсутствие зависимости
сохранности данных от static-поля или памяти первого процесса. Это остановка процесса, а не испытание
отключением питания, повреждением диска или потерей узла СУБД.

Скрипт сохраняет только отчёты и отобранные строки trace в .artifacts/web. Временные пароли, токены,
БД и key ring не входят в Git или CI-artifact. В GitHub Actions проверка выполняется на GitHub-hosted
windows-latest, без установки runner на компьютер учащегося и без CD-развёртывания.

## Нагрузочный опыт с известными границами

После прогрева выполняются 40 чтений /report с четырьмя одновременными клиентскими задачами.
Для каждого проверяется точное содержимое ответа, затем считаются p50, p95 и максимум времени.
Числа сохраняются в .artifacts/web/load.json, а не сравниваются с произвольным порогом в CI.
Это небольшой опыт работоспособности при конкуренции; он не измеряет предельный throughput,
длительный memory leak, production p99 или поведение распределённого limiter.

Для серьёзного измерения зафиксируйте оборудование, объём БД, распределение запросов, warmup,
частоту поступления, длительность и отдельно ошибки/очередь. Измерение только успешных ответов
при скрытом росте таймаутов создаёт ложное впечатление ускорения.

## Передача сервиса

Другой разработчик должен знать команды restore/build/migrate/run/test, обязательные настройки,
порты, схемы входа и порядок восстановления. Миграции выполняются явно до сервиса; каждый HTTP-запрос
не пытается одновременно обновить схему. Сохранение Data Protection keys и backup финансовой БД — разные задачи.
Практика backup/restore из L05 применима к SQLite, но Web-схема и пользователи должны проверяться отдельно.

Заявляйте границы: Redis, RabbitMQ, внешний OIDC, browser WebSocket, TLS reverse proxy и публичное
развёртывание в этот запускаемый пример не входят. Это продолжения с новыми критериями, а не включение
нескольких флагов. Полный жизненный цикл доставки и эксплуатации продолжится в главах 55–60.

## Практика

**49-A.** Выполните L06 по инструкции, найдите trace внешнего HTTP и отчёт малого нагрузочного опыта.
Критерий: объяснены метод измерения, отличие /report от /projection и сохранность после перезапуска.

**49-B.** Реализуйте L06 самостоятельно и передайте запуск другому человеку без устных подсказок.
Критерий: матрица приёмки автоматизирована, чистая среда собирает проект, все ограничения записаны.

**49-C.** Добавьте удаление расхода с версией, событием-дельтой и совместимым OpenAPI-контрактом.
Критерий: повтор/конкурирующее удаление не удваивают эффект, чужой Id не доступен,
основной отчёт и доставленная проекция сходятся после восстановления worker.
