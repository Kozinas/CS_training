# 44. HTTP API на ASP.NET Core

**Результат:** вы превращаете правила и хранилище в HTTP-контракт, объясняете порядок middleware,
разделяете ошибки клиента и сервера и проверяете API без ручного щёлканья по интерфейсу.
Нужны главы 28–29, 31 и 40–43. Запускаемый проект — [LedgerWeb](../../examples/Web/README.md).

## Запрос проходит через приложение

Kestrel принимает соединения и HTTP-запросы. Host управляет запуском, остановкой, конфигурацией и DI.
Middleware — звено обработки запроса: оно может вызвать следующее звено, завершить ответ или обработать
результат после возврата. Endpoint — выбранный маршрутизатором обработчик конкретного действия.
Создание сервиса в DI само по себе не добавляет его middleware в конвейер.

```text
Kestrel -> обработка ошибок -> маршрутизация -> CORS
        -> authentication -> authorization -> rate limiter
        -> ограничение тела -> endpoint -> предметные правила -> БД
```

Порядок из примера существенен. Routing должен определить endpoint до политик, привязанных к маршруту.
Authentication с основной схемой читает browser cookie. Authorization для /api/v1 дополнительно
применяет явно названную bearer-схему. Поэтому лимитер по пользователю стоит после authorization:
к этому моменту principal API уже установлен. Лимитер до этой точки ошибочно объединял бы bearer-клиентов
в одну анонимную группу. Ошибку обнаруживает тест с двумя пользователями и независимыми лимитами.

Код после `await next(context)` выполняется при возврате. Если ответ уже начат, заменить статус и заголовки
нельзя: обработку ошибок размещают снаружи операций, способных завершиться исключением.
HttpContext живёт в запросе; сохранять его в singleton или передавать незавершённой фоновой задаче нельзя.

## HTTP описывает договор

URL определяет ресурс, метод — действие, статус — результат, заголовки — метаданные, тело — представление.
GET не должен создавать расходы. PUT в нашем примере устанавливает новую сумму с ожидаемой версией.
POST импорта получает BatchId: клиент может повторить ту же команду после потери ответа.
Идемпотентность эффекта не требует одинакового HTTP-статуса всех повторов: устаревший PUT может получить 409.

| Результат | Статус в L06 | Что делает клиент |
| --- | --- | --- |
| Получен отчёт или квитанция | 200 | Читает JSON |
| Создан пользователь | 201 | Переходит к получению токена |
| Сумма изменена | 204 | Не пытается читать JSON-тело |
| Неверный JSON или предметные данные | 400 | Исправляет запрос |
| Нет пригодной аутентификации | 401 | Выполняет вход |
| Не выполнена политика admin | 403 | Не повторяет с теми же правами |
| Записи у текущего пользователя нет | 404 | Не раскрывает существование чужой записи |
| Ключ запроса или версия конфликтуют | 409 | Сверяет актуальное состояние |
| Тело превышает лимит | 413 | Уменьшает запрос |
| Неподдерживаемый Content-Type | 415 | Отправляет application/json |
| Превышена частота | 429 | Учитывает Retry-After |
| Зависимость недоступна | 503 | Применяет ограниченную политику повторов |

422 допустим в другом договоре для семантической ошибки, а 412 — при нарушении условного запроса If-Match.
Главное — единый опубликованный договор. Не заменяйте все исходы ответом 200 с полем success=false.

## Minimal API и controller

В [Program.cs](../../examples/Web/LedgerWeb/Program.cs) группа /api/v1 задаёт общие политики:

```csharp
var api = app.MapGroup("/api/v1")
    .RequireAuthorization("api")
    .RequireRateLimiting("api-limit");
api.MapGet("/report", async (ClaimsPrincipal user,
    LedgerService service, CancellationToken token) =>
    Results.Ok(await service.Report(
        user.FindFirstValue(ClaimTypes.NameIdentifier)!, token)));
```

Обработчик получает scoped-сервис из DI, principal из запроса и RequestAborted как CancellationToken.
DbContext не становится singleton. Endpoint связывает транспорт с приложением, а LedgerService управляет
предметной операцией. Такая граница позволяет вызвать то же правило из Razor Page и gRPC.

Контроллер решает ту же задачу через класс, методы действий и атрибуты маршрутов.
Ниже альтернативный учебный фрагмент, который не регистрируется параллельно тому же маршруту:

```csharp
[ApiController]
[Route("api/v1/expenses")]
[Authorize(Policy = "api")]
public sealed class ExpensesController(LedgerService ledger)
    : ControllerBase
{
    [HttpGet("{id:guid}")]
    public async Task<ActionResult<ExpenseView>> Get(
        Guid id, CancellationToken token) =>
        Ok(await ledger.Find(
            User.FindFirstValue(ClaimTypes.NameIdentifier)!, id, token));
}
```

Для такой версии понадобятся AddControllers и MapControllers. MVC предоставляет фильтры, conventions
и ModelState; Minimal API удобен для компактных endpoint-групп. Большой метод с SQL и проверкой пароля
не станет хорошей архитектурой от переноса в класс Controller.

## Binding не заменяет проверку правил

Binding получает значения из route, query, headers, body и DI. DTO определяет входной формат,
но доступность setter не означает разрешение клиенту менять поле. В ExpenseInput нет Owner, Version
и внутренних полей Identity. JSON с неизвестными полями в L06 отклоняется, владелец берётся из principal.

Ошибки синтаксиса JSON и неверный тип числа обнаруживает привязка. Нулевой Guid, дробные копейки,
пустую категорию и пакет из 101 строки отклоняет LedgerService до начала записи. Ограничение тела
128 KiB действует и для запроса без Content-Length: приложение читает не больше лимита плюс один байт.
Это отдельная защита от лимита числа записей и от лимитов reverse proxy.

В .NET 10 есть встроенная валидация Minimal API через пакет Microsoft.Extensions.Validation и AddValidation.
В MVC/Razor Pages действует собственная модель DataAnnotations/ModelState. В L06 API использует явную
проверку правил из L02; сами атрибуты на DTO без соответствующей регистрации не включают автоматическую
валидацию Minimal API. [Модель validation](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/validation?view=aspnetcore-10.0).

## Ошибки и описание API

AddProblemDetails вместе с обработчиками исключений и пустых error-ответов создаёт согласованный формат
application/problem+json. L06 добавляет traceId, а ожидаемые ContractException переводит в договорные статусы.
Неожиданная ошибка остаётся 500; её stack trace и SQL-параметры не отправляются клиенту.
ProblemDetails содержит поля type/title/status/detail/instance, когда они применимы, и расширения.
Код клиента должен опираться на документированные поля, а не распознавать фразы локализованного сообщения.
[Формат Problem Details](https://www.rfc-editor.org/info/rfc9457/).

OpenAPI — машиночитаемое описание путей, схем и ответов. AddOpenApi регистрирует генерацию,
MapOpenApi открывает документ; UI для запросов — отдельный инструмент. В L06 документ доступен
по /openapi/v1.json только в Development/Testing, содержит схему opaque bearer и требования безопасности
API. Тест проверяет не только существование JSON, но и схему ответа и security requirement.
[Генерация OpenAPI](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/openapi/aspnetcore-openapi?view=aspnetcore-10.0).

## Страницы и версии

GET /api/v1/expenses принимает after и size. Порядок — уникальный неизменяемый Sequence внутри выборки владельца.
Приложение читает size+1 записей: лишняя показывает наличие следующей страницы. Next=null означает конец
на момент чтения. Между запросами набор может измениться; это не снимок всей истории.

/v1 обозначает версию транспортного договора, Version записи защищает от потери обновления,
а миграция EF меняет схему БД. Эти три версии независимы. Добавление обязательного JSON-поля или изменение
смысла суммы может сломать старого клиента даже при неизменившемся URL. Сначала определите совместимость
и переходный период, затем выбирайте URL/header versioning и инструменты его реализации.

## Практика

**44-A.** Запустите API, получите 200, 204, 400, 401, 404 и 409. Для каждого сохраните метод,
путь, заголовки и тело. Критерий: 204 не содержит JSON, error-ответы имеют документированный смысл.

**44-B.** Добавьте фильтр категории к постраничному списку. Нормализуйте категорию, включите её
в договор cursor и OpenAPI. Критерий: две страницы не повторяют записи и не смешивают владельцев.

**44-C.** Реализуйте вариант обновления с ETag/If-Match и 412. Сохраните старый маршрут на переходный период.
Критерий: два клиента с одной версией не теряют обновление, старый клиент продолжает работать.
