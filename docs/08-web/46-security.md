# 46. Идентификация и защита API

**Результат:** вы различаете вход и разрешение действия, используете стандартную реализацию паролей,
проверяете владельца ресурса и доказываете изоляцию пользователей отрицательными тестами.
Нужны главы 44–45. Реализация и команды — [Web README](../../examples/Web/README.md).

## Кто обратился и что ему разрешено

Authentication устанавливает principal: набор identities и claims, полученный после проверки credential.
Authorization решает, может ли этот principal выполнить конкретное действие. Анонимный запрос к отчёту
даёт 401; вошедший пользователь без роли admin получает 403 на /api/v1/admin.
Наличие строки userId в JSON не устанавливает личность. Декодированный без проверки JWT также её не устанавливает.

В L06 principal создаётся стандартным SignInManager после проверки пароля через UserManager.
Identity хранит пользователей и хеши паролей в SQLite через EF Core. Вызов CreateAsync выполняет настройку
пароля стандартными средствами платформы; собственный SHA256(password) не используется.
Тест проверяет, что пароль не хранится открытым текстом, неверный вход отклоняется и пять неудач приводят к lockout.

Соль затрудняет переиспользование готовых таблиц хешей, а вычислительная стоимость замедляет перебор.
Шифрование пароля с общим ключом не является заменой password hashing. Параметры, форматы и rehash
должна обслуживать поддерживаемая библиотека. Не записывайте пароль, Authorization и authentication cookie в логи.

## Схема не равна формату токена

Cookie подходит серверному браузерному приложению: браузер отправляет её автоматически.
Bearer означает, что предъявитель токена может использовать предоставленные права. Токен может быть
JWT или непрозрачной строкой; название HTTP-схемы Bearer не обещает JWT.

L06 использует AddBearerToken и Results.SignIn с IdentityConstants.BearerScheme.
ASP.NET Core защищает билет средствами Data Protection. Такой access token нельзя передавать библиотеке,
ожидающей JWT с подписью и issuer. Время жизни access token — 15 минут.
Стандартный ответ также содержит refreshToken, но endpoint обновления в учебном сервисе не реализован:
после истечения клиент входит снова. Это явно ограниченный договор, а не полный OAuth-сервер.
[Варианты токенов Identity](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0).

Для API задана отдельная политика:

```csharp
options.AddPolicy("api", policy => policy
    .AddAuthenticationSchemes(IdentityConstants.BearerScheme)
    .RequireAuthenticatedUser()
    .RequireClaim(ClaimTypes.NameIdentifier));
```

Browser cookie не проходит эту политику. Razor Pages используют cookie-схему и antiforgery для POST.
Так не возникает случайного добавления cookie-аутентификации к JSON endpoint без соответствующей CSRF-защиты.
В cookie настроены Secure, HttpOnly, SameSite=Lax, срок билета и SecurityStampValidator.
Выход удаляет browser cookie; уже выданный bearer-токен не отзывается немедленно и живёт до окончания срока.

## OAuth 2.0 и OpenID Connect

OAuth 2.0 описывает делегированный доступ: клиент получает ограниченное право обратиться к resource server.
OIDC добавляет стандартный слой идентификации пользователя и ID token. Access token предназначен API,
ID token — клиенту, установившему сеанс входа; подмена одного другим нарушает договор audience.

Для пользовательского входа современный сценарий — authorization code с PKCE через поддерживаемую
OIDC-библиотеку и доверенный provider. Проверяются issuer, audience, подпись, срок, redirect URI,
state и nonce в соответствующем протоколе. Client secret нельзя помещать в публичное браузерное приложение.
Client credentials применяют к разрешённому взаимодействию сервисов, без выдачи себя за человека.
Password grant и собственный сбор пароля внешнего провайдера не являются заменой redirect-входа.
[OAuth Security BCP](https://www.rfc-editor.org/info/rfc9700/).

При переходе L06 к внешнему IdP меняется способ установления principal, а правила владения остаются.
Стабильный ключ пользователя задаётся договором provider/subject; email может изменяться и не обязан
быть глобально уникальным между провайдерами. Внешний OIDC-вход, MFA и подтверждение email — расширения L06.
Локальная регистрация с паролем здесь служит воспроизводимому практикуму, а не готовому публичному identity-сервису.

## Claims, роли, политики и ресурс

Claim — утверждение проверенного источника. Роль — способ группировать разрешения; политика объединяет требования.
Для сложного действия применяют IAuthorizationService и resource-based handler: решение зависит от пользователя,
ресурса и операции. Проверка только общей роли «пользователь» не доказывает владение конкретным расходом.

В L06 каждый запрос данных содержит Owner:

```csharp
var row = await db.Expenses.SingleOrDefaultAsync(
    e => e.Owner == owner && e.ExternalId == id, token);
```

owner получается из NameIdentifier после authentication. Запрос чужого Id даёт тот же 404, что отсутствующий Id.
Та же граница действует для UPDATE, списков, отчётов, gRPC и SignalR. Ключи расходов и квитанций составные:
(Owner, ExternalId) и (Owner, BatchId). Одинаковый BatchId разных пользователей не раскрывает чужую квитанцию.
Проверка Owner только после пагинации дала бы неполные страницы и могла бы раскрывать структуру чужих данных.

Глобальный EF query filter может снизить риск пропущенного предиката, но не заменяет проектирование:
IgnoreQueryFilters, raw SQL, фоновые операции и неверный lifetime tenant context способны обойти его.
В учебном коде предикат виден явно; тесты обращаются к одной записи от двух настоящих учётных записей.

## CORS, CSRF, HTTPS и секреты

| Механизм | Что ограничивает | Чего не обеспечивает |
| --- | --- | --- |
| CORS | Чтение cross-origin ответа браузерным кодом | Авторизацию небраузерного клиента |
| Antiforgery | Подделку browser POST с автоматически отправленной cookie | Защиту от выполнения XSS в своём origin |
| HTML-кодирование | Интерпретацию текста как HTML | Проверку прав доступа |
| TLS/HTTPS | Подслушивание и изменение трафика на соединении | Проверку владельца ресурса |
| Rate limiting | Частоту запросов в определённых пределах | Полную защиту от распределённой атаки |

CORS L06 разрешает только https://localhost:5173 и определённые методы/заголовки, без credential-cookie.
Preflight обрабатывается до требований входа. Origin нельзя использовать как доказательство личности.
Сценарий AllowAnyOrigin с credentials не является корректной политикой для приватных данных.

HTTPS обязателен при передаче пароля и токена вне изолированного локального опыта. В инструкции есть
явное исключение AllowHttp для loopback-проверки Kestrel; оно не разрешает публикацию сервиса по HTTP.
За reverse proxy нужно настроить доверенные адреса и forwarded headers: доверять любому X-Forwarded-For
опасно, в том числе для IP-лимитера и HTTPS redirects.

Секреты разработки хранят в user-secrets или в подходящем хранилище, production — в secret store среды.
Переменная окружения сама по себе не шифрует значение. Не помещайте ключи в appsettings репозитория или wwwroot.
Для нескольких экземпляров приложения согласуйте Data Protection key ring, защиту ключей и application name.
Потеря ключей может сделать старые cookie/opaque tokens нечитаемыми даже при целой базе пользователей.

## Модель угроз как рабочая таблица

Начните с ценных данных, точек входа и границ доверия. Для L06 полезны четыре конкретных сценария:

| Попытка | Мера | Проверяемый исход |
| --- | --- | --- |
| Bob отправляет Id Alice | Owner в запросе и UPDATE | 404, сумма Alice прежняя |
| Клиент повторяет пакет после потери ответа | Receipt в той же транзакции | Исходный результат, нет нового события |
| Сторонняя форма меняет сумму через cookie | Antiforgery | 400, БД прежняя |
| Большое тело или много запросов | Лимит байтов, строк, частоты | 413/400/429, без частичной записи |

Добавьте перебор паролей, подмену токена, open redirect, утечку в логах и зависимость от стороннего HTTP.
Не объявляйте сервис безопасным только потому, что все функциональные тесты зелёные: они доказывают
конкретные условия. Публичный продукт дополнительно требует процессов восстановления доступа, аудита,
управления регистрацией, хранения ключей и реагирования на компрометацию.

## Практика

**46-A.** Создайте Alice и Bob. Воспроизведите 401 без токена, 403 без роли и 404 на чужой расход.
Критерий: GET, PUT и отчёт не раскрывают данные Alice пользователю Bob.

**46-B.** Добавьте политику expenses.write и пользователя только для чтения. Не принимайте разрешение
из тела запроса. Критерий: чтение работает, изменение даёт 403, новый токен отражает выданные доверенным кодом права.

**46-C.** Подключите тестовый OIDC provider через поддерживаемую библиотеку и разделите окружения.
Критерий: неверные issuer/audience и просроченный токен отклоняются, ключ пользователя не зависит от email,
секреты не попадают в Git, прежние тесты владения продолжают проходить.
