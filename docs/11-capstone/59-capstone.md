# 59. Итоговый проект

**Результат:** вы превращаете требования в проверяемое приложение, защищаете границы данных и передаёте
воспроизводимый выпуск другому разработчику. Нужны L01–L07, главы 36–49 и выбранная специализация.
Условие — [L08](../../labs/08-capstone/README.md), разобранное правило — [Capstone](../../examples/Capstone/README.md).

## От функций к наблюдаемому договору

«Добавить бюджеты» не определяет поведение. Нужно решить, чей это бюджет, к какому периоду он относится,
что происходит ровно на границе, какие изменения допускаются и что увидит второй одновременный запрос.
Сначала запишите примеры входа и результата. Затем выбирайте классы, таблицы и библиотеки.

ExpenseLedger v3 продолжает API и клиент из L07. Новая возможность — месячный лимит категории.
Валюта одна, как в прежних работах; суммы хранятся в целых minor units. Это учебный учёт расходов,
а не модель банковского счёта. Ключ бюджета: authenticated owner + год + месяц + нормализованная категория.
Месяц берётся из DateOnly расхода: серверное «сейчас» и часовой пояс запроса его не меняют.

| Ситуация | Договор v3 |
| --- | --- |
| Бюджет категории не задан | Прежнее поведение L06, без нового ограничения |
| Лимит 2000, потрачено 1250, новый расход 750 | Успех: итог 2000, остаток 0 |
| Вместо 750 поступает 751 | Весь пакет отклонён, прежние данные сохранены |
| Тот же успешный BatchId и payload | Прежняя квитанция, новая сумма не списывается |
| Тот же BatchId с другим payload | Конфликт, даже если денег достаточно |
| Лимит уменьшают ниже уже потраченного | Конфликт, прежний лимит сохранён |
| Другой пользователь или следующий месяц | Независимый бюджет |

Пакет может содержать несколько категорий/месяцев. Если хотя бы одна группа превысит свой лимит,
не записывается ни один новый расход, receipt или outbox event. Уже существующие идентичные строки
считаются дубликатами, а не новыми тратами. Проверка прав выполняется до выдачи чужого состояния;
owner никогда не принимается из доверенного «по умолчанию» поля JSON.

## Вертикальный срез и границы ответственности

Первый срез проходит полный путь: пользователь задаёт лимит, импортирует расход и видит остаток.
Он включает модель, миграцию, API, клиент и проверку. После него добавляют конкуренцию, отказы и поставку.
Десятки пустых проектов без работающего сценария не уменьшают неопределённость требований.

```text
UI -> HTTP contract -> application operation -> transaction -> database
                              |
                              +-> pure budget rule
                              +-> outbox in the same commit
background worker -> durable delivery -> observable result
```

Чистое правило отвечает на вопрос о числах. Application operation получает owner из auth,
разбирает идемпотентность, загружает состояние и завершает транзакцию. Хранилище обеспечивает
уникальность и конкуренцию. UI показывает ожидание, отказ и актуальные данные; он не является
единственным местом проверки лимита. Повторите запрос напрямую без UI, чтобы это проверить.

Не создавайте общий generic repository только ради количества слоёв. Сначала назовите операцию,
её атомарную границу и необходимые запросы. Не передавайте DbContext в singleton worker или между
параллельными запросами. Outbox сохраняет намерение внутри commit, а внешний вызов выполняется позже.

## Разобранный пример: предварительный расчёт

BudgetPolicy принимает лимит, уже потраченную сумму и **только новые**, заранее дедуплицированные
суммы одной группы. Это снимок; правило не владеет БД и ничего не резервирует.

```csharp
BudgetDecision decision = BudgetPolicy.Preview(
    limitMinor: 2000,
    spentMinor: 1250,
    incomingMinor: [250, 500]);
// Allowed=true, ProposedMinor=2000, RemainingMinor=0
```

Контракт требует 0 <= spent <= limit, не более 100 строк и каждой новой суммы 1..99999999.
Нулевой лимит допустим: пустой набор проходит, новый положительный расход — нет.
Сложение выполняется checked; переполнение нельзя превращать в отрицательную «свободную сумму».
При отказе по лимиту ProposedMinor содержит предложенный итог, RemainingMinor равен 0.

Последовательность читается один раз. Даже после превышения лимита проверяются оставшиеся строки:
[11,-1] при лимите 10 — ошибка входа, а не корректный отказ бюджета. Количество ограничивает обход;
это не таймаут произвольного блокирующего MoveNext. В API сначала действует прежний лимит размера
пакета, затем материализуется и валидируется небольшой набор строк.

```text
python tools/verify_capstone.py
```

Команда собирает два проекта без внешних NuGet-пакетов, выполняет 47 проверок, затем убеждается,
что два намеренно испорченных варианта отвергаются. Ответы в JSON заданы независимо от реализации.
Это проверка опорного правила, не автоматическая сдача вашего приложения.

## Почему правильного правила недостаточно

Пусть в БД потрачено 600 при лимите 1000. Два запроса читают 600, каждый хочет добавить 300.
Оба расчёта дают 900 и разрешают расход. Если commit не защищает прочитанное состояние,
в базе окажется 1200. Interlocked для записи отдельного числа не делает атомарной всю операцию
«прочитать — проверить — записать». Опыт в AcceptanceChecks воспроизводит именно этот порядок
через сигналы, не через случайные задержки.

Lock вокруг проверки и записи исправляет опыт с одним общим объектом в одном процессе. У двух
экземпляров API разные lock. В БД нужен согласованный протокол: например, условное изменение
строки бюджета по version вместе с расходами/receipt/outbox в одной транзакции, либо подходящий
уровень изоляции и обработка конфликтов выбранного провайдера. Каждая успешная операция,
влияющая на бюджет, должна участвовать в этом протоколе, включая изменение самого лимита.

Если храните spent как агрегат, обновляйте его в той же транзакции и проверяйте сверкой с расходами.
Если вычисляете SUM, защищайте от изменения набора строк между чтением и commit; concurrency token
на произвольном Expense не защищает вставку другой строки. Для нескольких бюджетов задайте стабильный
порядок доступа. При конфликте повторяют всю операцию на новом состоянии, с ограниченным числом попыток.
Возврат управляемого busy допустим; частичный commit и молчаливый перерасход — нет.
[Конкуренция EF Core](https://learn.microsoft.com/en-us/ef/core/saving/concurrency),
[транзакции](https://learn.microsoft.com/en-us/ef/core/saving/transactions).

## Решение, которое можно пересмотреть

ADR фиксирует один существенный выбор: контекст, рассмотренные варианты, решение, последствия и статус.
Например, SQLite достаточна для локальной сдачи, поскольку установка проста, а гонки проверяются на
настоящих файлах. Цена — ограничения конкурентной записи и отдельная работа при переносе на серверную
СУБД. Из этого следуют испытание двух процессов и запрет выдавать локальный lock за распределённую защиту.

Другое ADR описывает хранение потраченной суммы: вычисляемый SUM или поддерживаемый агрегат.
В нём должны быть схема атомарного изменения, способ восстановления и данные измерения, если выбор
обоснован скоростью. Изменившееся решение оформляют новой записью со ссылкой на прежнюю.
[О составе ADR](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record).

## План испытаний и прослеживаемость

Для каждого требования укажите идентификатор, проверку, уровень и свидетельство. Unit-тест чисел
не заменяет HTTP-проверку owner; HTTP-тест с подменой хранилища не доказывает транзакцию SQLite.
В L08 дана матрица CAP-01..CAP-10. Добавьте отрицательный контроль: специально нарушьте условие
в отдельной рабочей копии и убедитесь, что нужный тест перестал проходить по ожидаемой причине.

Нагрузка должна отвечать на вопрос о выбранной системе. Зафиксируйте CPU/RAM/runtime, объём БД,
прогрев, параллелизм, число запросов и распределение задержек. Ошибки учитываются отдельно от latency;
100 быстрых отказов не означают быстрый сервис. Сначала сохраните baseline, затем меняйте один фактор.
Нельзя обещать универсальную скорость по одной локальной машине или запуску с отладчиком.

Наблюдаемость связывает HTTP operation с commit и фоновой доставкой. Для метрик используйте ограниченные
наборы меток; user ID, BatchId и произвольная категория не должны создавать безграничную cardinality.
Логи не содержат паролей, bearer или полных пользовательских payload. При отказе по бюджету клиент
получает стабильный код причины, а оператор — достаточно сведений о выполнении без чужих данных.

## Передача проекта

Другой человек должен получить исходники, закреплённые зависимости, конфигурационный пример без секретов,
команды миграции/запуска, demo input, результаты испытаний и runbook. В README укажите проверенные ОС,
порты и пути состояния. Успешная CI-сборка и успешный запуск опубликованного приложения — разные факты.

В review сначала ищите нарушения договора, потерю данных и прав; затем ошибки отмены, ресурсов и
конкуренции; после этого читайте структуру и имена. Замечание должно содержать сценарий и последствие.
«Мне не нравится LINQ» не помогает; «этот Count повторно открывает одноразовый источник» проверяется.

Типичные ошибки: считать число библиотек мерой готовности; начать с полной смены архитектуры;
проверять лимит только в UI; добавлять receipt до проверки всех групп; забыть update-путь;
хранить release и mutable state вместе; ссылаться на зелёные тесты другой версии commit.
