# 60. Проверка знаний и дальнейший маршрут

**Результат:** вы читаете незнакомый C#-код, проверяете предположения, находите дефект и самостоятельно
выполняете изменение требований. Нужны главы 01–59 и собственная реализация L08.
Запускаемый опыт — [AcceptanceChecks](../../examples/Capstone/README.md).

## Что считать освоением

Прочитанная глава, запускаемый пример и самостоятельно сделанное изменение — разные свидетельства.
Для каждой темы используйте шкалу: 0 — не объясняю; 1 — узнаю термин; 2 — предсказываю поведение и
привожу контрпример; 3 — меняю реализацию и подтверждаю договор тестом. Сохраняйте конкретный файл,
commit или диагностический отчёт. Число просмотренных страниц не заменяет эти свидетельства.

Основное ядро нужно всем ролям: типы, null, коллекции, исключения, ресурсы, async, инструменты и тесты.
Глубина движка Unity, мобильного lifecycle или конкретной СУБД зависит от работы. Закончив книгу,
вы получаете маршрут и практику; готовность к роли подтверждаете самостоятельным проектом выбранной
ветки. Компиляция примеров курса не является сертификатом выполнения вашего проекта.

## Как читать незнакомый проект

1. Найдите solution, global.json, target frameworks, package locks и команды проверки.
2. Найдите вход операции: CLI, endpoint, event handler или worker. Запишите ожидаемый результат.
3. Проследите модель данных, владельцев ресурсов, границы auth, транзакции и внешние вызовы.
4. Прочитайте тесты выбранного сценария и найдите отсутствующую границу.
5. Воспроизведите один успешный случай и один отказ. Только затем меняйте код.

Упражнение на чужом коде: откройте LedgerService.Import в examples/Web. Найдите источник owner,
момент вычисления fingerprint, проверку receipt, начало транзакции, создание outbox и commit.
Проверьте, что происходит при конфликте второй строки. Затем найдите, какие части понадобится
дополнить для бюджета. Не переносите метод целиком в UI и не добавляйте отдельный SaveChanges
после уже завершённого commit ради «ещё одной проверки».

## Разбор ошибки повторного перечисления

Предположим, перед бюджетным расчётом добавили диагностику:

```csharp
// Намеренно ошибочный фрагмент для одноразового IEnumerable.
int count = incoming.Count();
var decision = BudgetPolicy.Preview(limit, spent, incoming);
```

Array скрывает проблему: его можно пройти повторно. Но IEnumerable не обещает ни кеширование,
ни одинаковый результат следующего обхода. Источник может читать поток, обращаться к БД или иметь
побочный эффект. В OnePass второй GetEnumerator бросает исключение. Это делает дефект наблюдаемым
без сети и случайного времени. Правильное место счётчика — тот же ограниченный обход; материализация
тоже возможна, если заранее ограничены объём и lifetime источника.
[CA1851 и повторное перечисление](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1851).

```text
python tools/verify_capstone.py
```

Сначала проходят 47 проверок. Потом runner запускает намеренные дефекты strict-boundary и
double-enumeration и требует **ожидаемого отказа** с конкретной причиной. Первая мутация меняет <=
на < и ломает точную границу 2000; вторая ломает одноразовый источник. Ошибка компиляции или другая
случайная ошибка не считается успешным обнаружением. Рабочая BudgetPolicy не изменяется.

Отдельный опыт воспроизводит два снимка 600 и итог 1200 при лимите 1000. После локального lock
принимается ровно один расход и получается 900. Объясните, почему это исправление ещё не является
решением для двух процессов и БД. Граница доказательства важнее слова «потокобезопасно».

## Изменение требований после сдачи

В L08 есть обязательный CR-01: редактирование суммы расхода должно сохранять месячный лимит.
Прежний update API из L06 уже умеет version; теперь он должен участвовать в защите бюджета.
Положительная delta расходует остаток, отрицательная освобождает его. Старый ExpectedVersion
отклоняется, повтор update не должен снова менять агрегат или отправлять второй эффект.

До реализации напишите влияние изменения на модель, auth, миграцию, кеш, фоновые события, UI и тесты.
Отдельно проверьте гонку update/import. Нельзя просто вызвать Preview со всей новой суммой: старая
сумма уже включена в spent. Нельзя также позволить отрицательный расход в исходном контракте импорта
ради удобства вычисления delta. Это разные входные договоры.

Порядок работы: уточнить примеры → сохранить failing test → изменить минимальную границу →
прогнать связанные сценарии → проверить publish → обновить инструкцию и ADR при необходимости.
Если выяснилось, что условие неоднозначно, запишите принятое решение и его влияние до большого рефакторинга.

## Поиск ответа и техническое обсуждение

Сформулируйте точный вопрос: API, target/runtime, provider, версия и минимальный вход. Начните с
официальной документации и сигнатуры, затем воспроизведите утверждение в маленьком проекте.
Различайте гарантированный договор и деталь текущей реализации. Issue другого runtime или старый
пример может подсказать направление, но не заменяет проверку вашей версии.
[Спецификация C#](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/),
[справочник .NET API](https://learn.microsoft.com/en-us/dotnet/api/).

На review и собеседовании полезен ход рассуждения: наблюдение, гипотеза, опыт, вывод и ограничения.
Если ответ неизвестен, объясните, как его проверите. Не выдумывайте устройство GC или SQL-плана
ради мгновенного ответа. Умение уменьшить задачу и исправить своё предположение — рабочий навык.

## Следующий цикл практики

Составьте список пробелов по карточкам и evidence L08. Выберите три, которые мешают вашей роли.
На каждый задайте маленькое изменение, критерий и дату повторной проверки. Например: добавить
отмену загрузки WPF и доказать отсутствие обновления закрытого экрана; проверить reconnect клиента;
снять план SQL на целевом провайдере; экспортировать Godot-проект и испытать ввод на устройстве.

Для backend углубляйте выбранную СУБД, auth и эксплуатацию; для desktop — dispatcher, lifecycle,
доступность и установку; для mobile — реальные устройства, permissions, offline и ограничения фоновой
работы; для игр — цикл движка, память, физику и профиль кадра; для вычислений — численную ошибку,
данные и воспроизводимость. В главах 50–58 отмечено, что проверено в курсе, а что требует этих сред.

Повторяйте цикл «прочитал чужой код → изменил требование → получил review → измерил результат».
После обновления SDK или библиотеки сверяйте breaking changes и прогоняйте собственные контракты.
Сохранение единого PDF помогает повторению, но рабочее свидетельство — воспроизводимый проект и история решений.
