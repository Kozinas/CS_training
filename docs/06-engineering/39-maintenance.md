# 39. Практикум сопровождения

**Результат:** вы принимаете незнакомый код, воспроизводите дефект, исправляете его с тестом,
сохраняете оговорённую совместимость и передаёте проверяемый результат на review.
Нужны главы 36–38. Это сквозной кейс сопровождения; лабораторная L05 посвящена данным в 40–43.

## Заявка на исправление

«Расход на 100 единиц иногда согласовывается автоматически ровно через 30 минут после подачи.
По договору после наступления дедлайна требуется исход Expired. Заявки из будущего нужно отличать
от обычного превышения лимита. Для travel вводится лимит 500, общий лимит остаётся 1000».

Слова «иногда» недостаточно для исправления. Уточните наблюдаемые входы и ожидаемый исход:

| Сумма / категория | Возраст | Исход |
| --- | --- | --- |
| 100 / food | 30 минут минус один tick | AutoApproved |
| 100 / food | Ровно 30 минут | Expired |
| 100 / food | 30 минут плюс один tick | Expired |
| 100 / food | Минус одна секунда | FutureSubmission |
| 500 / travel | 0 | AutoApproved |
| 500.01 / travel | 0 | ManualReview |
| 500.01 / food | 0 | AutoApproved |

Интервал допустимого возраста: `[0, MaximumAge)`. Сначала определяется будущее/просрочка,
затем сумма: старая заявка на большую сумму всё равно Expired. Сравниваются моменты DateTimeOffset,
поэтому разные offset одного момента не меняют возраст. Правила представлены в
[PolicyTests](../../examples/Engineering/ReviewRules.Tests/PolicyTests.cs).

## Минимальное воспроизведение

Готовая библиотека уже содержит исправление. Чтобы изучить дефект, запустите из корня:

```powershell
python tools/reproduce_boundary.py
```

Скрипт копирует библиотеку и тесты во временную папку, меняет только `>=` на `>`,
проверяет успешную компиляцию и запускает один Exact_deadline_is_expired.
Он требует ровно один неуспешный тест с Expected: Expired и Actual: AutoApproved.
Падение restore, ошибка компиляции или случайное другое исключение не засчитывается.
Исходники курса не переписываются. Краткий отчёт сохраняется в .artifacts/engineering/boundary-repro.txt.

Это red-step: до исправления тест доказывает наличие конкретного дефекта.
Green-step — тот же тест на исходной исправленной библиотеке; его выполняет общий проверочный скрипт.
Если тест проходит с обеими версиями, он не защищает от этой регрессии.

```csharp
// Условие внутри Evaluate; остальные правила остаются прежними.
if (now - submittedAt >= MaximumAge)
    return ApprovalDecision.Expired;
```

Один символ может менять публичное поведение. Минимальный diff не освобождает от проверки границ,
но помогает отделить причину от сопутствующего рефакторинга.

## Отладчик и диагностические данные

Поставьте breakpoint в Evaluate и запустите Exact_deadline_is_expired из Test Explorer IDE.
Посмотрите submittedAt, now, MaximumAge и результат сравнения в Watch.
Проверьте Call Stack: время приходит аргументом из теста, чтения системных часов в policy нет.
Условный breakpoint на возраст 30 минут полезен, если другие сценарии создают много вызовов.
Exception breakpoint нужен для неожиданного сбоя sink, но Expired является нормальным результатом,
поэтому исключение при нём не возникает.

В сервисе при диагностике достаточно Id, EvaluatedAt, исхода и категории ошибки записи;
не нужно журналировать весь объект и чувствительные данные расхода.
События «решение вычислено» и «решение сохранено» имеют разный смысл.
Сообщение об успехе до await записи вводит оператора в заблуждение, если запись затем падает.
Счетчик CountingReviewSink поэтому увеличивается только после завершения вложенного sink.
В готовом примере отдельного логирующего sink нет; добавление structured logging — расширение задания.

## Совместимость и миграция

Раньше вызывающему коду хватало ответа CanAutoApprove. Новые сценарии требуют различать причины.
В учебном API добавлен Evaluate, возвращающий ApprovalDecision, а старый метод оставлен адаптером:

```csharp
// Метод внутри ApprovalPolicy; предупреждает о миграции.
[Obsolete("Use Evaluate to distinguish rejection reasons.",
    DiagnosticId = "CRV001")]
public bool CanAutoApprove(decimal amount, string category,
    DateTimeOffset submittedAt, DateTimeOffset now) =>
    Evaluate(amount, category, submittedAt, now)
        == ApprovalDecision.AutoApproved;
```

Wrapper не дублирует правила и сохраняет прежний смысл true; false объединяет остальные исходы.
Он наследует исправленный дедлайн. Совместимость сигнатуры не обещает сохранения дефекта.
Тест старого метода локально подавляет CRV001, остальные вызовы получают диагностику.
Потребитель с warnings-as-errors должен мигрировать либо явно разрешить эту диагностику
в своём контролируемом переходном месте.

Порядок миграции: добавить новый метод и tests → описать переход → обновить потребителей →
проверить использование старого API → отдельно согласовать его удаление в несовместимом выпуске.
Значения enum, сохранённые в данных, тоже становятся контрактом; не переставляйте их незаметно.
Учебный пакет 1.1.0 не публикуется в общий feed, настоящего предыдущего пакета 1.0.0 здесь нет.
Проверка bool-wrapper и нового API подтверждает этот пример, но не заменяет проверку ABI
с бинарным потребителем предыдущего реального выпуска.

## ADR: решение о границе правил

ADR — короткая запись архитектурного решения, сохраняющая контекст и последствия.
Она полезна, когда будущему разработчику важно знать причину, которую не видно из кода.
Пример для этой задачи:

**ADR-001. Чистая policy и явные часы. Статус: принято в учебном примере.**

Контекст: дедлайн нужно проверять без ожидания реальных 30 минут, а правила использовать в CLI
и будущем сервисе. Сохранение может завершиться ошибкой или отменой.

Решение: policy получает now и submittedAt значениями; ReviewService получает TimeProvider,
читает время один раз и ожидает IReviewSink. Лимит выбирает IApprovalLimit.
ReviewRules не зависит от Host, SQL или HTTP.

Последствия: тесты граничного времени детерминированы, вариант лимита меняется композицией;
появляются небольшой интерфейс и место сборки объектов. Стабильность сторонней стратегии,
идемпотентность хранилища и атомарность нескольких эффектов остаются отдельными договорами.

Рассмотренная альтернатива: DateTimeOffset.UtcNow внутри policy проще в первой строке кода,
но связывает тест с часами ОС. Интерфейс отдельного «сервиса получения времени» не нужен,
поскольку подходящий TimeProvider уже есть в платформе.

Не превращайте ADR в журнал всех переименований. При изменении решения добавьте новую запись
со ссылкой на заменяемую, чтобы читатель видел действующий вариант и причину перехода.

## README и описание изменения

[README примера](../../examples/Engineering/README.md) фиксирует SDK, версии пакетов,
команды restore/build/test, отдельный запуск Docker и ограничения.
Для коллеги важнее воспроизводимая команда и ожидаемый исход, чем фраза «всё работает».
Минимальное описание PR для этого кейса может выглядеть так:

> На точной границе 30 минут заявка теперь получает Expired. Добавлены различимые исходы
> Evaluate и лимит travel=500; CanAutoApprove сохранён как устаревший адаптер.
> Регрессионный тест падает на прежнем сравнении и проходит на исправленном.
> Проверены unit/HTTP/contract-сценарии и потребление локального пакета.
> PostgreSQL-проект компилируется; выполнение требует отдельного Linux Docker engine.

Это описание относится к учебному diff; реальный PR должен ссылаться на свою задачу,
коммит и фактически полученные результаты. Не копируйте статус чужого прогона как свой.

## Проверяемая готовность

Перед review последовательно проверьте:

1. Есть конкретные входы и договор для дедлайна, будущего времени и приоритета причин.
2. Тест воспроизводит дефект в компилируемой версии; исправление устраняет именно этот провал.
3. Отмена и ошибка sink не становятся успешным ответом; время берётся один раз.
4. Правило travel не продублировано в CLI; изменение исходного словаря не меняет snapshot.
5. Старый вызов и новое API проверены, влияние Obsolete и версии пакета описано.
6. Потребитель восстанавливает nupkg без ProjectReference и запускается из чистого кэша.
7. CI перечисляет реальные проверки, README и ADR соответствуют поведению, diff содержит нужные файлы.
8. Глава, упражнения и подсказки включены в единый PDF; ссылки и переносы читаемы.

Команда `python tools/verify_engineering.py` проверяет 27 unit-кейсов, 6 HTTP/contract-кейсов,
CLI, пакет, отказ locked restore, мутацию границы и отдельное Git-упражнение.
Полная команда курса — `python tools/verify.py`. Формальная готовность задания не означает,
что уже реализованы БД согласования, сетевой API или production-развёртывание: их добавляют следующие блоки.

## Практика

**39-A.** Выполните воспроизведение и найдите условие, пропустившее точный дедлайн.
Критерий: в отчёте указан нужный тест и Expired/AutoApproved; вы объясняете, почему другой timezone offset
не меняет сравнение моментов и почему Sleep не нужен.

**39-B.** Добавьте лимит meals=750 и проверьте точную границу суммы, категорию с пробелами,
отсутствующую категорию и позднее изменение конфигурационного словаря.
Критерий: старые сценарии сохраняются, новый лимит подключается в composition root,
тесты отличают новое поведение от ошибочной общей замены 1000 на 750.

**39-C.** Подготовьте изменение для независимого review: issue с шагами, минимальный red/green тест,
код, миграционную заметку, ADR и воспроизводимый локальный пакет.
Добавьте отмену во время записи и structured logging после успешного сохранения.
Критерий: другой человек выполняет README из чистой копии, получает ожидаемые результаты
и видит отдельный статус контейнерного теста; общий PDF содержит обновлённый учебный материал.
