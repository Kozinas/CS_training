# 37. Проектирование и изменение кода

**Результат:** вы меняете правило в одном месте, отделяете решения от эффектов и обосновываете
границы абстракций. Нужны главы 11–18, 29 и 36. Полный пример —
[ReviewRules](../../examples/Engineering/ReviewRules/ApprovalPolicy.cs).

## Начинайте с причины изменения

Предположим, согласование расходов было одним методом: прочитать JSON, узнать время,
проверить сумму, сохранить решение и вывести сообщение. Новое правило «для travel лимит 500»
заставляет менять метод, который одновременно знает формат файла, политику и устройство БД.
Тесту правила тоже приходится готовить файл и хранилище. Эти зависимости и есть цена изменения.

Cohesion, или связность внутри модуля, высока, когда его части служат одной задаче.
Coupling, или связанность модулей, растёт, когда изменение одного требует знать детали другого.
Количество классов само по себе ничего не измеряет: десять классов, передающих друг другу
одинаковые аргументы, могут быть труднее одного небольшого класса.

В примере выделены три разных решения:

| Элемент | Ответственность | Чего требует от окружения |
| --- | --- | --- |
| ApprovalPolicy | Выбрать исход по сумме, категории и двум моментам | Стратегию лимита |
| ReviewService | Получить время, вычислить и сохранить решение | Policy, TimeProvider, IReviewSink |
| ReviewDemo | Разобрать аргументы и показать результат | Консоль и готовую policy |

Чистая policy принимает время аргументом и не знает Host, JSON и SQL.
Service читает часы один раз: сохранённый EvaluatedAt соответствует моменту решения,
даже если запись закончилась позже. Успех возвращается после await записи.
Разделение полезно потому, что изменения формата, политики и транспорта происходят независимо.

## Композиция и Strategy

Наследование от ApprovalPolicy для каждой категории создало бы иерархию вариантов,
которые отличаются только выбором числа. Здесь объект получает маленькую стратегию IApprovalLimit.
Фабрика Standard создаёт прежний вариант; композиция ниже добавляет новую настройку:

```csharp
// Фрагмент программы с using Course.Review.
var limits = new CategoryApprovalLimit(
    new Dictionary<string, decimal> { ["travel"] = 500m },
    new FixedApprovalLimit(1000m));
var policy = new ApprovalPolicy(limits, TimeSpan.FromMinutes(30));
var now = DateTimeOffset.UnixEpoch;

Console.WriteLine(policy.Evaluate(501m, "travel", now, now));
Console.WriteLine(policy.Evaluate(501m, "food", now, now));
// ManualReview, AutoApproved.
```

CategoryApprovalLimit копирует словарь, убирает пробелы в ключах и сравнивает их без учёта регистра.
Две записи, совпавшие после нормализации, считаются ошибкой конфигурации; отрицательный лимит запрещён.
Ноль допустим и означает отсутствие автоматически разрешённых положительных сумм.
Позднее изменение переданного словаря не меняет созданную стратегию.
Fallback — самостоятельный объект: если передать свою изменяемую реализацию, её стабильность
надо обеспечить отдельно. Immutable snapshot словаря не делает неизменяемым весь граф объектов.

Договор IApprovalLimit: для допустимой категории вернуть неотрицательный лимит, без I/O
и скрытого изменения бизнес-состояния. Встроенные реализации это обеспечивают.
Произвольная реализация интерфейса всё ещё способна нарушить договор; компилятор проверяет сигнатуры,
а поведенческую подстановку проверяют contract-тесты и review.

## SOLID как вопросы к изменению

| Принцип | Полезный вопрос | Контрпример формального применения |
| --- | --- | --- |
| SRP | Какие независимые причины меняют этот модуль? | Класс на каждый оператор усложняет навигацию |
| OCP | Можно ли добавить известный вариант через явную точку расширения? | Плагинная система ради двух констант |
| LSP | Сохраняет ли реализация обещания интерфейса? | Хранилище молча перезаписывает дубликат вместо отказа |
| ISP | Требуются ли клиенту все методы зависимости? | Интерфейс с Write, SQL и UI для чистого правила |
| DIP | Зависит ли правило от деталей внешней системы? | Интерфейс на каждый private helper без внешней границы |

OCP не запрещает редактировать существующий код. Когда поменялся сам договор дедлайна,
правильно изменить policy и её тесты. LSP включает исключения, эффекты и результат,
а не только возможность присвоить объект переменной интерфейсного типа.
Возврат null там, где контракт обещал значение, нарушает подстановку даже при успешной компиляции.

## DI и место сборки приложения

Dependency injection — передача зависимостей извне. Конструктор с тремя параметрами уже использует DI,
даже без контейнера. Composition root, обычно Program, выбирает реализации и сроки жизни.
Контейнер из главы 29 автоматизирует эту сборку, но не принимает архитектурные решения.

Не передавайте IServiceProvider в policy для поиска зависимостей по требованию:
service locator скрывает реальные требования и переносит ошибки из сборки в выполнение.
Scoped sink нельзя захватить singleton-сервисом; background worker создаёт scope на работу.
Объект, созданный владельцем вручную, освобождает его владелец; ресурсы из контейнера
обычно освобождает соответствующий scope. Эти правила нужно сохранить и в тестах.

## Паттерны на реальных границах

| Паттерн | Пример или место применения | Условие корректности |
| --- | --- | --- |
| Strategy | FixedApprovalLimit и CategoryApprovalLimit | Общий смысл лимита |
| Factory | ApprovalPolicy.Standard() | Возвращает полностью готовую конфигурацию |
| Decorator | CountingReviewSink вокруг IReviewSink | Передаёт token, результат и ошибки |
| Adapter | Преобразование проверенного Expense в ReviewRequest | Не теряет Id, сумму и смысл времени |
| Observer | События из главы 14 для нескольких подписчиков | Определены срок подписки и политика ошибок |

В CountingReviewSink счётчик увеличивается после успешного await. При IOException он остаётся прежним.
Interlocked защищает только счётчик, а не вложенное хранилище. Декоратор не делает непотокобезопасный
sink потокобезопасным. Observer в памяти не обеспечивает доставку после падения процесса;
такое требование приводит к очереди или outbox, а не к дополнительному обработчику события.

Adapter в таблице — направление самостоятельного расширения. ReviewRules принимает decimal,
проверяет положительность, но не заменяет Money и парсер ExpenseLedger.Core:
правила точности валюты и допустимых сумм остаются на входной доменной границе.
Не называйте запись ReviewRecord полной транзакцией согласования: в примере нет общей БД,
идемпотентности по Id и распределённого подтверждения.

## Слои, сценарии и CQRS

Layered architecture группирует код по роли: представление, сценарии приложения, домен, инфраструктура.
Домен задаёт правила и порты, инфраструктура реализует работу с SQL/HTTP; направление ссылок
проекта должно сохранять независимость правил. Отдельная папка Domain без ограничения зависимостей
не мешает случайно добавить туда HttpClient.

Vertical slices группируют код по пользовательскому действию: Import, Review, Report.
Внутри slice рядом находятся запрос, обработчик и его проверки. Общие доменные типы можно вынести,
но не нужно преждевременно создавать универсальный обработчик всех операций.
Оба подхода совместимы: небольшой проект может иметь общую доменную библиотеку и сценарии по папкам.

CQRS разделяет команды изменения и запросы чтения. Разные модели полезны, если отчёт и изменение
имеют разные требования. На первом шаге достаточно методов ReviewAsync и GetReportAsync
с понятными эффектами. Отдельные базы, брокер и eventual consistency — дополнительные решения:
они требуют обработки задержки, повторов и восстановления. В этом примере они не нужны и не реализованы.

## Контракты, ошибки и рефакторинг

В ReviewRules неправильный аргумент — исключение программисту; Expired — обычное бизнес-решение;
IOException из sink — неуспешный внешний эффект; отмена остаётся отменой.
Если всё заменить bool, вызывающий код не отличит просроченную заявку от недоступного хранилища.
Record с init-свойствами удобен как снимок данных, однако конструктор record сам по себе
не гарантирует инварианты: ReviewService всё равно проверяет пустой Id.

Рефакторинг сохраняет наблюдаемое поведение. Изменение `>` на `>=` по уточнённому договору —
исправление поведения, поэтому его полезно отделять от перемещения методов и переименований.
Рабочая последовательность: зафиксировать существующий контракт тестами, выделить чистое вычисление,
проверить сохранение поведения, затем добавить новое правило с отдельными ожиданиями.
Не обновляйте expected только потому, что «тест теперь красный»: сначала выясните, какой договор изменён.

На code review проследите один путь целиком: аргументы → решение → await эффекта → ответ.
Проверьте владение ресурсами, точку отмены, совместимость и тест негативного исхода.
Замечание должно объяснять воспроизводимое нарушение или стоимость изменения,
а предпочтение стиля лучше закрепить автоматическим правилом.

## Практика

**37-A.** Нарисуйте зависимости ReviewDemo, ApprovalPolicy, IApprovalLimit и ReviewService.
Добавьте лимит travel=500, сохранив 1000 для остальных категорий.
Критерий: при одном времени 500/travel разрешено, 500.01/travel требует проверки,
500.01/food разрешено; CLI не содержит копии правила.

**37-B.** Напишите декоратор sink с учётом успешных записей и отдельным учётом ошибок.
Задайте, считается ли отмена ошибкой. Критерий: исходное исключение и token сохраняются,
успех считается после await, параллельные вызовы не теряют обновления счётчиков.

**37-C.** Спроектируйте адаптер от проверенного Expense к запросу согласования и добавьте
два сценария: согласование и чтение отчёта. Документируйте источник SubmittedAt.
Критерий: доменная библиотека не ссылается на консоль/HTTP/SQL; тесты подтверждают правила,
а короткая ADR объясняет выбранные слои или slices и необходимость либо отсутствие CQRS.
