# 33. Параллельные конвейеры

**Результат:** вы ограничиваете число активных операций, очередь и накопление результатов,
сохраняете порядок и завершаете всех участников при сбое. Нужны главы 25, 27 и 31–32.
Основной пример — [ImportPipeline](../../examples/Integration/PipelineCore/ImportPipeline.cs).

## Выбрать уровень управления

| Средство | Когда подходит | Что нужно решить отдельно |
| --- | --- | --- |
| Task.WhenAll | Небольшой известный набор независимых операций | Отмену группы и размер набора |
| Parallel.ForEachAsync | Одинаковая обработка большого источника с лимитом | Хранение результатов и порядок |
| PLINQ / Parallel.For | CPU-вычисления над данными в памяти | Побочные эффекты и стоимость разделения |
| Channel | Несколько стадий с очередями | Владельцев completion, ошибок и состояния |
| TPL Dataflow | Граф преобразований и маршрутизации | Лимиты блоков, связь ошибок и завершения |

Parallel.ForEachAsync принимает MaxDegreeOfParallelism и token каждой итерации.
При лимите 4 одновременно исполняется не более четырёх тел; это не ограничивает размер коллекции,
в которую вы складываете все ответы. Результаты могут завершиться в любом порядке.
В AsyncLab 33 каждая итерация пишет в свой индекс массива: общего счётчика и конкурирующих Add нет.
[Parallel.ForEachAsync](https://learn.microsoft.com/en-us/dotnet/api/system.threading.tasks.parallel.foreachasync?view=net-10.0).

PLINQ делит CPU-запрос между исполнителями. AsOrdered сохраняет логический порядок результата
ценой координации; выполнение Select всё равно может идти параллельно. Не меняйте общий List из Select.
Не передавайте async-лямбду в синхронный Parallel.ForEach: можно получить async void и потерять ожидание.
Для маленькой коллекции обычный цикл нередко быстрее из-за отсутствия накладных расходов.

## Backpressure — ожидание свободного места

Channel объединяет асинхронные записи и чтения. У bounded channel есть ёмкость.
FullMode.Wait заставляет WriteAsync ждать, когда потребитель освободит место: это backpressure.
DropOldest/DropNewest/DropWrite допустимы для некоторых потоков телеметрии, но не для финансовых записей.
TryWrite возвращает false, если запись сейчас невозможна; игнорировать этот результат нельзя.
[Channels](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels).

```csharp
// Фрагмент создания очереди; Channel входит в .NET 10.
var queue = Channel.CreateBounded<byte[]>(
    new BoundedChannelOptions(8)
    {
        SingleWriter = true,
        FullMode = BoundedChannelFullMode.Wait
    });
```

SingleWriter/SingleReader — обещания вызывающего о числе одновременных участников, а не блокировки,
которые исправят неверное использование. AllowSynchronousContinuations оставляем по умолчанию false,
чтобы запись не заставляла неожиданно выполнять код читателя на том же стеке.
Reader.ReadAllAsync завершает перечисление после закрытия writer и чтения накопленных элементов.
Канал в памяти не является долговечной очередью: при падении процесса его содержимое теряется.

## Схема L04

```text
ограниченное чтение NDJSON
          │
          ▼
окно допуска W → очередь C → P обработчиков → очередь C
          ▲                                      │
          └── освобождение слота ← упорядоченный сборщик
                                                  │
                                         план нового состояния
                                                  │
                                     одна замена checkpoint
```

NDJSON содержит один JSON-объект на физической строке. Такой источник можно читать частями,
не загружая весь документ. Схема состояния остаётся JSON версии 1 из L03.
[BoundedLines](../../examples/Integration/PipelineCore/BoundedLines.cs) ограничивает байты строки,
всего входа и число строк **во время чтения**. Проверка длины после неограниченного ReadLineAsync
происходила бы слишком поздно: огромная строка уже заняла бы память.

Producer присваивает строкам номера. Обработчики независимо разбирают и проверяют строку.
Collector единолично меняет словарь расходов и применяет результаты в порядке номеров.
Поэтому при конфликте Id выигрывает первая корректная строка входа, а не самый быстрый worker.
Domain Expense неизменяем, а изменяемый Dictionary не передаётся обработчикам.

## Почему двух ограниченных очередей недостаточно

Представьте, что строка 1 обрабатывается минуту, а строки 2–100000 — быстро.
Collector читает их, освобождает очередь и складывает в pending, ожидая 1.
Обе очереди имеют размер 8, но pending растёт почти до размера файла.

В примере SemaphoreSlim выдаёт максимум W разрешений. Producer получает разрешение до записи задания;
Collector возвращает его только после **упорядоченного применения** результата.
Если строка 1 задержалась, дальше W строк не уйдёт. Capacity ограничивает отдельную очередь,
Window — весь участок от допуска до применения. Workers ограничивает вычислителей.

При максимальной длине строки L, ограничении состояния S и первых E ошибках память имеет порядок
O(W × L + S + E), плюс фиксированные буферы, P задач и представление сохраняемого состояния.
Читатель может заранее иметь ещё одну строку и свой буфер на 4096 байт.
Это оценка структур, а не точное число байтов GC: есть объекты, строки, таблицы и временная сериализация.
Число исходных строк N не создаёт N задач и не добавляет N записей в журнал ошибок.

Малое W может снизить параллелизм, а большое — увеличить память и время ожидания.
При W=1 результат остаётся верным и работа становится последовательной.
Медленная ранняя запись задерживает применение последующих: это цена детерминированного порядка.

## Ошибки, completion и отмена

У каждой очереди должен быть понятный владелец закрытия. Producer закрывает jobs в finally.
Координатор ждёт **всех** workers и затем закрывает results. Один worker не должен закрывать общую очередь,
пока остальные ещё пишут. Collector читает её до конца и проверяет отсутствие незавершённого pending.

Различаются два класса ошибок:

- Ошибка записи — данные результата: invalid_json, invalid_amount, id_conflict и т. п.
  Она учитывается в отчёте и не отменяет остальные записи.
- Ошибка инфраструктуры или нарушение лимита — сбой всей операции.
  Первый такой сбой сохраняется, общий CTS отменяет заблокированные чтения, записи и обработчики.
  Все участники ожидаются через WhenAll; затем исходная ошибка пробрасывается наружу.

Если бы код только ждал WhenAll, упавший consumer мог бы оставить producer навсегда заблокированным
на заполненной очереди. Если бы он сразу выбросил исключение, оставшиеся задачи могли бы продолжить
использовать уже освобождённые Stream и SemaphoreSlim. Нужны обе части: отменить и дождаться.
При одновременном сбое и внешней отмене этот пример отдаёт приоритет сохранённой инфраструктурной ошибке.

Для CPU-парсинга запускается фиксированное число Task.Run, а не задача для каждой строки.
Не создавайте Task.Run с уже отменённым token для стадии, чей finally обязан закрыть очередь:
делегат может вообще не начаться. В примере отмена передаётся внутрь участника.

## Повтор, poison record и завершение потока

IRowProcessor должен быть безопасен для параллельного вызова и повторения. Только явно обозначенный
TransientWorkException повторяется до Attempts, с задержкой и тем же token.
После исчерпания попыток строка получает retry_exhausted. JSON-парсер не выбрасывает эту ошибку:
неправильные данные повторять бессмысленно; проверки используют управляемую подмену обработчика.
Живой сервис должен добавить backoff/jitter и учитывать суммарный deadline из главы 28.

Нормальный EOF закрывает вход и позволяет очередям опустеть. Внешняя отмена в L04 прерывает текущую
работу и отменяет весь ещё не сохранённый план. Это разные протоколы завершения.
Для drain при остановке daemon нужны два сигнала: прекратить приём новых заданий, затем до отдельного
срока дождаться принятых; после срока — abort. Не используйте один уже отменённый token для обоих шагов.

## Периодическая работа и TPL Dataflow

PeriodicTimer позволяет одному циклу ждать тиков через WaitForNextTickAsync(token).
Если тело заняло дольше периода, тики объединяются, а не создают неограниченную очередь запусков.
Одновременно ждать следующий тик должен один потребитель. await тела внутри цикла предотвращает
наложение запусков; обычный callback Timer может запускаться повторно до завершения предыдущего.
[PeriodicTimer](https://learn.microsoft.com/en-us/dotnet/api/system.threading.periodictimer?view=net-10.0).

TPL Dataflow предлагает TransformBlock, ActionBlock и связи между ними.
BoundedCapacity ограничивает принятые сообщения, MaxDegreeOfParallelism — работу блока,
EnsureOrdered — порядок выходов. SendAsync нужен, когда следует ждать место; Post может отказать.
PropagateCompletion передаёт завершение вниз по связи, но не заменяет общий протокол отмены всего графа.
Это обзор альтернативы; L04 реализована на Channels и отдельного Dataflow-приложения не содержит.
[TPL Dataflow](https://learn.microsoft.com/en-us/dotnet/standard/parallel-programming/dataflow-task-parallel-library).

## Практика

**33-A.** Выполните AsyncLab 33. Ожидаются две строки `0,1,4,9`.
Измените лимит Parallel.ForEachAsync с 2 на 1: значения должны сохраниться.
Критерий: объяснено, почему порядок массива определяется индексом, а не очередностью завершения.

**33-B.** Реализуйте producer/consumer для 1000 чисел: C=2, P=3, результат — квадрат каждого числа.
Проверьте ровно 1000 результатов, отсутствие повторов/пропусков и остановку при ошибке consumer.
Критерий: нет Task на каждый элемент; исключение не оставляет producer в ожидании заполненной очереди.

**33-C.** Добавьте восстановление порядка и окно W=4; удерживайте результат 1 управляемым сигналом,
дайте 2–4 завершиться. До освобождения 1 нельзя допустить 5; после сигнала все 1000 чисел проходят.
Критерий: тест проверяет предел по счётчику допуска, отмену при заполненных очередях и join участников.
