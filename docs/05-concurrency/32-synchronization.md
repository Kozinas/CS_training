# 32. Потоки и синхронизация

**Результат:** вы воспроизводите гонку, выбираете примитив синхронизации и обосновываете владение
изменяемым состоянием. Нужны главы 12, 20, 25 и 31.
Пример — [SharedState](../../examples/Integration/AsyncLab/SharedState.cs), режим AsyncLab 32.

## От потока к общему состоянию

Thread — отдельный исполнитель с собственным стеком. ThreadPool переиспользует потоки и обслуживает
задачи, таймеры и продолжения. Task.Run обычно отправляет работу в этот пул. Создавать Thread для каждого
запроса дорого; отдельный поток оправдан для специального длительного блокирующего цикла или API с привязкой к потоку.

Объекты в куче могут быть доступны нескольким потокам. Даже если чтение/запись поля int атомарны,
`value++` содержит чтение, вычисление и запись. Два исполнителя могут прочитать одно значение
и записать одинаковый результат: одно обновление потеряется.

```text
Поток A: прочитать 0 ───────────────→ записать 1
Поток B:             прочитать 0 ──────────────→ записать 1
Итог: 1 вместо 2
```

LostUpdate в примере использует Barrier: оба специально созданных потока сначала читают,
затем оба проходят барьер и записывают. Результат воспроизводим без случайного расписания.
Барьер служит постановке эксперимента; он не исправляет read-modify-write.

## lock защищает инвариант

Защищайте всю последовательность, которая должна наблюдаться как единое изменение.
Например, перевод между счетами меняет два остатка; два независимых атомарных присваивания
не делают перевод атомарным. Чтение согласованного снимка должно пользоваться тем же протоколом.

```csharp
// Члены класса; System.Threading.Lock доступен в .NET 9+ / C# 13+.
private readonly Lock gate = new();
private int count;

public void Add()
{
    lock (gate) count++;
}

public int Count
{
    get { lock (gate) return count; }
}
```

Если статический тип выражения — System.Threading.Lock, компилятор использует EnterScope/Dispose.
Для обычного object lock основан на Monitor.Enter/Exit с try/finally.
Не приводите Lock к object: это меняет механизм синхронизации и может нарушить общий протокол.
Внутри lock нельзя await. [Семантика lock](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/lock).

Объект блокировки должен быть приватным и стабильным: не this, не typeof(T), не строковый литерал.
Удерживайте блокировку коротко. I/O, пользовательский callback и событие внутри неё
могут надолго остановить других или войти обратно в объект в момент нарушенного инварианта.

## Видимость памяти и атомарность

Компилятор и процессор могут менять порядок независимых обращений к памяти. Без синхронизации
другой поток не обязан наблюдать связанные изменения в ожидаемом порядке.
Вход и выход из lock задают правила публикации; Interlocked и Volatile имеют собственные гарантии.
Потокобезопасность нельзя вывести только из того, что тест несколько раз прошёл.

| Средство | Типичная задача | Что оно не обещает |
| --- | --- | --- |
| Interlocked.Increment/Exchange/CompareExchange | Атомарная операция над одним значением | Транзакцию над несколькими полями |
| Volatile.Read/Write, volatile | Упорядоченное чтение/публикация отдельного поля | Атомарность `++`, согласованный снимок графа |
| lock / Monitor | Короткое синхронное изменение инварианта | Ожидание с await |
| SemaphoreSlim | Ограничение числа входов; WaitAsync | Привязку разрешения к потоку, автоматический Release |
| Mutex | Исключение между потоками/процессами ОС | Удобное асинхронное ожидание |

CompareExchange сравнивает старое значение и при совпадении заменяет его. Цикл CAS должен
повторять вычисление при конфликте, не выполнять необратимые эффекты до успешной замены.
Volatile.Write флага после подготовки данных и соответствующее Volatile.Read позволяют задать публикацию,
но изменяемые опубликованные данные всё ещё требуют отдельного протокола.
Наивный spin-loop расходует ядро; для ожидания предпочитайте сигналы или задачи.
[Volatile](https://learn.microsoft.com/en-us/dotnet/api/system.threading.volatile?view=net-10.0),
[модель памяти runtime](https://github.com/dotnet/runtime/blob/main/docs/design/specs/Memory-model.md).

## Ожидание без удержания потока

```csharp
// semaphore создан владельцем как new SemaphoreSlim(4, 4).
await semaphore.WaitAsync(token);
try
{
    await SendAsync(token);
}
finally
{
    semaphore.Release();
}
```

try начинается **после** успешного WaitAsync. Если ожидание отменено до входа,
разрешение не получено и Release делать нельзя. Освобождать сам SemaphoreSlim можно,
когда все пользователи завершились. Лимит в 4 не ограничивает миллион заранее созданных ожидающих Task:
для ограничения очереди нужна схема следующей главы.

Monitor.Wait освобождает монитор и блокирует поток до сигнала с повторным захватом.
Условие проверяют в while под тем же монитором; Pulse/PulseAll лишь сигнализирует, что состояние могло измениться.
Это протокол condition variable, а не сохранённое сообщение. Для асинхронного обмена удобнее Channel.
Mutex имеет владение потоком; при AbandonedMutexException защищённое состояние могло остаться повреждённым.

## Deadlock, порядок и повторный вход

Если A держит lock X и ждёт Y, а B держит Y и ждёт X, обе операции остановятся.
Задайте единый порядок захвата, например по неизменяемому Id ресурса; все пути обязаны его соблюдать.
Другая стратегия — один владелец состояния и передача ему сообщений.
Тайм-аут помогает обнаружить ожидание, но не исправляет неверную модель владения.

Monitor и Lock допускают повторный вход того же потока. Это не означает безопасность reentrancy:
callback может прочитать объект посередине изменения. Сначала восстановите инвариант,
выйдите из блокировки, затем уведомляйте внешних подписчиков.
Метод, безопасный для двух потоков, не обязательно безопасен для повторного вызова из самого себя.

ConcurrentDictionary обеспечивает атомарность отдельных операций, например TryAdd.
Пара ContainsKey + присваивание не становится общей атомарной операцией.
Фабрики GetOrAdd/AddOrUpdate могут вызываться несколько раз и вне внутренней блокировки;
не помещайте в них отправку платежа или другое действие, которое нельзя повторить.
Неизменяемый снимок убирает гонки чтения самого снимка, но публикация новой ссылки остаётся отдельной операцией.

## AsyncLocal и данные запроса

ThreadLocal привязан к физическому потоку: после await работа может продолжиться на другом.
AsyncLocal хранит значение в логическом ExecutionContext; оно обычно проходит через await и Task.Run.
Так переносят correlation id, культуру и контекст диагностики.
Изменение значения в дочернем async-потоке не является способом вернуть значение родителю.

`AsyncLocal<List<T>>` не клонирует список: несколько контекстов могут держать ссылку на один изменяемый объект.
Предпочитайте небольшие неизменяемые значения, ограничивайте область через scope и восстанавливайте прежнее
значение в finally. ConfigureAwait(false) не подавляет этот перенос контекста.

## Практика

**32-A.** Запустите режим 32. Ожидаются `lost=1`, `atomic=4000`, `locked=4000`.
Нарисуйте порядок двух чтений и двух записей в LostUpdate.
Критерий: объяснена разница между атомарной записью int и атомарным увеличением.

**32-B.** Создайте счёт с балансом 100.00 и потокобезопасным TryWithdraw.
Две операции одновременно снимают 70.00: ровно одна успешна, итог 30.00.
Критерий: проверка достаточности и изменение входят в одну критическую секцию;
чтение Balance согласовано с записью; исход проверки не зависит от победившего потока.

**32-C.** Добавьте TransferTo для двух счетов и встречные переводы по 1.00.
У каждого счёта изначально 100.00; после 100 встречных переводов остатки снова 100.00 и 100.00.
Проверьте перевод самому себе и недостаток денег. Критерий: единый порядок блокировок,
сохранение общей суммы, отсутствие callbacks под lock и завершение теста за заданный предел времени.
