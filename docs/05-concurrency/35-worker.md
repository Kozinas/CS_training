# 35. Практикум фонового обработчика

**Результат:** вы соединяете ограниченный конвейер с Generic Host, сохраняете совместимое состояние
и останавливаете обработку без оставшихся задач. Нужны главы 29–34 и L03.
Договор — [L04](../../labs/04-background-pipeline/README.md), реализация —
[PipelineWorker](../../examples/Integration/PipelineWorker/Program.cs).

## От библиотеки к приложению

PipelineCore отвечает за чтение строк, независимую обработку и упорядоченное применение результатов.
FileImportJob владеет файлами, блокировкой и фиксацией. ImportWorker запускает одну работу внутри Host.
Program разбирает аргументы и собирает зависимости. Domain Core остаётся независимой от потоков,
Host и файлов: правила корректного Expense не меняются из-за добавления конкурентности.

```text
Program / System.CommandLine
           │
       Generic Host
           │
       ImportWorker (BackgroundService, singleton)
           │ scope одной работы
       FileImportJob → ImportPipeline → JsonRowProcessor
           │                             │
      checkpoint                      Expense
```

Этот Host выполняет один файл и завершается. Это удобная законченная учебная единица
с жизненным циклом BackgroundService; бесконечный daemon и установка службы ОС остаются расширениями.
Несколько workers внутри конвейера не означают несколько конкурентных владельцев checkpoint.

## BackgroundService и scope

ExecuteAsync представляет время жизни фоновой операции. В **.NET 10** весь этот метод запускается
в фоне; нельзя полагаться на синхронный участок до первого await как на блокирующую инициализацию Host.
Если готовность должна предшествовать запуску зависимостей, задайте явную фазу StartAsync или lifecycle hook.
[Изменение .NET 10](https://learn.microsoft.com/en-us/dotnet/core/compatibility/extensions/10.0/backgroundservice-executeasync-task).

Hosted service регистрируется как singleton. Scoped-зависимости нужно разрешать в созданном scope,
а не захватывать в его конструкторе. У каждой логической работы должен быть собственный scope.

```csharp
// Фрагмент ExecuteAsync; scopes — IServiceScopeFactory.
await using var scope = scopes.CreateAsyncScope();
var job = scope.ServiceProvider.GetRequiredService<FileImportJob>();
PipelineReport report = await job.ExecuteAsync(stoppingToken);
```

await using дождётся асинхронного освобождения сервисов scope.
JsonRowProcessor зарегистрирован singleton, потому что он не хранит изменяемого состояния отдельной записи
и допускает конкурентные вызовы. При добавлении изменяемого парсера или клиента проверьте этот договор заново.
[Scope в фоновой службе](https://learn.microsoft.com/en-us/dotnet/core/extensions/scoped-service).

## Фиксация и повторный запуск

FileImportJob открывает state.json.lock с FileShare.None и удерживает handle на время чтения,
вычисления и замены состояния. Другой процесс, соблюдающий этот договор, получает ошибку I/O.
Затем проверяется старый JSON checkpoint из L03. Повреждённое состояние никогда не считается пустым.

В процессе чтения конвейер строит ограниченный по MaxRecords кандидат в памяти.
Корректные новые записи добавляются, эквивалентные Id считаются duplicates, конфликт сохраняет прежнее значение.
При нормальном EOF и завершении всех стадий кандидат сериализуется и заменяет checkpoint через временный файл.
Если добавлений нет, файл не переписывается. Ошибка строки не запрещает сохранить другие правильные строки;
ошибка I/O, превышение лимита или отмена до фиксации запрещает всю замену.

```text
прочитать прежнее состояние → обработать файл → дождаться всех
            → проверить отмену → временный файл → заменить checkpoint
```

После замены файла нельзя обещать откат из-за поздней отмены. Если процесс погиб между заменой и печатью отчёта,
повторный запуск найдёт уже принятые Id и не добавит их повторно.
Сетевые эффекты внутри processor таким способом не откатываются; пример не выполняет их.
Для долговечного приёма заданий и согласования с БД понадобятся транзакции, idempotency key и outbox в следующих блоках.

## Остановка и ошибки

При EOF очереди естественно опустошаются. При Host.StopAsync stoppingToken отменяется,
конвейер будит ожидающих и дожидается участников, после чего scope и файлы освобождаются.
ShutdownTimeout Host установлен в 10 секунд. Это предел ожидания, а не принудительный останов
произвольного чужого кода; IRowProcessor обязан соблюдать token.

ImportWorker классифицирует ожидаемые исходы, записывает JobOutcome и вызывает StopApplication
для завершения конечной работы. JobCompletion использует TaskCompletionSource с асинхронными продолжениями.
Program читает результат после RunAsync; отчёт появляется только после успешной фиксации.
Необработанная ошибка фоновой службы по умолчанию останавливает Host; Ignore не перезапускает упавший цикл.

| Код | Значение | stdout |
| --- | --- | --- |
| 0 | Все строки приняты или признаны дубликатами | JSON-отчёт |
| 4 | Есть отклонённые строки, остальные обработаны | JSON-отчёт |
| 2 | Неверные аргументы/лимиты | Пусто |
| 3 | Ошибка I/O, checkpoint или лимита входа/состояния | Пусто |
| 130 | Отмена до завершения работы | Пусто |
| 1 | Неожиданная ошибка реализации | Пусто |

Диагностика ILogger идёт в stderr; входные строки и полные исключения с потенциальными данными не печатаются.
В отчёте сохраняются первые 20 ошибок по порядку строк, общий failed и признак errorsTruncated.
Retried считает дополнительные попытки, а не исходные вызовы. По обычным JSON-данным он равен нулю.

## Проверка управляемых отказов

PipelineChecks удерживает первую строку сигналом, позволяет следующим завершиться и проверяет окно допуска.
Другие сценарии отменяют заполненные очереди, бросают IOException из worker, ломают чтение,
исчерпывают retry и останавливают настоящий Host через StopAsync.
В каждом случае проверяется, что активных обработчиков не осталось и старый checkpoint сохранился.
Произвольный Sleep не используется для угадывания порядка событий; тайм-аут теста лишь обнаруживает зависание.

```powershell
$jobArgs = @("--file", "labs/04-background-pipeline/data/mixed.ndjson",
    "--state", "work/l04/state.json", "--workers", "4",
    "--capacity", "8", "--window", "16")
dotnet run --project examples/Integration/PipelineWorker -- @jobArgs
python tools/verify_pipeline.py
```

На первом запуске ожидаются processed=6, added=2, duplicates=1, failed=3, total=2.
При повторе — added=0, duplicates=3, остальные счётчики сохраняются; checkpoint одинаков по байтам.
При P=1, C=1, W=1 решения должны быть такими же, как при 4/8/16.

## Нагрузочный опыт и пределы результата

В проверенной среде главы 34 импорт 10000 уникальных строк дал медиану 0.343 с для P=1
и 0.330 с для P=4, при C=8 и W=16. Это примерно 29117 и 30276 записей/с
с учётом запуска процесса, Host и записи файла. Использованы один прогрев и три наблюдения на вариант.
[Исходные измерения](../../examples/Integration/PerfLab/results/pipeline-2026-10-22.json).

Небольшая разница не обосновывает универсальный выбор четырёх потоков: парсинг короткий,
есть последовательный collector и стоимость запуска/файла. Увеличение P может повысить накладные расходы.
Этот опыт проверяет процедуру и сохранение результата, а не долговременную устойчивость сервиса.
Ограничения памяти обоснованы устройством очередей/окна и лимитами; точный пик RSS отдельно не измерялся.

## Практика

**35-A.** Импортируйте mixed.ndjson дважды, затем повторите в новой папке с 1/1/1.
Ожидаются одинаковые решения по строкам и одинаковые checkpoint.
Критерий: сохранены stdout, stderr и exit code; вывод журнала не ломает JSON.

**35-B.** Реализуйте договор L04 самостоятельно. Добавьте управляемый процессор,
который дважды выдаёт TransientWorkException и на третий раз возвращает Expense.
Ожидаются added=1, retried=2; постоянно ошибающийся процессор получает retry_exhausted после трёх попыток.
Критерий: повтор ограничен и отменяем; обычная неправильная сумма не повторяется.

**35-C.** Расширьте приложение до очереди нескольких файлов с drain/abort.
После запрета приёма новые файлы отклоняются, принятые завершаются до срока остановки;
после срока текущий незавершённый план отменяется. Критерий: отдельные сигналы приёма и abort,
scope на работу, последовательная фиксация общего checkpoint и проверка повторного запуска.
Готовый пример выполняет одну работу и этот daemon-режим не реализует.
