# 34. Измерение и оптимизация

**Результат:** вы находите затратный участок по наблюдениям, меняете его и подтверждаете
сохранение результата. Нужны главы 19–20, 23, 25 и 31–33.
Примеры — [AmountAlgorithms](../../examples/Integration/AsyncLab/AmountAlgorithms.cs),
[PerfLab](../../examples/Integration/PerfLab/Program.cs) и [нагрузочный эксперимент](../../tools/measure_pipeline.py).

## Сначала вопрос, затем инструмент

«Медленно» нужно превратить в измеримое утверждение: запуск CLI занимает 2 секунды,
p95 HTTP-ответа превышает 300 мс, либо импорт не успевает за поступлением записей.
Сравнивайте одинаковые данные, результат, режим сборки, runtime и ограничения нагрузки.
Изменение алгоритма, которое ускоряет программу за счёт пропуска проверки, не является эквивалентной оптимизацией.

| Метрика | Что означает | Частая ошибка |
| --- | --- | --- |
| Latency | Время отдельной операции | Забыть время ожидания в очереди |
| Throughput | Завершённых операций за интервал | Считать начатые вместо завершённых |
| p50/p95/p99 | Квантили распределения задержек | Выводить p99 по трём запросам |
| Allocated bytes | Выделения управляемой памяти | Путать с размером живой кучи |
| Working set | Физическая память процесса | Приписать весь рост утечке объектов |
| CPU time / wall time | Работа процессора / прошедшее время | Назвать любое ожидание загрузкой CPU |

Например, при последовательной регистрации 1000 задержек p95 — значение, ниже которого примерно 95% наблюдений;
нужно указать способ расчёта и учитывать незавершённые/отменённые запросы. Система под перегрузкой
может иметь быстрые успешные ответы и огромную очередь отклонённых: одно среднее скроет проблему.

## Release, прогрев и воспроизводимость

Debug, подключённый debugger, первый JIT, загрузка сборок, tiered compilation, GC и файловый кэш
влияют на измерение. Для устойчивого сравнения используйте Release, несколько итераций и описание среды.
Прогрев измеряет установившийся режим; cold start надо измерять отдельно в новом процессе.
Stopwatch подходит для длительности целого сценария, а не для одного слишком короткого вызова без контроля шума.

Не используйте GC.GetAllocatedBytesForCurrentThread для асинхронного метода с переходом между потоками:
разность может относиться к разным исполнителям. Рабочие метрики и профили должны соответствовать вопросу.
Не добавляйте GC.Collect в обычный код приложения «для уменьшения памяти» без подтверждённой причины.

## BenchmarkDotNet

В PerfLab закреплён BenchmarkDotNet **0.15.8**. Он создаёт отдельный процесс,
подбирает число повторений и отделяет прогрев от измерений. MemoryDiagnoser показывает выделения.
GlobalSetup подготавливает данные вне измеряемого участка; Benchmark возвращает результат,
чтобы измерялась полезная работа. Baseline задаёт основу сравнения, Params — размеры входа.
[Запуск BenchmarkDotNet](https://benchmarkdotnet.org/articles/guides/getting-started.html).

Здесь сравнивается извлечение последнего поля уже проверенной строки `2026-01-10;food;12.50`:
Split создаёт массив и подстроки; Span берёт срез существующей строки.
Оба варианта используют decimal и invariant culture. Это не замена полного парсера L01:
формат и бизнес-ограничения считаются проверенными до горячего участка.

```powershell
# Из корня; предварительно соберите Integration.slnx в Release.
Push-Location examples/Integration
try {
    $benchArgs = @("--filter", "*AmountBenchmarks*", "--job", "short",
        "--artifacts", "../../.artifacts/benchmarks-05")
    dotnet run --project PerfLab -c Release --no-build -- @benchArgs
} finally { Pop-Location }
```

ShortRun удобен для проверки процедуры, но недостаточен для точных обещаний скорости.
Для серьёзного сравнения уберите `--job short`, выполните несколько независимых запусков
и сохраните полные отчёты. Время измерений не должно быть порогом обычного CI-теста.

## От процесса к участку кода

dotnet-counters показывает динамику runtime-метрик: CPU, heap, GC, ThreadPool, исключения.
dotnet-trace собирает события и выборки стеков; профиль помогает найти кандидата на оптимизацию.
dotnet-dump сохраняет состояние для анализа удерживаемых объектов и стеков;
это снимок, поэтому он сам по себе не измеряет длительность метода.
[Counters](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-counters),
[trace](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-trace),
[dump](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-dump).

В этом выпуске инструменты версии **10.0.750501** установлены только в .artifacts/diagnostics.
Следующие команды PowerShell выполняются из корня после сборки примеров:

```powershell
$nuget = "examples/Integration/NuGet.Config"
$installArgs = @("dotnet-trace", "--version", "10.0.750501",
    "--tool-path", ".artifacts/diagnostics", "--configfile", $nuget)
dotnet tool install @installArgs
$trace = ".artifacts/diagnostics/dotnet-trace"
$demo = "examples/Integration/AsyncLab/bin/Release/net10.0/AsyncLab.dll"
$collectArgs = @("collect", "--profile", "dotnet-sampled-thread-time",
    "--output", ".artifacts/split.nettrace", "--", "dotnet", $demo,
    "34", "split", "5")
& $trace @collectArgs
& $trace report .artifacts/split.nettrace topN -n 8
```

Если инструмент уже установлен по этому пути, повторять install не нужно.
В версии 10 прежнее имя cpu-sampling не подходит для обычного collect на Windows;
список проверяется через list-profiles. dotnet-sampled-thread-time оценивает время по выборкам
управляемых стеков, включая ожидания: его проценты нельзя автоматически называть процентами CPU.

В собранном профиле SplitInternal занял 19.78% exclusive, SplitSum — 64.11% inclusive.
Также видны разбор decimal и ожидание GC. Inclusive включает вызванные методы,
exclusive относится к самому кадру. Это объясняет выбор кандидата Split для отдельного измерения.
[Сохранённый topN](../../examples/Integration/PerfLab/results/split-profile-2026-10-22.txt).

Для counters установите аналогично dotnet-counters той же версии и запустите:

```powershell
$counters = ".artifacts/diagnostics/dotnet-counters"
$counterArgs = @("collect", "--format", "csv", "--output",
    ".artifacts/span-counters", "--counters", "System.Runtime",
    "--", "dotnet", $demo, "34", "span", "5")
& $counters @counterArgs
```

Сбор CSV проверен. Для живого процесса можно использовать monitor --process-id с его PID.
Для dump после аналогичной установки: `dotnet-dump collect --process-id <PID>` и
`dotnet-dump analyze <путь>`; внутри анализатора начните с help, clrstack, dumpheap -stat,
затем gcroot конкретного удерживаемого объекта. Угловые скобки здесь — места подстановки,
не буквальные аргументы. Снятие и анализ dump в этом выпуске не выполнялись.
Dump может содержать входные данные и секреты процесса; храните его как диагностический артефакт с ограниченным доступом.

## Что исправлять по симптомам

При высоком CPU ищите горячие стеки и алгоритмическую сложность.
При частых GC и большом allocation rate ищите временные строки, boxing, замыкания и материализацию LINQ.
При низком CPU, растущем числе потоков и очереди ThreadPool проверьте блокировки .Result/Wait
и синхронное I/O: добавление потоков может только отсрочить starvation.
[Диагностика starvation](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/debug-threadpool-starvation).

ArrayPool требует возврата массива в finally и запрета использования после возврата.
Span уменьшает копирование, но не владеет памятью. SIMD обрабатывает несколько чисел за инструкцию,
однако требует подходящего алгоритма, обработки остатка и учёта поддержки оборудования.
Не применяйте их до обнаружения соответствующего узкого места. Начните с удаления повторной работы
и выбора подходящей структуры данных; только затем меняйте горячий участок.

## Практика

**34-A.** Запустите PerfLab и объясните Mean, Error, Allocated для Count=100 и 1000.
Критерий: записаны среда и команда, проверено равенство сумм; нет требования совпасть с таблицей по времени.

**34-B.** Соберите профиль режима `34 split 5`, найдите SplitInternal и сравните со `34 span 5`.
Ожидается исчезновение разделения строки из горячего пути. Критерий: различены inclusive/exclusive,
выборки стеков и точное CPU-время; ускорение подтверждается отдельным benchmark, а не одним процентом.

**34-C.** Выполните `python tools/measure_pipeline.py`: по 10000 записей, один прогрев и три запуска
при P=1 и P=4, C=8, W=16. Скрипт проверяет отчёт и пишет время всего процесса в .artifacts/pipeline-load.json.
Критерий: сравниваются медиана, разброс и правильность; холодный запуск каждого процесса и файловый кэш
указаны как часть опыта. Три наблюдения не выдаются за надёжный p99 или тест долговременной стабильности.
