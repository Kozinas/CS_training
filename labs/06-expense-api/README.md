# L06. ExpenseLedger API

**Вход:** главы 44–49 и выполненные правила L05. **Результат:** локальный сервис, который другой разработчик
может собрать, запустить, проверить и восстановить после остановки процесса.
Сначала реализуйте условия самостоятельно; [полный пример](../../examples/Web/README.md) используйте для сверки.

## Обязательный договор

Два пользователя имеют независимые журналы расходов. Регистрируйте их через стандартные средства Identity,
не храните пароли в открытом виде и не пишите собственную криптографию.
API использует bearer, браузерная форма — cookie и antiforgery. Все операции определяют Owner из principal.

Expense имеет Id, Date, Category, Amount и необязательную Note. Сохраняются правила L02:
ненулевой Guid, категория из ASCII-букв/цифр/_/- с первой буквой и длиной 1–32,
нормализация trim/lowercase, сумма 0.01–999999.99 с точностью до копейки. Заметка — не более 200 символов C# string.
На входе нет Owner, Version и полей Identity; неизвестные JSON-поля отклоняются.

Пакет имеет BatchId и Rows, не более 100 строк и 128 KiB HTTP-тела. Пустой массив допустим,
null-массив, null-строка и нулевой BatchId — ошибка. Порядок строк значим для fingerprint;
регистр/краевые пробелы категории и число нулей после десятичной точки суммы не меняют нормализованный пакет.
Заметка сравнивается точно, null отличается от пустой строки.

## Модель данных

| Данные | Ключ или правило |
| --- | --- |
| Пользователь | Identity Id, стандартный хеш пароля, Revision |
| Расход | Уникальные Owner + ExternalId; отдельный Sequence для пагинации |
| Квитанция | Owner + BatchId, fingerprint, added/duplicates |
| Outbox | MessageId, Owner, дельты суммы/числа, состояние доставки |
| Inbox | Уникальный MessageId одного потребителя |
| Проекция | Owner, Count, AmountMinor |

Импорт атомарен: расходы, receipt, Revision и outbox фиксируются одной транзакцией.
Если строка конфликтует, не остаются предыдущие строки этого пакета, receipt и event.
Повтор receipt после отдельного изменения суммы возвращает исходный результат импорта.

## HTTP-поведение

| Операция | Обязательный результат |
| --- | --- |
| POST /auth/register | 201 при регистрации; некорректные данные — 400 |
| POST /auth/token | 200 с токеном или 401 |
| POST /api/v1/imports | 200 с added, duplicates, replayed |
| GET /api/v1/expenses | Только свои записи, after=0, size=20 по умолчанию |
| GET /api/v1/expenses/{id} | Своя запись или 404 |
| PUT /api/v1/expenses/{id} | expectedVersion и amount; 204 при успехе |
| GET /api/v1/report | Отчёт по категориям из основных данных |
| GET /api/v1/projection | Состояние потребителя после доставки событий |

Неверный JSON/домен — 400, неправильный Content-Type — 415, большое тело — 413,
нет пригодного bearer — 401, запрет политики — 403, конфликт BatchId/Id/Version — 409.
Структурированные ошибки содержат traceId. Stack trace, SQL-параметры, пароли и чужие данные не возвращаются.
Нагрузочный лимит задаёт 429 и Retry-After; лимит Alice не должен расходовать бюджет Bob.

Страница списка имеет Rows и Next. Порядок — Sequence, размер 1–100, after неотрицательный.
Next=null означает, что дополнительной записи при чтении не было. При изменении набора между запросами
глобальный снимок не гарантируется; владелец фильтруется до Take.

Для изменения суммы клиент читает Version и передаёт ExpectedVersion. Два запроса одной версии имеют
одного победителя; чужой Id получает 404 без изменения записи. После изменения версия повышается.

## Исходные сценарии

Используйте [batch.json](data/batch.json) и команды из Web README.

| Шаг | Ожидание |
| --- | --- |
| Первый импорт Alice | added=3, duplicates=1, replayed=false |
| Тот же нормализованный пакет Alice | added=3, duplicates=1, replayed=true |
| Тот же BatchId с другой суммой | 409, записи не изменились |
| Новый BatchId с прежними расходами | added=0, duplicates=4, replayed=false |
| Тот же пакет Bob | Его собственные 3 расхода, replayed=false |
| Отчёт Alice | food: count=2, amountMinor=2000; travel: count=1, amountMinor=3000 |
| Сумма первого расхода 12.50 -> 20.50 | Version 0 -> 1; food amountMinor=2800 |
| Повтор изменения с ExpectedVersion=0 | 409; сумма 20.50 сохранена |

Отдельно создайте пакет, где первая строка новая, а вторая конфликтует с существующим Id.
После 409 первая строка отсутствует. Проверка только статуса без чтения БД недостаточна.

## Браузер и альтернативные транспорты

Razor Page показывает свои расходы и форму изменения суммы. Ошибки сохраняют введённые данные,
успех использует Post/Redirect/Get. Текст заметки кодируется; пользовательский script остаётся текстом.
Вход и изменение без правильного antiforgery-токена отклоняются. ReturnUrl не уводит на внешний сайт.

gRPC Reports.Get возвращает тот же отчёт с целыми минимальными единицами суммы.
SignalR отправляет changed группе владельца после доставки события. Клиент после уведомления перечитывает API;
уведомление не считается долговечной записью. Не разрешайте клиенту произвольно подписываться на Owner другого пользователя.

## Фоновая обработка и восстановление

Worker берёт ограниченную порцию Outbox и создаёт scope. Consumer одной транзакцией вставляет Inbox
и меняет Projection. Повтор MessageId не меняет результат. Delivered подтверждается после consumer commit.
Внедрите сбой между этими точками и покажите, что повтор завершает доставку без второго эффекта.

Воспроизводимый процессный опыт:

1. Примените миграции, запустите сервис с Worker__Enabled=false.
2. Создайте пользователя, импортируйте пакет, измените сумму. /report актуален, /projection отстаёт.
3. Остановите процесс, сохранив SQLite и key ring.
4. Запустите сервис с Worker__Enabled=true на той же БД.
5. Повторите импорт и дождитесь схождения проекции; сумма и Version должны сохраниться.

В примере producer и consumer имеют разные транзакции в одной физической БД.
Redis/брокер/OIDC и распределённый delivery — дополнительные варианты, не обязательная инфраструктура L06.
Не выдавайте local outbox за проверку работы RabbitMQ при потере сети.

## Проверки и наблюдаемость

Автоматизируйте HTTP/Identity/ownership, invalid input и лимиты, rollback/replay/concurrency,
cache revision, CSRF/XSS, readiness, OpenAPI, gRPC/SignalR и окно сбоя доставки.
Зависимость /rate должна иметь deadline, ограничение тела и отмену. Её отказ не изменяет расходы.
Логи, метрики и traces не содержат credentials. Счётчик новых фиксаций не растёт при replay.

Выполните небольшой опыт с несколькими конкурентными клиентами. Проверяйте правильность каждого ответа,
запишите параметры и измерения, отделите их от утверждений о предельной производительности.
Команда эталонного прогона из корня: `python -B tools/verify_web.py`.

## Что предъявить

1. Исходники, pinned SDK/packages, lock-файлы и миграция.
2. README с командами и обязательными настройками; отдельная команда миграции.
3. HTTP/OpenAPI-договор, ограничения cookie/bearer и negative tests двух пользователей.
4. Сценарий остановки/возобновления, проверка окна commit/ack и диагностический trace.
5. Отчёт нагрузочного опыта и список ещё не проверенных внешних интеграций.

Работа принята, если её можно воспроизвести без ручного редактирования БД и устных пояснений.
Публичный deploy не требуется; политика регистрации, MFA, recovery, глобальные квоты и хранение ключей
для production проектируются отдельно. Пример автоматизации выполняется в CI на GitHub-hosted Windows runner.
