# L05. Надёжное хранение расходов

**Цель:** заменить файловый checkpoint транзакционной БД и доказать договор повторов и конкуренции.
Нужны главы 36–43 и правила данных L02/L03. Образец — [Data](../../examples/Data/README.md).
Базовый вариант выполняется на SQLite без установки сервера или Docker.

## Что сдать

Solution с моделью, отображением БД, параметризованным импортом, CLI и автоматическими тестами.
Сдача включает две миграции, SQL их применения, данные примеров и отчёт восстановления backup.
Тесты должны работать на настоящем движке БД, а не только на List или mock DbSet.
Архитектура может отличаться от образца, если весь наблюдаемый договор сохранён.

## Среда и команды

В примере SDK 10.0.402, Microsoft.Data.Sqlite/EF Core/dotnet-ef 10.0.13, Dapper 2.1.89.
Сначала соберите [Data.slnx](../../examples/Data/Data.slnx), затем запускайте DataCli.dll:

```text
init DB
import DB BATCH_ID INPUT.json
page DB [AFTER_DATE AFTER_SEQUENCE SIZE]
report DB
update DB EXPENSE_ID EXPECTED_VERSION AMOUNT
backup DB NEW_BACKUP
integrity DB
plan DB
```

DB и NEW_BACKUP — пути файлов. Родительская папка должна существовать.
Только init создаёт новую базу; остальные команды требуют существующий файл.
Init применяет миграции и допускает повторное выполнение.
Все успешные команды пишут один JSON-документ в stdout. Ошибка пишет stderr без успешного JSON.

| Код | Смысл |
| --- | --- |
| 0 | Операция успешна |
| 2 | Неверная команда, аргумент, размер страницы или сумма обновления |
| 3 | Ошибка файла, документа или БД |
| 4 | Конфликт BatchId/ExternalId либо устаревшая версия/отсутствующий расход |
| 130 | Замечена запрошенная отмена |

## Схема и нормализация

Expenses содержит Sequence, ExternalId, Day, CategoryName, AmountMinor, Version и nullable Note.
Categories задаёт допустимые нормализованные имена; ImportReceipts хранит BatchId,
Fingerprint, Added и Duplicates. Внешний ключ запрещает ссылку на неизвестную категорию.
У ExternalId уникальный индекс; сумма, день и версия имеют CHECK.
Строка внешнего Id проходит полноценную валидацию в приложении; SQL CHECK длины не заменяет Guid.TryParseExact.

Вход — версия JSON 1 из L03, UTF-8 с допустимым BOM. Максимум 1 048 576 байт и 1000 записей
в одном пакете. Поля расхода проходят прежние правила Guid, DateOnly, категории и Money.
Сумма 0.01–999999.99 имеет не более двух знаков; в БД хранится long сотых.
Категория нормализуется trim + lowercase, формат допускает только оговорённый ASCII-набор.
Любая неверная строка теперь отклоняет весь пакет. Это явное изменение договора относительно L03.

У базы нет учебного лимита на общее число записей: ограничены один входной пакет и одна страница.
Групповой report возвращает все существующие категории с расходами; при очень большом числе категорий
публичному сервису потребуется дополнительный договор ограничения/пагинации этого отчёта.

## Идемпотентность и транзакция

BatchId — непустой Guid формата D. Fingerprint зависит от нормализованного содержимого и порядка строк.
Повтор BatchId с тем же fingerprint возвращает исходные Added/Duplicates и Replayed=true.
Изменившиеся впоследствии расходы не меняют сохранённый результат запроса.
Другой fingerprint при известном BatchId даёт batch_id_conflict без изменений.

В новом пакете неизвестный ExternalId добавляется, известный с теми же датой/категорией/суммой
считается duplicate. Совпавший Id с другими полями даёт expense_id_conflict.
Все расходы, новые категории и квитанция фиксируются одной транзакцией.
После отказа не должно оставаться ни частичного расхода, ни его новой категории, ни квитанции.
Отчёт об успехе появляется только после commit; потеря ответа разрешается повтором того же BatchId.

## Точный сценарий приёмки

Используйте новую базу. В [batch.json](data/batch.json) четыре строки и три уникальных расхода.
Сохраните один BatchId, например `10000000-0000-0000-0000-000000000001`.

| Действие | Результат |
| --- | --- |
| Первый импорт batch.json | added=3, duplicates=1, replayed=false |
| Повтор с тем же BatchId | added=3, duplicates=1, replayed=true |
| Тот же файл с новым BatchId | added=0, duplicates=4, replayed=false |
| conflict.json со старым BatchId | Код 4, batch_id_conflict |
| conflict.json с новым BatchId | Код 4, expense_id_conflict |
| Отчёт после конфликтов | food: count=2, amountMinor=2000; travel: 1/3000 |

В [conflict.json](data/conflict.json) перед конфликтом находится новый расход категории books.
Он нужен, чтобы обнаружить частичную фиксацию: после отказа в БД по-прежнему три расхода,
две категории и только квитанции успешных пакетов.

## Пагинация и обновление

Page сортирует по Day, затем Sequence. По умолчанию размер 20; явно можно передать 1–100.
AFTER_DATE имеет формат yyyy-MM-dd, AFTER_SEQUENCE — неотрицательный long.
Для первой страницы произвольного размера используйте 0001-01-01 и 0.

Результат содержит rows и next. У строки есть sequence, id, date, category, строковая amount
с двумя знаками и version. Cursor next содержит day/sequence последней строки, если набрана
полная страница; у последней страницы точного кратного размера допускается ещё один запрос с пустыми rows.
Day в next — DayNumber; для CLI преобразуйте его через DateOnly.FromDayNumber.

Update меняет только сумму. ExpectedVersion должна совпасть с текущей версией в момент записи;
проверка включается в SQL. Успех увеличивает Version на 1; конфликт не меняет сумму.
Пустой Id и недопустимая сумма отклоняются. Изменение даты/категории и удаление расхода в CLI не реализованы.

## Миграции и восстановление

Первая миграция создаёт схему без Note, вторая добавляет nullable Note.
Проверьте создание с нуля, переход первой версии со строками ко второй и повторный init.
Старые Id/суммы сохраняются, Note равен NULL. Модель не должна расходиться с snapshot миграций.
Скрипт от нулевой версии применяется к пустой базе; это не idempotent script для любой существующей базы.

Backup использует API SQLite и принимает только новый путь. Существующий файл не перезаписывается.
Для восстановления скопируйте завершённый backup под новым именем, откройте его и проверьте:
report, версии расходов, replay прежнего BatchId, историю миграций, integrity и внешние ключи.
Проверка должна выполняться после изменения исходной базы, чтобы отличить её от восстановленной копии.

## Обязательные негативные и конкурентные проверки

1. Прямые SQL-попытки нарушить UNIQUE, FK, диапазон/тип суммы, день и версию.
2. SQL-фрагмент в параметре категории не меняет структуру запроса.
3. Ошибка после INSERT и отмена перед commit откатывают весь пакет.
4. Два соединения импортируют один расход: дублей нет, результаты соответствуют BatchId.
5. Два контекста читают одну версию до барьера: один UPDATE проходит, второй получает конфликт.
6. Два CLI-процесса с одним BatchId оставляют один расходный набор и одну квитанцию.
7. Keyset не теряет строки с одинаковой датой и не сдвигается из-за вставки более раннего расхода.
8. N+1 воспроизведён счётчиком команд и устранён SQL-проекцией.

`python tools/verify_data.py` проверяет готовый образец; это не автоматическая проверка произвольной
пользовательской архитектуры. Своё решение прогоните по договору и представьте команды воспроизведения.
Проверка всего курса: `python tools/verify.py`.

## Граница результата

Выполненные проверки относятся к SQLite-файлам на Windows. Внешние PostgreSQL/SQL Server,
сетевой диск, отключение питания и прерывание native SQLite-команды токеном не проверялись.
Серверная реализация через Testcontainers — задание 43-C. Файл receipt не очищается по TTL:
удаление истории требует отдельного срока действия ключей идемпотентности.
БД не хранит мультвалютность, распределённые эффекты и outbox — они не следуют из локального commit.
