# L03. Воспроизводимая утилита импорта

**Цель:** объединить BCL, форматы, HTTP, Host и CLI, сохранив правила ExpenseLedger.Core.
Нужны главы 19–30 и L02. Образец — [ImportCli](../../examples/Integration/ImportCli/Program.cs).

## Что нужно сдать

Самостоятельную solution с библиотекой правил, адаптером формата, CLI и проверками.
Один запуск принимает один JSON-документ из файла или HTTP.
Результат — checkpoint с принятыми записями, отчёт с ошибками каждой отклонённой записи и код завершения.
Экспорт checkpoint должен быть пригоден для повторного импорта.

## Команды и конфигурация

```text
import (--file PATH | --url URL) --state PATH [--pretty]
export --state PATH --output PATH
--help
```

Пути не должны совпадать: вход/состояние и состояние/экспорт различаются.
Для HTTP разрешены HTTPS и loopback HTTP; redirects не следуются.
URL с user info отвергается. Реальная проверка TLS остаётся включённой.

appsettings задаёт Import:MaxBytes=1048576, MaxRecords=10000 и TimeoutSeconds=15.
Префикс CS_IMPORT_ с двойным подчёркиванием позволяет переопределить настройки,
например CS_IMPORT_Import__MaxRecords.
Диапазоны: 128–16777216 байт, 1–100000 записей, 1–120 секунд.
Неверная конфигурация должна обнаруживаться до изменения состояния.

MaxBytes ограничивает вход и итоговый сериализованный checkpoint; из-за отступов
канонический экспорт может оказаться больше компактного входа.
MaxRecords ограничивает и входной массив, и совокупное состояние.
Превышение итогового лимита — ошибка операции, а не разрешение молча обрезать данные.

## Формат документа

UTF-8, допустим начальный UTF-8 BOM. Верхний объект содержит ровно поля version и records.
version — целое 1, records — массив. Отсутствующие обязательные поля, records=null,
повторные имена свойств, неизвестные свойства, слишком глубокий JSON и неверные JSON-типы
дают ошибку всего документа. Комментарии и trailing comma не разрешены.

Элемент records — объект с полями id, date, category, amount, либо null.
Поля записи строковые; отсутствующие и null-поля проходят в построчную валидацию.
Число вместо строкового amount — структурная ошибка. null-элемент даёт invalid_id.

| Поле | Проверка |
| --- | --- |
| id | Guid.TryParseExact с форматом D, значение не Guid.Empty |
| date | Существующая DateOnly в yyyy-MM-dd, InvariantCulture |
| amount | ASCII-цифры, необязательная точка и 1–2 дробных знака; 0.01–999999.99 |
| category | Правила L02: trim, ASCII-буква, затем буквы/цифры/_/-, длина 1–32, lowercase |

amount не принимает знак, пробелы, запятую и exponent; ведущие нули допустимы.
Внешняя числовая строка ограничена 32 символами.
При нескольких неверных полях сообщается первая ошибка в порядке id, date, amount, category.
Номер record в отчёте начинается с 1 и относится к позиции в массиве.

## Дедупликация и конфликт

Сравнение выполняется после преобразования в Expense.
FOOD и food, 12.5 и 12.50 дают одинаковые нормализованные значения.

Новый корректный Id добавляется. Известный Id с равными датой, категорией и Money считается duplicate.
Известный Id с другими данными даёт id_conflict и не перезаписывается.
Правило действует и внутри текущего входа, и относительно прежнего состояния.

Checkpoint содержит только корректные записи с уникальными Id, версию 1,
нормализованные категории и amount с двумя дробными знаками.
Порядок экспорта определяется сортировкой Guid через comparer .NET, а не исходной позицией.

## Фиксация и повторный запуск

Сначала прочитайте и проверьте внешний документ, затем возьмите блокировку состояния,
прочитайте и проверьте прежний checkpoint, вычислите изменения и сохраните новый файл.
Файл .lock остаётся после освобождения; наличие файла само по себе не означает занятую блокировку.
Одновременный второй писатель должен завершиться ошибкой, а не потерять изменения первого.

Если есть ошибки отдельных записей, корректные новые записи всё равно сохраняются.
При структурной ошибке, неверном checkpoint, превышении итогового лимита, сбое получения
или отмене до фиксации прежнее состояние остаётся.
При отсутствии добавлений checkpoint не переписывается; для пустого первого импорта файл данных не создаётся.

Временный файл создаётся рядом с назначением и удаляется при обычном отказе.
Успешная замена предшествует публикации отчёта. Повтор после потери ответа распознаёт уже принятые Id.
Контракт не обещает устойчивость к отключению питания и атомарность между файлом, stdout и логами.
Это учебное файловое хранилище; проверка транзакций БД относится к L05.

## HTTP и ресурсы

Чтение response body ограничивается даже без Content-Length.
Проверяется application/json. Response, поток, token source, scope и host освобождаются владельцами.
Разрешена не более чем одна повторная попытка GET при временной ошибке;
404 и ошибки формата не должны превращаться в бесконечный retry.

Пользовательская отмена и deadline различаются. Общий deadline включает чтение тела после заголовков.
Проверки поднимают сервер только на loopback и выбирают свободный порт.

## Вывод и коды завершения

| Код | Значение | stdout |
| --- | --- | --- |
| 0 | Успех без ошибок записей, успешный export или help | JSON-отчёт, exported либо справка |
| 2 | Неверные аргументы или конфигурация | Пусто при ошибке |
| 3 | Файл, структура, лимиты, состояние или запись результата | Пусто |
| 4 | Частичный успех с ошибками записей | Полный JSON-отчёт |
| 5 | Ошибка HTTP/сети или сетевой deadline | Пусто |
| 130 | Отмена | Пусто до завершения операции |

Обычный отчёт содержит added, duplicates, failed, total и errors.
Сумма added+duplicates+failed равна числу элементов входного records.
total — число принятых записей в итоговом состоянии, включая прежние.
В errors только record и code; содержимое отклонённого текста не требуется.

Диагностика и структурированные логи идут в stderr.
--pretty меняет stdout на таблицу Spectre.Console и список ошибок, сохраняя коды и состояние.

## Контрольный набор

Используйте [mixed.json](data/mixed.json) и отсутствующий checkpoint.

| Запись | Решение |
| --- | --- |
| 1 | Добавить food=12.50 |
| 2 | Добавить travel=30.00 |
| 3 | Duplicate записи 1 после нормализации |
| 4 | invalid_date |
| 5 | invalid_amount |
| 6 | id_conflict с записью 1 |

Первый отчёт совпадает с [expected-first.json](data/expected-first.json): 2/1/3/2, код 4.
Повторный отчёт: 0/3/3/2, те же ошибки и те же байты состояния.
Экспорт содержит две записи; его импорт в то же состояние даёт 0/2/0/2 и код 0.
[valid.json](data/valid.json) содержит только две корректные записи.

## Проверка сдачи

```powershell
python tools/verify_integration.py
```

Скрипт проверяет поставляемый образец; он не является универсальным автогрейдером чужой структуры.
Для своего решения перенесите тот же набор контрактных сценариев и укажите команду запуска.

Обязательны обычный и пустой ввод, неверные поля, duplicate/conflict, повреждённый документ
и checkpoint, лимиты, повторный запуск, экспорт, сбой до замены файла, отмена,
два конкурирующих владельца блокировки, GET 503→200, 404 без retry и медленное тело.
Тесты не должны зависеть от публичного API, реального ожидания истечения даты или порядка Dictionary.

На защите объясните владение каждым disposable-объектом, направления зависимостей,
границу фиксации, стоимость обработки в памяти и отличие идемпотентности от exactly-once.
Расширение --dry-run из 30-C выполняется самостоятельно.
