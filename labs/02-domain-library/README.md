# L02. Библиотека правил и отчётов

Постройте второй этап ExpenseLedger после глав 11–18. Ориентир: 8–12 часов с проверками.
Работа развивает L01: одни правила должны обслуживать разные способы ввода и хранения.

## Структура решения

Создайте библиотеку Core с моделью, Result, интерфейсом хранения и сервисом.
Отдельная библиотека Memory реализует хранилище. Консольный клиент демонстрирует работу,
а отдельный проект проверок вызывает библиотеку напрямую.

Core не зависит от клиента или Memory. Он не читает файлы и не выводит сообщения в Console.
Парсинг текстового формата L01 остаётся на границе приложения.
Готовые проекты находятся в examples; самостоятельное решение размещайте в work/L02.

## Договор Money и Expense

Money — readonly record struct для одной условной денежной единицы.
Он хранит неотрицательный decimal, точно выражаемый сотыми.
Допустимы 0, 0.01, 1.2300m; недопустимы −1 и 1.001.
Default равен нулю. Оператор + сохраняет правила и выбрасывает OverflowException при переполнении.

Expense — неизменяемый record class с Guid Id, DateOnly Date, string Category и Money Amount.
Id не равен Guid.Empty. Сумма больше 0 и не выше 999999.99.
Категория после Trim содержит 1–32 ASCII-символа: первая буква, остальные буквы, цифры, дефис или подчёркивание.
Хранится нижний регистр. Невалидный аргумент конструктора вызывает подходящий ArgumentException
или его производный тип. Null-категория явно отклоняется.

Записи с одинаковыми данными равны; идентичность для хранилища определяется только Id.
Нельзя изменить сумму или категорию существующего Expense, обходя его конструктор.

## Договор Result

`Result<T> where T : notnull` создаётся только через Success(value) и Failure(error).
При успехе IsSuccess=true, Error=null и Value содержит значение, включая 0 для int.
При отказе IsSuccess=false, Error — непустой стабильный код;
чтение Value бросает InvalidOperationException.
Success с null и Failure с пустым/пробельным кодом отклоняются.

## Договор хранения

```csharp
public interface IExpenseStore
{
    bool TryAdd(Expense expense);
    IReadOnlyList<Expense> Snapshot();
}
```

Первое добавление Id возвращает true. Повторный Id возвращает false и сохраняет прежний объект,
даже если новая запись имеет другую сумму. Отдельные Id с одинаковыми остальными данными допустимы.

Snapshot возвращает отдельный снимок. Последующие добавления его не меняют.
Через возвращённый объект нельзя изменить содержимое хранилища.
Контракт не определяет порядок строк и не обещает потокобезопасность.

## Договор сервиса

LedgerService получает IExpenseStore через конструктор.
Add возвращает Success(expense) либо Failure("duplicate_id").
Added возникает один раз после успешного добавления и не возникает при дубликате.

ByCategory(year, month) возвращает read-only список CategoryTotal(Category, Total, Count).
Включаются записи только данного месяца и года. Категории отсортированы Ordinal;
итоги и количества точны. Пустой выбор даёт пустой список.
Year должен подходить DateOnly, month лежать в 1…12. Неверные аргументы отклоняются даже на пустом хранилище.

Готовый отчёт не меняется после добавления новых записей.
Вызов события синхронный. Если подписчик бросит исключение, оно выйдет из Add,
но расход уже сохранён. Проверьте это явно: повтор операции не должен создать вторую запись.

## Набор данных

Используйте четыре разных непустых Guid и следующие записи:

| Дата | Категория | Сумма |
| --- | --- | --- |
| 2026-01-01 | food | 12.50 |
| 2026-01-01 | travel | 30.00 |
| 2026-01-01 | FOOD | 7.50 |
| 2026-02-01 | food | 1.00 |

За январь: food=20.00, Count=2; travel=30.00, Count=1.
За февраль: food=1.00, Count=1. За март — пусто.
Число уведомлений после четырёх добавлений — 4, после попытки дубликата — всё ещё 4.

## Проверки приёмки

1. Default Money равен Money(0), а две равные суммы ведут себя как один ключ HashSet.
2. Отрицательная сумма и дробь 1.001 отклоняются; 1.2300 не округляется и допустима.
3. Expense запрещает нулевой Id, нулевую сумму, невалидную категорию и сумму выше лимита.
4. Повторный Id с изменёнными данными не перезаписывает исходную запись.
5. Снимок не меняется после Add. Не должно существовать обходного изменения через cast к List/IList.
6. Отчёт учитывает год и месяц, объединяет регистр, имеет явный порядок и сохраняется после новых Add.
7. Событие вызывается только при новом Id; после отписки обработчик не вызывается.
8. Бросающий обработчик не откатывает запись. Повторный Add возвращает duplicate_id.
9. Проверки работают при ru-RU, en-US и tr-TR; машинное представление отчёта остаётся одинаковым.
10. Тот же сервис и набор контрактных проверок работают со второй реализацией хранения на List.

```powershell
dotnet run --project examples/TypesAndQueries -- 18

```

CoreChecks проверяет поставляемое решение. Для проверки своего решения создайте отдельный тестовый
проект, ссылающийся на ваши Core/Memory, и перенесите контрактные сценарии; имена API приведены выше.
Не заменяйте собственные ссылки на библиотеки готовыми только ради зелёной проверки.

Сдайте исходники, схему зависимостей и список проверок. Объясните один дефект, который выявила
подмена хранилища или проверка снимка. Оценка из 10: контракты и инварианты 4; отчёт и ошибки 2;
направление зависимостей 2; воспроизводимые проверки и объяснение 2.
Нарушение денежной точности, уникальности Id или независимости снимка требует исправления до зачёта.

Дополнительно выполните 18-C: фильтр категории с явной нормализацией и сохранением исходных контрактов.
