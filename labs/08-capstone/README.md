# L08. Самостоятельный проект и защита изменения

**Цель:** самостоятельно собрать ExpenseLedger v3, пройти приёмку, устранить воспроизводимый дефект
и выполнить изменение требований. Предпосылки: главы 01–59 и L01–L07. Защита — после главы 60.
Можно выбрать другой предметный проект, если заранее сопоставлены все критерии ниже; число экранов
или используемых библиотек не является эквивалентом сложности.

## Что даёт комплект и что делаете вы

В репозитории есть работающий API L06, клиент/поставка L07 и чистое правило BudgetPolicy с проверками.
Вы самостоятельно добавляете бюджеты в БД, API и клиент, защищаете конкуренцию, расширяете диагностику
и сдаёте выпуск. Готовой интеграции бюджетов в LedgerWeb здесь нет: это самостоятельная итоговая работа.
Успешный `verify_capstone.py` подтверждает опорное правило и учебные опыты, а не сдачу вашей L08.

Храните решение в собственном Git-репозитории или отдельной рабочей копии. Если используете `work`
в этом репозитории, помните: каталог исключён из Git; для передачи нужна своя история и явный архив/remote.
Не публикуйте реальные расходы, секреты и чужие данные. Учебные credentials создаются локально.

## Обязательный договор ExpenseLedger v3

Сохраните валидацию, owner isolation, receipt/replay, optimistic update и outbox/inbox из L06.
Клиент — выбранный в L07 Blazor/WPF или другая обоснованная ветка с такими же состояниями.
Добавьте бюджет по ключу `(owner, year, month, category)`:

- Owner задаётся серверной аутентификацией. Категория нормализуется прежним правилом курса.
- Период — год и месяц DateOnly расхода. Границы: декабрь/январь и февраль високосного года.
- LimitMinor — целое число 0..long.MaxValue. Суммы расходов сохраняют диапазон 1..99999999 minor units.
- Отсутствующая строка бюджета означает отсутствие ограничения; ноль означает нулевой лимит.
- Создание/изменение лимита ниже уже потраченного отклоняется с 409. Ошибочный формат — 400.
- При создании ExpectedVersion=0, новая version=1. Изменение требует текущую version и увеличивает её.
  Устаревшая version возвращает 409; нельзя потерять параллельное изменение.
- Остаток вычисляется по реально принятым расходам. Каждая операция, меняющая сумму или лимит,
  участвует в одном протоколе конкурентного доступа к соответствующей группе.
- Новый пакет либо целиком проходит по всем группам, либо не создаёт расходов, receipt и outbox.
  Переполнение суммы отклоняется как недопустимый пакет, без частичной записи.
- Успешный повтор BatchId с тем же payload возвращает прежнюю квитанцию. Изменённый payload — 409.
  Идентичный уже существующий ExpenseId не занимает остаток повторно; конфликтующий — 409.

Договор API можно выразить как PUT `/api/v1/budgets/{year}/{month}/{category}` с LimitMinor/ExpectedVersion
и GET для просмотра. Зафиксируйте формат ответа, error codes, 401/404/409 и схему в OpenAPI.
Не передавайте owner через маршрут как авторизацию. Ограничение лимита должно действовать и при прямом
HTTP-вызове в обход клиента. В UI нужны Loading/Empty/Error/Canceled, остаток и понятный отказ.

## Данные и независимые ожидаемые ответы

Файл [budget-cases.json](data/budget-cases.json) содержит 12 случаев для числового правила, включая
точную границу, ошибочное состояние и overflow. JSON хранит Int64 точно; не прогоняйте его через
JavaScript Number перед проверкой крайних значений. Для browser API большие Int64 передавайте
десятичной строкой либо явно ограничьте поддерживаемый UI-диапазон и отразите это в договоре.

Основной сценарий выполняйте для нового owner A: бюджет food за январь 2026 равен 2000, расход
от 2026-01-10 равен 1250. Следующий пакет [250,500] разрешён: итог 2000. На отдельном свежем
состоянии пакет [751] отвергнут: итог остался 1250. У owner B и в феврале независимое состояние.

Для всех гонок используйте свежую БД/owner и стартовый барьер. Конкретный победитель не фиксирован.
Проверяйте множество допустимых результатов и инвариант после обоих ответов. Отдельно запускайте
два процесса API с одной БД: только два Task в одном объекте не доказывают защиту между процессами.
При exhausted busy retry допустим документированный 503 без эффекта; 500 и перерасход недопустимы.

## Матрица обязательной приёмки

| ID | Вход/действие | Ожидаемый результат и свидетельство |
| --- | --- | --- |
| CAP-01 | A: limit=2000, spent=1250, [250,500]; свежий сценарий [751] | 2000 после успеха; 1250 после отказа, ни одной частичной строки |
| CAP-02 | B запрашивает/меняет ресурс A; соседний месяц и категория | Нет чужого состояния; независимые суммы и лимиты |
| CAP-03 | Повтор успеха, другой payload, одинаковый ExpenseId в новом пакете | Replay без расходования остатка; 409 для конфликта; дубликат не добавляет сумму |
| CAP-04 | Один пакет затрагивает две группы, в одной не хватает 1 | Обе группы неизменны; нет нового receipt/outbox |
| CAP-05 | spent=600, limit=1000; два процесса импортируют по 300 | Ровно один успех, итог 900; повтор после управляемого busy не допускает второй расход |
| CAP-06 | Два изменения budget с одной version; лимит ниже spent | Один version-конфликт; недопустимое уменьшение не меняет данные |
| CAP-07 | Неверная дата/сумма, 101 строка, null, overflow | Управляемый отказ без частичного commit и без раскрытия внутреннего exception |
| CAP-08 | Потеря ответа после commit, restart, повтор; сбой фоновой доставки | Receipt переживает restart; outbox/inbox сохраняют договор; восстановление без дубликата эффекта |
| CAP-09 | Миграция прежней L06 БД, publish, backup/restore | Данные сохранены; прежние категории без бюджета доступны; восстановленный отчёт совпал |
| CAP-10 | Клиент, отмена, load и независимый запуск | Видны состояния/отказ; результаты измерений и инструкция воспроизводимы |

Для CAP-09 новая схема сначала добавляется совместимым способом. Откат к L06-коду после включения
бюджетов небезопасен: старая версия не знает ограничения и может записать перерасход. Зафиксируйте
точку, после которой нужен forward fix или восстановление данных с согласованной потерей последних
изменений. Откат папки из L07 с одинаковой схемой не является готовым планом для v3.

## Этапы работы и границы решений

1. Зафиксируйте договор и исходный commit. Составьте таблицу «требование → тест → evidence».
2. Напишите ADR конкурентной записи и ADR хранения spent. Выберите схему и миграцию.
3. Соберите вертикальный срез: настройка бюджета → импорт → остаток в клиенте.
4. Добавьте CAP-02..CAP-08, включая два процесса и настоящую БД. Исправьте найденные нарушения.
5. Проведите publish/restore, измерьте нагрузку и оформите runbook. Передайте первую версию на review.
6. Получите CR-01, сохраните failing regression, реализуйте изменение и повторите затронутую приёмку.

Для ADR достаточно страницы: контекст; варианты; решение; последствия; доказательства; статус.
Схема должна показывать auth boundary, transaction boundary, owner и mutable state. Не требуется
добавлять broker или микросервисы: уже существующий durable outbox позволяет проверить нужное поведение.

## Нагрузка, сбой и восстановление

Для повторимого учебного измерения подготовьте 10000 расходов, выполните 100 прогревочных чтений,
затем 1000 чтений отчёта при параллелизме 1 и 20. Сохраните ошибки, median/p95/max, allocations или
RSS, количество SQL-запросов и параметры машины. До оптимизации задайте свой измеримый целевой p95;
курс не назначает одинаковую скорость разным компьютерам. Не смешивайте прогрев с измерением.

Во время отдельного прогона отключите тестовую зависимость, затем восстановите её. Запишите симптом,
timeline, trace/log без секретов, причину и действие. Убедитесь, что независимый отчёт продолжает работать.
Сделайте backup через поддерживаемый API, восстановите в новый файл и сравните отчёт, receipt и бюджеты.
Если есть внешние эффекты, заранее решите, как restore не отправит их повторно.

Передача включает запуск из publish-папки, конфигурацию, явную миграцию, readiness и остановку.
Выберите проверенную целевую среду: локальная Windows допустима при точном описании ограничений.
Чистая VM, Linux, публичный TLS и реальное мобильное устройство засчитываются только после собственного
испытания; наличие Dockerfile или target в csproj само по себе не является свидетельством.

## CR-01: редактирование суммы после первой приёмки

Заказчик хочет менять сумму существующего расхода, сохраняя месячный лимит. ID, дата и категория
расхода в этом изменении неизменны; перенос между месяцами — другая задача. Используйте прежний
ExpectedVersion расхода и обеспечьте атомарность с бюджетом, report revision и outbox.

На новом сценарии единственный расход равен 1250, его version=0, бюджет равен 2000:

1. Update с expected=0 до 2000 успешен: spent=2000, expense version=1.
2. Update с expected=1 до 2001 отклонён: spent=2000, version остаётся 1.
3. Update с expected=1 до 1000 успешен: spent=1000, expense version=2.
4. Повтор старого update с expected=1 возвращает 409 и не создаёт новый эффект.
5. Одновременные update и import не нарушают лимит; проверьте два процесса и финальную сумму.

Сначала предъявите тест, который падает на первой версии проекта по правильной причине. Затем
измените код и покажите его прохождение вместе с прежними сценариями. Обновите клиент, error contract
и документацию. Не добавляйте отрицательные расходы в import ради вычисления delta.

## Рубрика и блокирующие дефекты

Для каждой строки проверяющий выставляет 0, половину или полный вес: нет свидетельств; часть
подтверждена с описанным пробелом; выполнены все критерии. Приложите ссылки на исходники/команды/логи.

| Область | Вес | Что подтверждает полный балл |
| --- | --- | --- |
| Предметный договор | 20 | Границы, группы, replay, ошибки и CR-01 объяснены и проверены |
| Данные и конкуренция | 20 | Миграция, атомарность, два процесса, version и restore |
| Auth и внешняя граница | 15 | Owner isolation, валидация, ограничение входа, отсутствие секретов в выводе |
| Тесты и диагностика | 15 | Независимые ответы, обнаруженная регрессия, incident и измерения |
| Клиент выбранной ветки | 10 | Полный пользовательский путь, Loading/Error/Cancel и конфликт |
| Поставка и передача | 10 | Закреплённая сборка, publish, конфигурация и воспроизводимый runbook |
| Объяснение и изменение | 10 | ADR, review, CR-01 и точное описание границ доказательств |

Порог — **80/100**, по каждой области не меньше половины веса. Независимо от суммы блокируют сдачу:
чужие данные доступны; бюджет нарушается гонкой; ошибочный пакет оставляет частичную запись;
успешный повтор создаёт второй расход; заявленное восстановление теряет подтверждённые данные;
сборка/запуск по инструкции не воспроизводятся. Сначала исправьте блокирующее нарушение, затем пересчитайте баллы.

## Комплект передачи и защита

Предъявите commit, README запуска, конфигурационный пример, миграции, demo data, ADR, тесты,
отчёты CAP-01..CAP-10, benchmark/incident, описание CR-01 и release manifest. Evidence относится
к сдаваемому commit. Если review был самостоятельным, так и укажите; не называйте его внешней оценкой.

На защите выполните пять действий: запуск с новой БД; импорт/отказ; гонка; восстановление; изменение
суммы по CR-01. Затем объясните lifetime одного ресурса, один async-путь и одну транзакцию по исходникам.
Закончите списком трёх пробелов и следующими измеримыми упражнениями из главы 60.

Методичка предоставляет все условия, опорные примеры и критерии. Самостоятельная реализация,
демонстрация и защита являются результатом учащегося.
