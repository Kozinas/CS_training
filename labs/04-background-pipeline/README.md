# L04. Ограниченный фоновый конвейер

**Цель:** перейти от одного документа L03 к потоку записей, сохранив правила расходов,
детерминированный результат, отмену и воспроизводимый запуск.
Предварительно изучите главы 31–35 и сдайте L03. Готовую реализацию открывайте после собственной попытки.

## Что сдавать

Решение содержит библиотеку конвейера, Host-приложение, проверки, инструкцию запуска и протокол измерений.
Укажите, кто закрывает очереди, кто меняет состояние, когда возможна фиксация и что происходит при отмене.
Не достаточно показать только успешный запуск: нужны управляемые сценарии отказов.

## Формат входа

Вход — локальный файл NDJSON: на каждой физической строке один JSON-объект
с полями id, date, category, amount. Это отдельный потоковый формат; объект с version/records из L03
не является NDJSON-входом. Пример одной строки:

```json
{"id":"11111111-1111-1111-1111-111111111111","date":"2026-01-10","category":"food","amount":"12.50"}
```

Правила Id, даты, категории и суммы совпадают с L03. Нормализация категории предшествует сравнению.
Запрещены неизвестные/повторные JSON-свойства, комментарии и неправильные типы.
Файл использует UTF-8; допускаются BOM в начале, LF/CRLF и последняя строка без LF.
Перевод строки внутри JSON-строки должен быть escape-последовательностью, а не физическим LF.

Пустая физическая строка — invalid_json и учитывается в processed/failed.
Пустой файл содержит ноль строк. Один завершающий LF не создаёт дополнительную строку;
два LF подряд создают пустую строку. Один BOM без данных считается одной пустой строкой.
Неправильный JSON, включая повреждённый UTF-8 внутри строки, даёт invalid_json только для этой строки.
JSON null даёт invalid_id. Структурно правильная строка проверяется в порядке Id, date, amount, category.

## Ограничения готового приложения

| Ресурс | Значение по умолчанию | Допустимое изменение |
| --- | --- | --- |
| Workers P | 4 | CLI --workers, 1–32 |
| Capacity C каждой очереди | 8 | CLI --capacity, 1–1024 |
| Window W допущенных строк | 16 | CLI --window, 1–4096 |
| Байты физической строки | 4096 | До удаления CR/BOM, без LF |
| Байты всего входа | 16 MiB | Включая BOM и разделители |
| Число физических строк | 100000 | Включая ошибочные |
| Итоговое состояние | 10000 расходов, 16 MiB JSON | Превышение отменяет фиксацию |
| Подробные ошибки в отчёте | Первые 20 | failed считает все |
| Попытки временной ошибки | 3 | Задержка между попытками 50 мс |

Остальные лимиты настраиваются через PipelineOptions при использовании библиотеки,
но не вынесены в CLI. Для библиотеки Validate задаёт конечные допустимые диапазоны.
Размер строки проверяется при чтении; накопление полного входного файла запрещено.
Состояние ограничено, но хранится в памяти; это не обработчик произвольно большой базы расходов.

## Стадии и порядок

Producer читает ограниченные строки, получает разрешение окна и записывает задание с номером.
P workers проверяют строки. Collector получает результаты через вторую ограниченную очередь
и применяет их строго в исходном порядке. Разрешение окна освобождается после применения.
Обе очереди используют FullMode.Wait, без потери сообщений при заполнении.

Решение для корректной записи:

1. Новый Id добавляется в кандидат состояния.
2. Совпадающие Id и нормализованные поля дают duplicate.
3. Совпадающий Id с другими полями даёт id_conflict; прежняя запись сохраняется.

Поэтому конфликт внутри файла решается порядком входа, а не скоростью потоков.
Неправильные поля проверяются до дедупликации. Коллектор — единственный владелец изменяемого Dictionary.
Каждый допущенный элемент даёт ровно один результат при нормальном завершении.

## Сбой и повтор

Ошибочная строка не прерывает файл. Только TransientWorkException допускает повтор;
после трёх неудач результат — retry_exhausted, retried=2 для этой строки.
Настоящий JsonRowProcessor не использует повторы: они проверяются через подмену IRowProcessor.
Подмена обязана быть потокобезопасной, идемпотентной и поддерживать CancellationToken.

Ошибка I/O, неожиданное исключение обработчика, превышение лимита или внешняя отмена
останавливает операцию. Заблокированные участники должны проснуться; вызывающий получает исход
только после завершения всех стадий. При инфраструктурном сбое кандидат не сохраняется.
Первый сохранённый инфраструктурный сбой имеет приоритет над сопутствующей отменой.

При нормальном EOF очереди опустошаются. Host.StopAsync выполняет abort текущей работы,
а не drain с обязательным сохранением. ShutdownTimeout=10 секунд не может принудительно остановить
процессор, игнорирующий token; такой процессор нарушает договор.

## Checkpoint

Формат — JSON версии 1, совместимый с экспортом L03. Сначала проверяется прежнее состояние;
повреждение, неверная запись и повторный Id в checkpoint — фатальная ошибка.
На всю работу удерживается state.json.lock через FileShare.None. Lock-файл остаётся на диске,
а исключительность определяется открытым handle. Все участники записи должны соблюдать этот протокол.

Фиксация выполняется один раз после полного чтения и завершения стадий: временный файл в каталоге
checkpoint, flush, закрытие и замена. При нуле добавлений checkpoint не переписывается.
Вход не должен совпадать с checkpoint или его lock-файлом; проверка сравнивает нормализованные пути.
Alias через hard link/symlink не определяется: используйте отдельные обычные файлы в своём work.
Потеря питания и сетевые файловые системы не входят в гарантию примера.

Отмена до замены сохраняет прежние байты. Сбой после замены, но до печати отчёта не отменяет запись;
повторный запуск распознаёт сохранённые расходы как duplicates. Очереди не долговечны,
а exactly-once для внешних побочных эффектов не заявляется.

## Проверяемый пример

```powershell
$jobArgs = @("--file", "labs/04-background-pipeline/data/mixed.ndjson",
    "--state", "work/l04/state.json", "--workers", "4",
    "--capacity", "8", "--window", "16")
dotnet run --project examples/Integration/PipelineWorker -- @jobArgs
```

[mixed.ndjson](data/mixed.ndjson) содержит шесть строк.
На отсутствующем checkpoint ожидается [expected-first.json](data/expected-first.json):
processed=6, added=2, duplicates=1, failed=3, total=2, retried=0.
Ошибки: строка 4 invalid_date, 5 invalid_amount, 6 id_conflict; errorsTruncated=false.
Код завершения 4 означает частичный успех с сохранением двух расходов.
Повтор даёт added=0, duplicates=3 при тех же остальных полях и байтах checkpoint.

stdout содержит только JSON при кодах 0/4; диагностические сообщения идут в stderr.
При других кодах stdout пуст: 2 — аргументы, 3 — данные/I/O/лимит,
130 — отмена, 1 — непредвиденная ошибка реализации. Длительность записывается в журнал,
но не в сравниваемый JSON, чтобы отчёт оставался воспроизводимым.

## Приёмка

- Пустой файл, BOM, CRLF, короткие чтения и отсутствие последнего LF обработаны по договору.
- При P/C/W=1/1/1, 2/1/3, 4/8/16 получаются одинаковые отчёты и состояние.
- Удержание строки 1 не позволяет допустить более W строк; число активных processor не превышает P.
- Нормальный EOF не теряет записи; ошибка consumer будит producer с заполненной очередью.
- Отмена завершает все processors до возврата, checkpoint не меняется, временные файлы не остаются.
- Три неудачные попытки дают одну ошибку retry_exhausted; отмена прерывает задержку повтора.
- Неправильный checkpoint и занятый lock не перезаписываются; повторный импорт идемпотентен.
- Проверки времени используют сигналы для порядка и конечный timeout для обнаружения зависания.
- Нагрузочный опыт сохраняет результат, параметры, время и ограничения интерпретации.

Команды проверки: `python tools/verify_pipeline.py`; измерения после Release-сборки:
`python tools/measure_pipeline.py`. Встроенные проверки не оценивают решение учащегося автоматически:
при переносе контрактных сценариев подключите свою реализацию и сохраняйте независимые ожидаемые результаты.
Пример, проверки и benchmark находятся в [Integration](../../examples/Integration/README.md).
